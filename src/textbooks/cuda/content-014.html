2.7Benchmarking Correctly

Most "kernel is faster" claims are measurement artifacts

The single most common mistake in CUDA performance work is timing the wrong thing. The cardinal rules:

  1. Use CUDA events, not std::chrono or clock_gettime. The host clock will measure host time, which includes kernel-launch overhead, driver queuing, and may miss the actual GPU work entirely if the launch is asynchronous.
  2. Warm up the GPU. The first kernel launch pays JIT compilation costs (if PTX is loaded), driver setup, and clock ramp-up. Throw away the first 5–10 runs.
  3. Run many iterations (≥ 100, often 500–1000) and report mean and standard deviation. Variance under 1% is the bar for "stable enough to claim a winner."
  4. Lock GPU clocks before benchmarking. Without locking, the boost clock drifts with temperature and you compare apples to oranges. (Covered in §5.4.)
  5. Always run a correctness check against a CPU reference (or against a trusted GPU reference). A "30% faster" kernel that produces wrong answers is worse than a slow correct kernel.
#include <cuda_runtime.h>
#include <chrono>
#include <vector>
#include <numeric>
#include <cmath>
#include <cstdio>

struct BenchResult {
    double mean_ms;
    double stddev_ms;
    double gflops;
};

template <typename Launcher>
BenchResult benchmarkKernel(Launcher launch,
                            long long flops,           // 2*M*N*K for GEMM
                            int warmup = 10,
                            int iters  = 500)
{
    cudaEvent_t start, stop;
    cudaEventCreate(&start);
    cudaEventCreate(&stop);

    // 1) Warmup.
    for (int i = 0; i < warmup; ++i) launch();
    cudaDeviceSynchronize();

    // 2) Timed runs.
    std::vector<float> times_ms(iters);
    for (int i = 0; i < iters; ++i) {
        cudaEventRecord(start);
        launch();
        cudaEventRecord(stop);
        cudaEventSynchronize(stop);
        cudaEventElapsedTime(&times_ms[i], start, stop);
    }

    // 3) Stats.
    double mean = std::accumulate(times_ms.begin(), times_ms.end(), 0.0) / iters;
    double var  = 0.0;
    for (float t : times_ms) var += (t - mean) * (t - mean);
    var /= iters;
    double sd = std::sqrt(var);

    cudaEventDestroy(start);
    cudaEventDestroy(stop);

    // 4) Convert to GFLOPS.  flops / (ms * 1e6) = GFLOPS.
    double gflops = (double)flops / (mean * 1e6);
    return { mean, sd, gflops };
}

// Usage:
//   long long flops = 2LL * M * N * K;
//   auto r = benchmarkKernel([&]() {
//       gemmTiled<<<grid, block>>>(d_A, d_B, d_C, M, N, K);
//   }, flops);
//   printf("mean=%.3f ms  stddev=%.3f ms  %.1f GFLOPS\n",
//          r.mean_ms, r.stddev_ms, r.gflops);

Correctness check

// CPU reference (slow but trusted).
void gemmRef(const float* A, const float* B, float* C, int M, int N, int K) {
    for (int i = 0; i < M; ++i)
        for (int j = 0; j < N; ++j) {
            float s = 0.f;
            for (int k = 0; k < K; ++k) s += A[i*K + k] * B[k*N + j];
            C[i*N + j] = s;
        }
}

// Compare with a relative-tolerance threshold.
bool verify(const float* test, const float* ref, int N, float rtol = 1e-3f) {
    int wrong = 0;
    double maxrel = 0.0;
    for (int i = 0; i < N; ++i) {
        float r = ref[i];
        float t = test[i];
        float denom = std::max(std::abs(r), 1.0f);
        float rel = std::abs(t - r) / denom;
        if (rel > maxrel) maxrel = rel;
        if (rel > rtol) ++wrong;
    }
    printf("verify: %d/%d wrong, max rel err = %.2e\n", wrong, N, maxrel);
    return wrong == 0;
}
// rtol = 1e-3 is appropriate for FP16; tighten to 1e-5 or so for FP32.

2.8The CUDA Software Stack — From .cu to SASS

What actually happens when you press nvcc
Reading order. Every box in the compile pipeline (preprocessor → CUDA front-end → PTX → SASS → cubin → fatbin) is a checkpoint where something can go wrong silently and you must know how to peek. The atomic notes below split the pipeline into its inspectable stages.
[[A2.8.1]]

Runtime API vs Driver API — two front doors to the same hardware

toolchain

CUDA exposes two C APIs that target the same underlying driver. The Runtime API (cuda_runtime.h, cudaMalloc, cudaMemcpy, cudaLaunchKernel) is what you use 95% of the time; it hides the context, module loading, and module unloading behind global per-process state. The Driver API (cuda.h, cuMemAlloc, cuLaunchKernel) exposes those — CUcontext, CUmodule, CUfunction — explicitly. Use the Driver API when you need to JIT load PTX at runtime, manage multiple contexts on one process, or implement a library others embed; for kernels and applications, the Runtime API is the right level.

You can call the two from the same process — the runtime is implemented on top of the driver — but mixing handles (driver CUstream vs runtime cudaStream_t) is a recipe for confusion. They are type-compatible on most platforms but not on all.

Used by [[A2.8.2]] [[A2.10.4]]
[[A2.8.2]]

The nvcc pipeline — five stages you can peek into

toolchain
  1. Host/device split. cudacc splits a .cu file into host-only and device-only intermediate files. The host file is shipped to your usual C++ compiler (g++/clang/cl); the device file goes to the CUDA front-end.
  2. CUDA front-end → PTX. NVIDIA's Clang-based front-end lowers the device file into PTX — a virtual ISA in textual form. nvcc --ptx stops here. PTX is forward-compatible across architectures; the driver can JIT-compile it at load time.
  3. ptxas → SASS. ptxas consumes PTX and emits SASS — the actual instructions for a specific compute capability (-arch=sm_86). This is where register allocation, instruction scheduling, and most peephole optimization happen. --ptxas-options=-v prints register and shared-memory usage; -keep keeps the intermediate SASS as .cubin.
  4. fatbin packaging. fatbinary bundles one or more cubins (different architectures) plus optionally the original PTX into a "fat binary" that the runtime can dispatch from based on the device it finds at load time.
  5. Driver load & JIT. At cuModuleLoad time (or implicitly during the first kernel launch), the driver picks the best cubin for the running device; if none matches, it JIT-compiles the embedded PTX to SASS, caching the result in ~/.nv/ComputeCache.

Inspecting the output of each stage is how you debug the compiler. cuobjdump --dump-ptx and cuobjdump --dump-sass extract PTX and SASS from a finished binary. nvdisasm disassembles a cubin into human-readable SASS. nvprof --print-gpu-trace (older) or ncu --target-processes all (newer) tells you which cubin was actually selected on a particular GPU.

Fatbin and -gencode — shipping one binary that runs everywhere

toolchain

A typical release-time compile looks like nvcc -gencode arch=compute_80,code=sm_80 -gencode arch=compute_86,code=sm_86 -gencode arch=compute_86,code=compute_86 .... The third entry, code=compute_86, embeds PTX so unknown future GPUs can JIT-compile it. Ship without it and your binary fails to launch on any device newer than what you compiled for; ship with it and the driver pays a one-time JIT cost on first launch (a few seconds in extreme cases). The right compile policy: ship cubins for every architecture you care about plus PTX for the newest architecture, so future GPUs can still run.

__launch_bounds__ and --maxrregcount — telling ptxas your contract

toolchain

Two ways to constrain the register usage of a kernel: a per-kernel attribute or a global compile flag. __launch_bounds__(maxThreadsPerBlock, minBlocksPerSM) tells ptxas "this kernel will run with at most maxThreadsPerBlock threads, and I want enough register room to host minBlocksPerSM blocks simultaneously." ptxas then targets a register budget of 65536 / (maxThreadsPerBlock · minBlocksPerSM) and spills if the kernel needs more. --maxrregcount=N is the global, less precise version. Prefer __launch_bounds__ because it's local to the kernel and survives refactoring.

Sharp edge

A too-tight launch_bounds can murder a Tensor-Core-heavy kernel: the compiler will spill rather than refuse, and the spills cost orders of magnitude more than the occupancy you bought. Profile both versions.
