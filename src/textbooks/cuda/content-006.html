Matrix multiply: the canonical parallel workload

Consider the operation at the heart of nearly every modern neural network and scientific computing kernel:

C[i,j] = Σk A[i,k] · B[k,j] for all i, j

Every output element C[i,j] is computed from a row of A and a column of B, completely independently of every other output element. For an M×N output matrix, that is M·N independent dot products. There is no data dependency between them. They could all run at once if the hardware existed. That is the entire reason GPUs exist — they are the hardware that exists.

The mental model

A CPU is a sports car: fast off the line, narrow, optimized for one driver getting from A to B in record time. A GPU is a freight train: enormous payload per trip, terrible if you need to make a sudden turn, unbeatable if your problem looks like move ten thousand identical things from A to B. Matrix multiply, attention, convolution, n-body simulation, ray-triangle intersection, and most of computer graphics look like that. That is why GPUs run them.

// ============================================================
// CPU: one thread, one big triple nested loop.
// Wall-clock time scales with M * N * K.
// ============================================================
for (int i = 0; i < M; i++) {
    for (int j = 0; j < N; j++) {
        float acc = 0.f;
        for (int k = 0; k < K; k++) {
            acc += A[i * K + k] * B[k * N + j];
        }
        C[i * N + j] = acc;
    }
}

// ============================================================
// GPU: launch M*N threads. Each one computes ONE output element.
// Wall-clock time scales with K (the inner loop), not M*N*K,
// because the M*N axis runs in parallel across thousands of cores.
// ============================================================
__global__ void gemmKernel(const float* A, const float* B, float* C,
                           int M, int N, int K) {
    int i = blockIdx.y * blockDim.y + threadIdx.y;  // row
    int j = blockIdx.x * blockDim.x + threadIdx.x;  // col
    if (i >= M || j >= N) return;
    float acc = 0.f;
    for (int k = 0; k < K; k++) {
        acc += A[i * K + k] * B[k * N + j];
    }
    C[i * N + j] = acc;
}
// Launch: one thread per (i, j) — M*N threads total.
dim3 block(16, 16);
dim3 grid((N + 15) / 16, (M + 15) / 16);
gemmKernel<<<grid, block>>>(A, B, C, M, N, K);
Mental model worth keeping
If your problem has an outer loop where every iteration is independent, you have GPU work. The whole game is identifying that loop, mapping iterations to threads, and feeding the resulting army of threads from memory fast enough to keep them busy.

1.2The Streaming Multiprocessor (SM)

The actual compute unit you need to understand

A modern NVIDIA GPU is, in the end, a collection of Streaming Multiprocessors (SMs) glued together with a memory system. Every CUDA optimization you will ever do is, ultimately, an attempt to keep the arithmetic units inside an SM busy. So you need to know what is inside one.

The numbers vary by generation. On the RTX 3090 (Ampere, GA102, compute capability sm_86) there are 82 SMs.[2] On the A100 (Ampere, GA100, sm_80) there are 108. On the H100 (Hopper, sm_90) there are 132. The internals of an SM, however, follow a recognizable pattern across generations.

Inside an Ampere SM

An Ampere SM is divided into four processing blocks (sometimes called SM sub-partitions, abbreviated SMSP). Each sub-partition is, for our purposes, a self-contained mini-SM:

  • Its own warp scheduler and dispatch unit.
  • Its own slice of the SM's register file (16,384 32-bit registers per sub-partition × 4 = 65,536 per SM).
  • 16 FP32 CUDA cores (so 64 per SM) and 16 INT32 ALUs that can co-issue with the FP32 units on Ampere — this is why the GA10x marketing material counts 128 "CUDA cores" per SM (the FP32-capable lanes including the dual-purpose ones).
  • One third-generation Tensor Core — so 4 per SM. Each can do a fairly large matrix multiply-accumulate per clock.
  • 4 Special Function Units (SFUs) for transcendentals (sin, cos, rcp, rsqrt).
  • 8 load/store units.

Above the four sub-partitions, the entire SM shares:

  • 128 KB of combined L1 cache and shared memory, split configurably (e.g. 32 KB L1 / 96 KB shared, or other ratios up to a maximum shared-memory allotment per block defined by the architecture).
  • A texture/L1 unit (l1tex in Nsight Compute) handling global-memory loads, texture, and shared-memory traffic.
  • A constant cache.
