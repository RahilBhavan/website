From .cu to Bare-Metal SASS

Learning goal. Stop treating nvcc as a black box. By the end of this chapter you can name every binary on the compilation path, read PTX and SASS side-by-side with the C++ that produced them, control register usage and spill behavior, JIT-compile kernels at runtime with NVRTC, and use cuobjdump / nvdisasm / cu++filt to extract the truth from any compiled binary. The compiler is not your enemy — once you can read it, it is the single most reliable source of information about what your kernel will do.

10.1The nvcc Pipeline — Every Stage Named

What happens between nvcc kernel.cu and a runnable binary

Cluster. nvcc is a driver, not a compiler. It dispatches host code to your system C++ compiler (g++, clang, MSVC) and device code through three dedicated front- and back-end stages. Understanding the boundaries between them is what turns "the compiler stripped my variable" from a mystery into a debuggable event.
[A10.1.1]

The Six-Stage Compilation Pipeline

toolchain · pipeline

A single foo.cu traverses six logical phases. Each stage has a binary you can invoke directly when debugging.

  1. cudafe++ — a CUDA-aware C++ front-end. Splits the .cu source into a host stub (calls to cudaLaunchKernel) and a device stub (kernels and __device__ functions). Produces foo.cpp1.ii (host) and foo.cpp4.ii (device).
  2. cicc — the NVVM (LLVM-IR) optimizer. Translates the C++ AST to NVVM IR, runs optimization passes (inlining, SROA, GVN, loop unrolling, instruction selection), emits PTX (foo.ptx).
  3. ptxas — assembles PTX into SASS (machine code) for one or more SM architectures. This is where register allocation, instruction scheduling, and the final ABI are decided. Output is a cubin (ELF) per architecture.
  4. fatbinary — concatenates multiple cubins (and optionally the PTX itself for forward compat) into a single fat-binary blob.
  5. Host C++ compiler — gcc/clang/MSVC processes the host stub, embedding the fatbinary as a const array via __cudaRegisterFatBinary.
  6. Host linker — links the host objects with libcudart (or statically with cudadevrt for device-side new/printf). Final ELF/PE has both host CPU code and embedded device code.

The fat-binary embedded in your executable is read at load time by the CUDA driver. If a section matches your GPU's compute capability, the driver maps that cubin directly. Otherwise the driver JIT-compiles the embedded PTX. This is why distributing PTX makes your binary forward-compatible — and why omitting PTX (-arch=sm_80 --no-ptx) makes it smaller but architecture-locked.

Top track is host code (CPU). Bottom track is device code (GPU). They merge in the fatbinary and finally at the linker. Every arrow is a separate process you can intercept with --keep --verbose.
# --verbose prints every subprocess; --keep retains intermediate files
nvcc --verbose --keep -arch=sm_80 kernel.cu -o kernel 2>&1 | grep -E "cudafe|cicc|ptxas|fatbinary"

# Files left behind by --keep:
ls kernel.cudafe1.cpp     # host stub
ls kernel.cpp1.ii         # preprocessed host
ls kernel.ptx             # PTX
ls kernel.cubin           # SASS (binary)
ls kernel.fatbin          # fatbinary blob

# Dump the PTX to stdout
nvcc -arch=sm_80 -ptx kernel.cu -o /dev/stdout | head -80

# Only emit a cubin (skip linking)
nvcc -arch=sm_80 -cubin kernel.cu -o kernel.cubin
Tip

Add -Xptxas -v to any compile to print per-kernel register count, spill stores/loads, shared-memory bytes, and constant-memory bytes. This single flag is the difference between guessing and knowing whether your latest tile-size change blew the register budget.

10.2ptxas, Register Pressure, and Spills

Why the same C++ runs 2× faster depending on a single __launch_bounds__

[A10.2.1]

The Register File Is a Shared Resource

registers · occupancy

Each SM owns a fixed register file: 65,536 × 32-bit registers on Ampere (sm_80/86) and Hopper (sm_90). All threads resident on that SM split it. If your kernel uses 64 registers/thread, an SM can host at most 65536 / 64 = 1024 threads — i.e. 32 warps, or 50% of the architectural max of 2048. Use 128 registers/thread and you crash to 25% occupancy.

The trade-off is spilling. If ptxas cannot allocate everything you need into registers, it generates loads and stores to local memory — which on the GPU is actually global memory backed by L1/L2. A single spill can cost 100s of cycles per access. The compiler does its best, but you set the budget.

Three knobs control this:

  • -maxrregcount=N — hard cap, applies to every kernel in the TU.
  • __launch_bounds__(maxThreadsPerBlock, minBlocksPerSM) — per-kernel, ptxas computes the register cap from the desired occupancy.
  • -Xptxas -O3 (default) vs -O0 — affects how aggressively cicc/ptxas inline and unroll, which directly grows register pressure.

Reading a -Xptxas -v Report

diagnostics

The verbose output is one line per kernel and tells you everything that matters in two seconds:

ptxas info    : Compiling entry function 'sgemm_kernel' for 'sm_80'
ptxas info    : Function properties for sgemm_kernel
    1024 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
ptxas info    : Used 96 registers, 16384 bytes smem, 388 bytes cmem[0]

Decode:

  • Stack frame — non-zero means you have local arrays or a recursive call. Try to drive to 0; even 0 spill stores can mask large stack frames.
  • Spill stores/loads — bytes per thread written/read to local memory because the register allocator ran out. Anything > 0 is a red flag.
  • Used registers — divide 65,536 by this to find max threads/SM, then divide by your block size for blocks/SM.
  • smem — bytes of static shared memory. Combine with dynamic shared mem to validate against the 100 KB/SM limit (sm_80) or 228 KB/SM (sm_90).
  • cmem[0] — bytes loaded from kernel param + global constant memory bank 0.
Worked Example — Pushing a Kernel Over the Spill Cliff

Suppose you have an 8×8 register-tiled GEMM (§2.5) using 72 registers/thread, 256 threads/block. Per-SM occupancy: 65536 / 72 ≈ 910 threads → 3 blocks of 256 → 768 threads → 37.5% occupancy. You want more occupancy so you set __launch_bounds__(256, 4), asking for 4 blocks/SM = 1024 threads.

ptxas must now squeeze into 65536 / 1024 = 64 registers/thread. The compiler spills 8 bytes/thread to local memory. Profiling shows a 3× slowdown despite the "higher occupancy." Spills moved hot operands to global memory and burned bandwidth that was already saturated.

Lesson: Occupancy is a secondary metric. The primary metric is "no spills, instructions per cycle high, memory throughput high." Pick the register count that lets your inner loop keep its operands in registers; let occupancy fall out of that decision, not lead it.

Pitfall

A struct passed by value to a __device__ function may force ptxas to reserve a stack frame even with no spills. Pass by const& or break the function up. Symptom: non-zero "bytes stack frame" with zero spills.
