0.4Computer Architecture Primer

Latency, throughput, and the memory wall

[[A0.4.1]]

Latency vs throughput — the two costs of every operation

arch

Latency is "how long does one of these take?" — measured in cycles or nanoseconds. Throughput is "how many can finish per unit time?" — measured in operations/cycle or operations/second. A long-latency unit can still have high throughput if the hardware pipelines it. Example: a Tensor Core mma.sync on Ampere has latency ≈ 16 cycles, but an SM can issue a new one every 4 cycles per scheduler → throughput is 4× higher than latency suggests. CPUs hide latency with out-of-order execution and branch prediction; GPUs hide latency with thread-level parallelism. Same physics, opposite micro-architectures.

Used by [[A0.4.6]] [[§1.5 Occupancy]]
[[A0.4.2]]

Flynn's taxonomy — SISD, SIMD, MIMD, and where SIMT fits

arch

Michael Flynn (1966): classify processors by how many instructions and data items they handle per cycle. SISD = one of each (the classical von Neumann CPU). SIMD = single instruction, multiple data lanes (AVX-512, NEON). MIMD = multiple instructions, multiple data streams (multicore CPUs). NVIDIA coined SIMT — single instruction, multiple threads — to describe the GPU model: 32 threads (a warp) execute one PTX instruction together, but each thread has its own register state, program counter (post-Volta), and conditional-execution mask. SIMT looks like MIMD to the programmer and like SIMD to the hardware. This is the single most useful framing for everything in §1.3.

[[A0.4.3]]

Cache fundamentals — line size, associativity, and locality

arch

A cache trades capacity for speed by storing copies of recently used memory close to the compute unit. Three numbers describe one: capacity (how much), line size (how much it fetches per miss — almost always 32, 64, or 128 bytes — never one byte), and associativity (how many places a given address can live). A cache "hit" returns in 1–10s of cycles; a "miss" punts the request down to the next level and costs orders of magnitude more. Spatial locality says "addresses near a hit are likely to hit too"; temporal locality says "an address that just hit is likely to hit again soon." Coalesced loads (§1.4) are the GPU's way of forcing spatial locality at the warp level.

Used by [[§1.4 Memory hierarchy]] [[§2.3 Coalescing]]
[[A0.4.4]]

The memory wall — why bandwidth gets harder, not easier

arch

Compute has grown ~50%/year for decades; DRAM bandwidth has grown ~7%/year. The ratio of FLOPs to bytes a chip can supply rose roughly two orders of magnitude over the 2000s and 2010s. Every algorithmic technique in this book — tiling, shared memory, register reuse, cp.async, software pipelining, TMA — is some flavor of "do more arithmetic with the bytes I already paid to move." The memory wall is the meta-reason the rooflines tilt the way they do.

[[A0.4.5]]

Pipelining and ILP — overlapping work in time

arch

A modern functional unit is a pipeline: instruction i is in stage 4 while i+1 is in stage 3 and i+2 is in stage 2 — all in the same cycle. The throughput is one instruction per cycle even though the latency is 4 cycles. Instruction-Level Parallelism (ILP) extends this by issuing multiple independent instructions in the same cycle when no two depend on the same register. On GPUs ILP is one of two latency-hiding strategies (the other is TLP, thread-level parallelism). The compiler discovers ILP by reordering independent instructions in the SASS; you help it by writing inner loops that have multiple independent accumulators.

[[A0.4.6]]

Little's Law — the universal latency-hiding equation

arch

In steady state for any system: in-flight requests = throughput × latency. On a GPU memory subsystem with 936 GB/s bandwidth and ~500 ns DRAM latency, the number of bytes that must be "in flight" to keep DRAM saturated is ≈ 936·109 · 500·10−9 ≈ 468 KB. That number — not "more threads is better" — is the reason occupancy matters: you need enough threads, each making enough outstanding loads, to cover that 468 KB. Little's Law is the equation behind every "why is my kernel slow even though it has lots of threads?" diagnosis.

0.5The Laws of Parallel Speedup

Amdahl, Gustafson, work-span, and the synchronization tax

[[A0.5.1]]

Amdahl's Law — the serial fraction is your ceiling

parallelism

If a fraction s of a program is inherently serial and the rest is perfectly parallelizable across p processors, total speedup is bounded by 1 / (s + (1−s)/p). As p → ∞ the speedup approaches 1/s. A 5% serial section caps you at 20× speedup no matter how many cores you throw at it. On GPUs the "serial section" usually hides in: launch overhead, host↔device copies, kernel-to-kernel barriers, single-threaded prologue/epilogue code. The first thing to optimize on a slow GPU pipeline is almost never the kernel — it is the serial glue.

Contrast [[A0.5.2-gustafson]]
Used by [[Ch2 — streams/graphs]]
[[A0.5.2]]

Gustafson's Law — bigger problems are easier to parallelize

parallelism

Amdahl assumes the problem size is fixed. Gustafson observed that in practice we make the problem larger as we get more cores: the serial section's runtime is roughly constant while the parallel section's runtime scales with problem size. So scaled speedup = p − s·(p−1), which grows linearly with p. This is why GPUs feel so productive on training: doubling the batch size doubles the parallel work but keeps the serial bookkeeping flat.

Contrast [[A0.5.1]]
[[A0.5.3]]

Strong vs weak scaling

parallelism

Strong scaling = fixed total work, varying core count. Bounded by Amdahl. Weak scaling = work per core fixed, varying core count. Bounded mostly by communication. For GEMM at fixed shape (the question this book asks) we care about strong scaling. For training across many GPUs we care about weak scaling, which is why multi-GPU is its own chapter.

[[A0.5.4]]

Work, span, and parallelism

parallelism

Two complexity measures of a parallel algorithm, ignoring the hardware: work T1 is total operations across all processors; span T∞ is the longest dependency chain — the critical path. Their ratio T1/T∞ is the parallelism, an upper bound on the speedup any scheduler can ever achieve. A parallel reduction over n elements has work O(n) and span O(log n) → parallelism n / log n. GEMM has work O(n³) and span O(log n) → parallelism O(n³ / log n), which is essentially unbounded for any n a real GPU runs.

[[A0.5.5]]

Race condition vs data race vs benign race

concurrency

A data race is two unsynchronized accesses to the same memory location where at least one is a write. C++ and CUDA both say it is undefined behavior. A race condition is a broader notion: the program's result depends on a timing nondeterminism, even when no memory access is racy in the C++-language sense (e.g., who completes an atomic first decides which value sticks). A benign race is one the programmer has analyzed and decided is safe — for example, all threads writing the same value to the same address. Compilers and tools (compute-sanitizer's racecheck) don't know which of your races are benign; they flag them all. Treat every flagged race as real until you've written down why it isn't.
