Foundations:
The Atoms Beneath the GPU

Learning goal. Build the conceptual atoms the rest of the book stands on: how numbers are stored in hardware, what a matrix multiply is as an operation count and a memory-traffic problem, the laws of parallel speedup, the architectural lineage that produced the modern GPU, and the vocabulary (latency, throughput, intensity, occupancy) you will use on every page that follows. Each idea is an atomic note with explicit links to what it depends on and what it leads into.

How to read this chapter

If you've taken an undergraduate "computer organization" plus a numerical-methods course, skim §0.2 and §0.4, then read §0.5 (parallelism laws) and §0.6 (GPU lineage) carefully. If you came from pure software, read every atomic note in order. Each note is short on purpose — return to them as reference cards while reading later chapters.

Concept dependency graph for the entire book

The textbook is laid out as a directed graph of atomic notes. Each note explains exactly one idea — what it is, why it exists, the smallest example that makes it true, and a short list of the other notes that lead into and out of it. The links carry semantics:

The four link types you will see everywhere

meta
  • prereq "You cannot meaningfully understand this note without first understanding the linked one." The linked note answers a sub-question the current note assumes.
  • builds-on "This note uses the linked one as a black box." Not strictly a prerequisite — you can read this note with only a one-sentence summary of what it builds on — but the formal definitions live in the linked note.
  • used-by "These later notes apply or extend this one." Forward edges in the graph; how to navigate downstream.
  • related "Sibling concept worth comparing." No direct dependency — usually a contrast or an alternative formulation.
  • contrast "Easy to confuse with this one." When the two concepts share vocabulary but have different mechanics (e.g. occupancy vs utilization, latency vs latency-hiding).

The visual concept map at the end of the book (Ch 9 — Knowledge Graph) renders these edges as a force-directed diagram. Until then, the chips at the bottom of each card are the graph.

The canonical question the book answers

framing

"Given a matrix multiply of a chosen shape, write a CUDA kernel that runs faster than NVIDIA's cuBLAS on the same GPU, and prove it." Every chapter is a layer of context that question demands:

  • What is a matrix multiply, exactly? → §0.3 (linear algebra) and [[A0.3.4]].
  • What is the machine running it? → Ch 1 — GPU architecture.
  • How do I tell the machine to do it? → Ch 2 — CUDA programming.
  • What does dedicated MM hardware do? → Ch 3 — Tensor cores & PTX.
  • How do I see what my kernel is actually doing? → Ch 4 — Nsight Compute.
  • Where does cuBLAS lose, and how do I prove I beat it? → Ch 5 — Beating cuBLAS.
  • Building blocks you'll need anyway → Ch 7 — reductions/scans, Ch 8 — multi-GPU.
