7.7Persistent Kernels, Split-K, and Stream-K

[[A7.7.1]]

Persistent kernel — launch once, work forever

scheduling

A persistent kernel launches enough blocks to fill the GPU exactly (numSMs × max blocks/SM) and each block loops over work items pulled from a work queue. The pattern eliminates per-iteration launch overhead and lets blocks dynamically rebalance load. The cost: you give up the GPU's scheduler — you have to write your own work-stealing loop and worry about fairness. Use for: latency-critical inference, fine-grained per-iteration solvers, anywhere the launch overhead is a measurable fraction of runtime.

Related [[A1.3.4]]
[[A7.7.2]]

Split-K — extra parallelism for skinny GEMMs

scheduling

Standard GEMM parallelism is over the (M, N) output tile grid. When M and N are small but K is huge (the canonical "wide GEMM" of a fully-connected layer's tall input), few output tiles exist and the GPU sits idle. Split-K cuts the K dimension into s chunks, launches s times more blocks, and reduces the partial outputs into the final tile via either a second-kernel reduction or atomic accumulation. The work doubles slightly (the reduction); occupancy quadruples. cuBLAS picks split-K automatically when the shape calls for it; in custom kernels you have to plan for it.

Prereq [[A0.3.4]]
Used by [[§5.2 cuBLAS]]
[[A7.7.3]]

Stream-K — work-stealing scheduling for GEMM

scheduling

Stream-K (Osama et al., 2023; landed in CUTLASS 2.10) merges split-K and persistent: each SM processes a continuous range of the K dimension across multiple output tiles, dynamically picking up the next chunk. The scheduler avoids the "last wave" inefficiency where a few stragglers finish long after the rest of the GPU is idle. On highly variable-shape workloads it can be 1.5–2× faster than the best static split-K. The implementation is non-trivial; for a portfolio GEMM kernel, CUTLASS's stream-K is the reference to study.

Chapter 08

Multi-GPU and
Distributed CUDA

Learning goal. Understand the physical topology that connects two or more GPUs, what NCCL actually does behind one ncclAllReduce call, and how training-scale parallelism (data, tensor, pipeline, sequence) maps to those wires. The atomic notes below give you the vocabulary and the trade-offs without committing to one framework.

8.1Physical Topology — PCIe, NVLink, NVSwitch

[[A8.1.1]]

Bandwidth tiers — PCIe Gen4 vs NVLink vs NVSwitch

interconnect
  • PCIe Gen4 x16 ≈ 32 GB/s per direction. The fallback path between any GPU and the CPU.
  • PCIe Gen5 x16 ≈ 64 GB/s per direction (H100 and later).
  • NVLink 3.0 12 lanes per A100 → 600 GB/s aggregated per GPU.
  • NVLink 4.0 18 lanes per H100 → 900 GB/s aggregated.
  • NVSwitch An on-PCB switch that lets every GPU talk to every other at full NVLink rate. The difference between "DGX" (NVSwitched) and "HGX" (point-to-point) topologies.

One sentence to remember: NVLink is ~20× faster than PCIe. The first sanity check when scaling across GPUs is which path your transfers actually take — nvidia-smi topo -m prints the topology matrix.

Used by [[A8.2.1]]
[[A8.1.2]]

Peer-to-peer (P2P) — letting one GPU read another's HBM directly

interconnect

With cudaDeviceEnablePeerAccess, GPU A can issue load/store instructions to addresses mapped to GPU B's memory. The traffic goes over NVLink if available, PCIe otherwise. P2P is the foundation under NCCL: it lets a single GPU's kernel pull data straight from a neighbor without bouncing through host memory. NVSwitch makes P2P uniform; on multi-socket PCIe-only systems some P2P paths cross NUMA nodes and are slower.

Builds on [[A8.1.1]]

8.2Collective Operations — What NCCL Does

[[A8.2.1]]

All-reduce — the operation that consumes most distributed-training time

collective

All-reduce takes one tensor per GPU and combines them with a reduction op (typically sum), leaving every GPU with the same result. Three classical algorithms in NCCL:

  • Ring Each of N GPUs holds 1/N of the tensor; N−1 reduce-scatter steps, then N−1 all-gather steps. Bandwidth-optimal: every GPU sends and receives at full link rate.
  • Tree A binary tree of reductions on the way up, then a broadcast on the way down. Lower latency (log N steps) but uses bandwidth less efficiently than ring.
  • 2D / 3D rings On NVSwitched systems, NCCL builds rings along multiple dimensions to exploit the fully-connected topology.

NCCL chooses between them automatically based on message size and topology. The relevant performance number is busBw, NCCL's effective per-GPU bandwidth across the collective; for an all-reduce, busBw ≈ algoBw × (N−1)/N.

Prereq [[A8.1.1]]
Used by [[A8.3.1]]
[[A8.2.2]]

All-gather, reduce-scatter, broadcast, all-to-all

collective

NCCL ships these and more. All-gather concatenates one shard per GPU into a full copy on every GPU. Reduce-scatter reduces along GPUs and leaves each with a shard. (All-reduce = reduce-scatter then all-gather.) Broadcast copies from one GPU to all. All-to-all sends a different shard from every GPU to every other; the workhorse of expert-parallel MoE. The collective you reach for tells you the parallelism strategy you implicitly chose.

Builds on [[A8.2.1]]

8.3Parallelism Strategies

[[A8.3.1]]

Data parallelism — replicate the model, split the batch

parallelism

Every GPU holds the full model, processes its own micro-batch, and after backward they all-reduce gradients. Simple, scales to "the model fits on one GPU." Overhead = one all-reduce per step. With ZeRO sharding, the model state itself is partitioned and an all-gather is inserted before each forward pass — trades extra communication for memory savings.

Prereq [[A8.2.1]]
[[A8.3.2]]

Tensor parallelism — split a matrix multiply across GPUs

parallelism

A linear layer Y = X·W can be split by column: each GPU holds W's slice and computes its slice of Y; an all-gather assembles the full Y. Or by row: each GPU holds the right W slice and computes a partial product; an all-reduce finishes it. Megatron's transformer layout uses column-then-row to merge two communications into one all-reduce per attention block and one per MLP. The collective cost is per layer; communication therefore scales with depth.

Prereq [[A0.3.4]] [[A8.2.2]]
[[A8.3.3]]

Pipeline parallelism — slice the model depthwise

parallelism

Stage 1 of the model lives on GPU 0, stage 2 on GPU 1, etc. Micro-batches stream through. Communication is point-to-point (only adjacent stages talk), bandwidth-light, latency-sensitive. The pipeline has a bubble: at the start and end of each batch the GPUs at the far ends idle. GPipe, 1F1B, and interleaved 1F1B (Megatron) are schedules that shrink the bubble. The right size of pipeline parallelism is "as many stages as you need to fit one micro-batch in GPU memory, no more."

Related [[A8.3.2]]
[[A8.3.4]]

Sequence parallelism — split the sequence axis

parallelism

For very long contexts, the activation tensors get too big for one GPU's HBM even at modest batch sizes. Sequence parallelism splits the sequence dimension across GPUs and synchronizes only at operations that mix tokens (attention's softmax row). Ring-attention is the formulation that does this with overlapping communication. Used in 100K-token+ training of modern LLMs.
