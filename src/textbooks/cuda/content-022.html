4.7Profiler Theory — Sampling, Replay, and PM Counters

What the numbers in Nsight Compute actually are
Why this section exists. The default Nsight Compute output looks like a stream of dashboard numbers. Each one is the output of a specific measurement strategy with specific costs and biases. The atomic notes below let you read the dashboard with the right amount of skepticism — and choose the right tool (NCU vs Nsight Systems vs nvbprof vs CUPTI) for each question.
[[A4.7.1]]

Sampling vs instrumentation — two ways to measure code

profiling

Sampling profilers interrupt the program at fixed intervals and record the PC. They are cheap (≤ 1% overhead), statistical, and miss anything rarer than the sample interval. Instrumentation profilers insert measurement code at events of interest (entry/exit of every function, every memory access). Exact, but slow — orders of magnitude. Nsight Systems is a sampler; it answers "what is the GPU doing over time?" Nsight Compute is hardware-instrumented via PM counters; it answers "what exactly happened inside one kernel launch?" Use them in that order: Sys to find which kernel matters, Compute to dissect that kernel.

Used by [[A4.7.2]]
[[A4.7.2]]

PM counters — the silicon's measurement hardware

profiling

Each SM has a fixed set of Performance Monitoring counters: free-running integers wired to events (cycles where the warp scheduler issued an instruction, sectors hitting L1, etc). There are far more interesting events than counters, so Nsight Compute replays the kernel many times, configuring different counter sets each pass and stitching the results into one report. The kernel-replay strategy explains two NCU quirks: (1) profiling makes a kernel run 20–100× longer wall-clock; (2) the kernel must be deterministic across replays or the report is garbage (set deterministic CUDA random seeds, lock graphics clocks, run on an idle GPU).

[[A4.7.3]]

The SM subsystems NCU names — L1TEX, LTS, FBPA, MIO, IDC

profiling
  • L1TEX The L1 cache + texture pipeline. Where shared memory accesses, vector loads, and read-only caches show up.
  • LTS L2 Texture/Scalar — the L2 slice. lts__t_sectors_op_read = L2 sector reads.
  • FBPA Frame Buffer Partition — the HBM controller. dram__bytes events live here.
  • MIO Memory I/O scheduler within the SM. Issue stalls show up as MIO throttle metrics.
  • IDC Indexed Constant cache. Almost always saturated by constant-memory loads; rarely a bottleneck.

Knowing which sub-system a metric belongs to is the difference between "L2 hit rate is 80%" being good or bad. If your kernel's bandwidth bottleneck is at FBPA, an LTS hit rate of 100% would not save you. Read top-down: SM → L1TEX → LTS → FBPA — the answer is at whichever level is closest to saturated.

[[A4.7.4]]

Warp state taxonomy — selected, eligible, stalled, the three big stall reasons

profiling

Every cycle, the warp scheduler classifies each resident warp into one of three states: selected (this warp issued an instruction), eligible (ready but not picked), stalled (waiting). The stall reasons NCU exposes most usefully:

  • long_scoreboard Waiting on a global or shared memory load. The single most common stall in a memory-bound kernel.
  • short_scoreboard Waiting on a math result (e.g., a register-dependent instruction). High share = ILP-bound.
  • mio_throttle Memory I/O pipeline is backed up. Usually means too many memory ops issued per cycle.
  • barrier Waiting on __syncthreads. High share = imbalanced work across the block.
  • not_selected Warp is ready but the scheduler picked someone else. Counterintuitively, some not_selected is good; it means TLP is doing its job.

[[A4.7.5]]

CUPTI and NVTX — your own custom tooling layer

profiling

CUPTI (CUDA Profiling Tools Interface) is the library Nsight is built on. Your code can use it to subscribe to events ("kernel started", "memcpy began"), read counters at runtime, and inject custom metrics. Few application engineers touch CUPTI directly; library authors (PyTorch's profiler, TensorRT's diagnostics) do. NVTX (NVIDIA Tools Extension) is the lighter-weight API: nvtxRangePushA("forward") ... nvtxRangePop() turns your code's logical structure into colored ranges in Nsight Systems' timeline. Always wrap your training/inference loop's logical phases in NVTX ranges; it makes Nsight Systems' output legible.

[[A4.7.6]]

Clock locking — why every benchmark needs it

profiling

Modern GPUs change their clock based on temperature, power, and workload. If you benchmark a kernel cold, then again warm, the second run will sit at a higher boost clock and look faster — even if your "optimization" is just running it twice. nvidia-smi -lgc <min,max> locks the graphics clock; nvidia-smi -lmc locks the memory clock. For consumer cards, the application clocks may be capped by power limits — check nvidia-smi -q -d CLOCK after locking to verify what you actually got. Without clock locking your before/after numbers are not comparable.

Chapter 05

Beating cuBLAS:
The Strategy and the Execution

Learning goal. Understand exactly why cuBLAS does not win every shape, identify a shape where a custom kernel can beat it, execute the full optimization stack, and validate the result with a benchmark protocol a stranger could reproduce.

5.1How cuBLAS Actually Works

A library of pre-compiled kernels and a dispatch heuristic

cuBLAS is a closed-source CUDA library that ships pre-compiled GEMM kernels for many common shapes, dtypes, and transposition modes. When you call cublasGemmEx for a specific configuration, an internal heuristic picks a kernel from the library based on (M, N, K, dtype, transpose flags, alpha/beta, hardware). The picked kernel is then launched.

Three properties of this design matter for your strategy:

  1. cuBLAS kernels are extraordinarily good for "large square" shapes in common dtypes (FP32, TF32, FP16) — they routinely hit 90–95% of the corresponding Tensor-Core peak. Beating them on these shapes is hard.
  2. The dispatch heuristic is fallible. For atypical (M, N, K) — small batch sizes, non-power-of-two dims, very tall/skinny matrices — the heuristic sometimes picks a tiled kernel whose tile shape mismatches your problem and leaves a lot on the table.
  3. cuBLAS only does GEMM. It does not fuse subsequent elementwise operations (bias add, activation, scaling). For any kernel that follows GEMM with arithmetic, a fused custom kernel saves one full pass over the output matrix in global memory.

You can see which internal kernel cuBLAS picked by enabling its logging (see §4.6). The kernel name encodes its tile shape and architecture. Knowing this is genuinely useful: if cuBLAS picked a 128×128 tile for a problem where 64×256 would obviously fit better, you have your opening.

5.2Where cuBLAS Is Vulnerable

The four families of shapes that admit a custom win

1. Small batch / decode shapes (M = 1, GEMV-like)

During LLM inference's decode phase, you compute one token at a time. The GEMM degenerates to a vector-matrix product with M = 1 and N, K in the thousands. The arithmetic intensity is near 1 FLOP/byte — fundamentally memory-bound. cuBLAS exposes cublasGemv for this shape but the wrapper has fixed overheads, and the dispatched kernel is not specialized to your specific N/K. A custom kernel that hand-tunes the load pattern (vectorized 128-bit reads of B, K-direction reduction in registers) can outpace it by 10–30%, especially for batch=1 inference.

2. Non-power-of-two shapes

cuBLAS tiles are typically 64, 128, or 256 elements wide. For M = N = K = 3072 (= 1024×3, not a power of two), the dispatcher may pick a 128-tile kernel and pay the cost of partial last-tile padding on three sides. A custom kernel tiled at, say, 96×96 — divides evenly — avoids the padding entirely and can win by a few percent.

3. Fused operations

Almost every neural-network linear layer is followed by add-bias-and-activate. cuBLAS computes C = α·A·B + β·C; it does not apply ReLU or GELU. The follow-on elementwise pass reads C from DRAM and writes it back — at 4096² FP16, ~33 MB in and out, costing roughly 0.07 ms at 936 GB/s. A fused kernel does the activation while C is still in registers and saves the entire DRAM round-trip. This is the single most consistent way to beat cuBLAS in real ML workloads.
