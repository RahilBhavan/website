4.3Reading the Summary View

What each section means and what it tells you to do

Opening a .ncu-rep in the UI, the kernel's Summary page is your first stop. It is organized into named sections; here is what each one means and how to read it.

GPU Speed Of Light (SOL)

The single most important section. Two numbers:

  • Compute (SM) Throughput — metric sm__throughput.avg.pct_of_peak_sustained_active. The fraction of peak SM throughput your kernel achieved.
  • Memory Throughput — the equivalent for the memory subsystem; on most reports this rolls up DRAM, L2, and L1.

The diagnostic table is short:

SM %Memory %DiagnosisWhat to try next
> 80%anyCompute-bound. You are near peak.Switch to a lower-precision Tensor Core. Reduce instruction count. Better mma fragments. Approach the roof.
< 60%> 80%Memory-bound. Bandwidth is your bottleneck.Tile bigger. Increase reuse (more output per input byte). Coalesce. Vectorize loads. Consider cp.async pipelining.
< 60%< 60%Latency-bound. Neither pipe is busy; warps are stalled.Check warp-state statistics — what are they waiting on? Increase occupancy. Increase ILP. Reduce per-thread sync.
> 60% both> 60% bothBalanced; both pipes have headroom. Likely launch-overhead or occupancy issue.Increase work per kernel. Use streams. Increase block count.

Compute Workload Analysis

Per-pipe utilization: ALU (FP32/INT32 CUDA cores), FMA, TENSOR, FP64, FP16, XU (transcendentals), LSU (load/store), ADU (address). If you wrote a Tensor-Core kernel and TENSOR throughput is low, you are not actually hitting the Tensor Cores — usually because mma.sync issue is starved by SMEM bandwidth or the wrong fragment layout.

Memory Workload Analysis

Per memory level: traffic in/out, request counts, sector counts, hit rates. The most diagnostic numbers:

  • L1/TEX Hit Rate. Low = your global-memory access pattern is wasting cache. Often a coalescing issue.
  • L2 Hit Rate. Low = the working set is not living in L2. Often a tiling issue.
  • Sectors / Request. 1.0 is perfect. 4.0 means every load is fetching 4× the cache lines it needed. Coalescing failure.
  • Shared Memory Wavefronts. The bank-conflict counter. A 32-way conflict shows up as 32× more wavefronts than requests for that load.

Warp State Statistics

Where your warps spend cycles when they are not issuing. Each "stall reason" is its own metric and each tells a different story:[2]

Stall reasonWhat it meansFix
long_scoreboardWaiting on an L1TEX (global/local/surface/tex) operation. Effectively: global memory latency.Hide it with more outstanding warps (occupancy) or more outstanding loads per warp (ILP). Or just reduce loads (tile).
short_scoreboardWaiting on an MIO operation — shared memory, special math units, or dynamic branching.Usually shared-memory access dominates. Check bank conflicts; reduce SMEM traffic via register reuse.
mio_throttleThe MIO pipe queue is saturated. Too many shared/special instructions piling up.Reduce shared-memory pressure. Replace SMEM ops with register-resident accumulators.
barrierWaiting at __syncthreads for slower threads in the block.Balance work across threads; check for divergent paths converging at the barrier.
waitGeneric dependency wait (e.g. mma.sync result not yet available).More ILP between dependent instructions; double-buffer the operands.
not_selectedWarp was eligible but scheduler chose another. This is good — means you have issue slack.Nothing. High values here are a healthy signal.
imc_missConstant-memory cache miss.Move data out of __constant__ or restructure access pattern.
tex_throttleTexture pipe saturated.Rarely relevant for GEMM. Indicates over-use of texture loads.

4.4The Roofline in Nsight Compute

Same plot as §1.6, now with your real kernel

Recent ncu versions include a built-in roofline plot in the GPU Speed Of Light Roofline Chart section (it is generated whenever the relevant metrics are collected, which they are with --set full and most analysis sets). The plot has the same shape as §1.6: arithmetic intensity on the x axis, GFLOPS on the y axis, the compute roof horizontal, the memory roof diagonal, your kernel as a single dot.

The diagnostic is simple. If the dot is on the diagonal, you are memory-bound. If it is below the horizontal roof on the right, you are compute-bound but not at peak — instruction mix or fragment layout. If it is in free space below both roofs, you are latency-bound — too few outstanding warps. Hopper-era reports also show hierarchical rooflines (DRAM, L2, L1, SMEM) so you can see which memory level you are bounded by.

# If your default set does not include roofline, the explicit metrics are:
ncu --metrics \
  sm__sass_thread_inst_executed_op_fadd_pred_on.sum,\
sm__sass_thread_inst_executed_op_fmul_pred_on.sum,\
sm__sass_thread_inst_executed_op_ffma_pred_on.sum,\
dram__bytes.sum.per_second,\
gpc__cycles_elapsed.avg.per_second \
  --launch-count 1 \
  -o roofline_report ./my_program

4.5Memory Workload Analysis Deep Dive

Diagnosing the memory subsystem in detail

The Memory Workload Analysis page shows traffic at every level: instructions issued, requests sent to each cache, sectors hit and missed, wavefronts on shared memory, and bytes ultimately reaching DRAM.

Reading the request → wavefront → sector cascade

When a warp issues a memory instruction, the L1TEX unit produces requests. Each request is split into sectors (32 bytes each on Ampere) and serviced as wavefronts through the cache. In the ideal case — perfectly coalesced 32-thread reads of contiguous floats — one request becomes one wavefront becomes four 32-byte sectors all in one cache line.

Two ratios reveal trouble:

  • Sectors / Request > 1: cache lines being only partially used (uncoalesced or strided access). A ratio of 4× means you are doing four trips for the data of one.
  • Wavefronts / Request > 1 in shared memory: bank conflicts. A 32-way conflict shows up as 32 wavefronts per request. The fix is padding or restructured indexing.

Hit rates by level

  • L1 Hit Rate. High = your global reads are being served by L1 thanks to spatial locality. Low + uncoalesced sectors = coalescing problem. Low + already coalesced = the working set is bigger than L1.
  • L2 Hit Rate. The cross-SM cache. High = different blocks are sharing data. Low + large working set = you are saturating DRAM. Low + small working set = you are evicting your own data; try a smaller tile or persistent kernels.
  • Texture cache hit rate (if you use texture loads or __ldg): same idea, separate unit.

4.6Source-Level Profiling

Per-line PTX and SASS with cycle counts

The Source view in Nsight Compute is the closest thing GPU programming has to perf annotate. With -lineinfo at compile time, every SASS instruction can be traced back to a source line, and counters tell you how many cycles were spent at each line.

The view has three correlated columns — source, PTX, SASS — that scroll in lock-step. Click a source line to highlight the SASS instructions it generated and see their per-instruction execution counts and stall reasons.

Reading SASS

SASS (Streaming Assembler) is the actual machine code for a specific compute capability. Reading it tells you whether the compiler made good decisions. The mnemonics that matter for GEMM:[3]

MnemonicWhat it doesWhy you care
FFMAFloat-32 fused multiply-add. The CUDA-core workhorse.Many FFMAs per LDG = compute-bound work.
HFMA2Packed half-precision FMA.Indicates the compiler vectorized your FP16 path.
HMMAHalf-precision MMA — the Tensor-Core instruction at the SASS level.Appears if and only if your kernel actually uses Tensor Cores. No HMMAs = no tensor-core work.
BMMA / IMMA / QMMABit / integer / FP8 variants of MMA.For quantized kernels.
LDGLoad from global memory.Many LDGs per FFMA = memory-bound.
LDSLoad from shared memory.SMEM throughput cost; look for high LDS counts paired with short_scoreboard stalls.
STG / STSStore global / shared.Output traffic. STG outside the inner loop is good; inside is suspect.
BAR__syncthreads barrier.Count of BARs tells you how synchronization-heavy the kernel is.
BRA / SSYBranch / set sync point (for handling divergence).Many of these in the inner loop = divergent code paths.

The key ratio to internalize: FFMA (or HMMA) count vs LDG count. In a well-tiled GEMM, this ratio should be in the tens or hundreds — many compute instructions per global load. In a naive kernel the ratio is close to 1:1, and you can see it directly in the SASS listing.

# Compile with line correlation
nvcc -O3 -arch=sm_86 -lineinfo -o gemm gemm.cu

# Dump SASS to a file you can read
cuobjdump --dump-sass gemm > gemm.sass

# Or just look at one kernel:
cuobjdump --dump-sass --function gemmTiled gemm

# Or look at the intermediate PTX:
nvcc -O3 -arch=sm_86 -ptx -o gemm.ptx gemm.cu

# In ncu, open the .ncu-rep, navigate to the Source view, and you will
# see per-line counts of: FFMA, LDG/STG, LDS/STS, HMMA, BAR, BRA, ...
The fastest debugging loop
For tight optimization work: write the kernel, run a single-pass profile (ncu --launch-count 1 -o r.ncu-rep ./prog), open in UI, jump to the Source view, find the hot line, ask "is the SASS what I expected?" If yes, look at the warp-state metric for that line. If no, change the C++ to coax the compiler. Repeat.

cuBLAS API logging — what the dispatcher chose

cuBLAS picks an internal kernel based on (M, N, K, dtype, transposition). To see which it picked — sometimes you can learn the right tile size from this — enable cuBLAS API logging via environment variables:

export CUBLAS_LOGINFO_DBG=1
export CUBLAS_LOGDEST_DBG=stdout    # or a filename
# Optional, newer versions: verbosity 1..5
export CUBLAS_LOGLEVEL_DBG=5

./my_cublas_program
# stdout will now show the cuBLAS internal kernel name, tile size,
# and dispatch heuristic for every cuBLAS call.

Note: the precise env-var names are CUBLAS_LOGINFO_DBG and CUBLAS_LOGDEST_DBG. Some older blog posts say CUBLASAPI; that is not the actual variable. Use NVIDIA's cuBLAS documentation page on logging as the authoritative reference.[4]
