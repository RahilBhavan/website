10.3SASS — The Real Machine Code

PTX is a virtual ISA. SASS is what the SM actually executes.

Cluster. PTX is portable — one binary covers many GPUs, and the driver JIT-compiles to SASS at load time. But the same PTX can yield different SASS on different architectures. When you need to understand "why is my kernel slow on this card and fast on that one," SASS is the answer.
[A10.3.1]

SASS Instruction Anatomy

SASS · decoding

A SASS instruction has four parts:

  1. Predicate guard (e.g. @P0) — runs only if the predicate register is true. Replaces small if/else with branchless predication.
  2. Mnemonic + modifiers (e.g. FFMA.FTZ, LDG.E.128) — operation plus encoding hints (flush-to-zero, vector width, cache policy).
  3. Operands — registers (R12), uniform registers (UR0 on Volta+), memory operands ([R0+0x40]), immediates.
  4. Scoreboard / yield bits (sm_70+) — control how the warp scheduler tracks dependencies; visible only in the raw control-code section.
# Show the cubin sections embedded in your executable
cuobjdump ./my_program

# Extract SASS for a specific arch (everything readable on stdout)
cuobjdump --dump-sass ./my_program

# Or compile -> cubin -> disasm in one shot
nvcc -arch=sm_80 -cubin kernel.cu -o kernel.cubin
nvdisasm --print-line-info kernel.cubin  # correlates SASS lines with .cu source lines

# Decode SASS control codes (sm_70+) — yield/reuse/stall bits
nvdisasm --print-instruction-encoding kernel.cubin

# Show PTX, then SASS, then both with source interleaved
cuobjdump --dump-ptx ./my_program
cuobjdump --dump-sass --gpu-architecture=sm_80 ./my_program

10.4NVRTC — JIT Compiling at Runtime

When the kernel doesn't exist until your data does

[A10.4.1]

Why JIT a CUDA Kernel

NVRTC · jit

NVRTC is a libcuda subsystem that compiles a CUDA C++ source string to PTX at runtime, which the driver then loads. Use cases:

  • Shape specialization — bake matrix dimensions into the kernel as compile-time constants for full unrolling. Most Triton-backed engines (vLLM, TensorRT-LLM) do this.
  • Fusion engines — assemble an epilogue (bias add + activation) at run-time based on user input.
  • Plugin systems — let end users supply custom ops without recompiling the entire library.

The compile cost is usually tens of milliseconds, so cache the produced PTX/cubin keyed by the source hash and arch.

RelatedCh 16 Triton/CUTLASS
#include <nvrtc.h>
#include <cuda.h>
#include <iostream>

const char* src = R"(
extern "C" __global__ void axpy(float a, float* x, float* y, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = a * x[i] + y[i];
})";

int main() {
    nvrtcProgram prog;
    nvrtcCreateProgram(&prog, src, "axpy.cu", 0, nullptr, nullptr);
    const char* opts[] = { "--gpu-architecture=compute_80", "--use_fast_math" };
    nvrtcCompileProgram(prog, 2, opts);

    size_t ptxSize; nvrtcGetPTXSize(prog, &ptxSize);
    std::string ptx(ptxSize, '\0'); nvrtcGetPTX(prog, ptx.data());
    nvrtcDestroyProgram(&prog);

    CUmodule mod; cuModuleLoadData(&mod, ptx.data());
    CUfunction fn; cuModuleGetFunction(&fn, mod, "axpy");
    // launch as usual with cuLaunchKernel...
}
Caveat

NVRTC has no access to your host headers. You must include any CUDA headers the kernel references as additional strings, or rely on what NVRTC bundles. Common gotcha: <cuda_fp16.h> works; <cooperative_groups.h> needs extra plumbing.

10.5The CUDA ABI & Separate Compilation

How __device__ functions cross translation-unit boundaries

[A10.5.1]

Relocatable Device Code (-rdc=true)

linking

By default nvcc compiles each .cu in whole-program mode: every device function must be visible (and inlinable) at the same translation unit as the kernel that calls it. With -rdc=true the device code is emitted as a relocatable cubin and a separate nvlink stage resolves cross-TU symbols, exactly like the host linker. Required for:

  • Calling a __device__ function defined in a different .cu.
  • Using dynamic parallelism (a kernel that launches another kernel) — that needs -rdc=true -lcudadevrt.
  • Linking against CUTLASS templates split across multiple files.

Costs: ~20% larger binaries, missed inlining (~5–10% perf on hot inner loops), and slower link times. Profile before assuming you need it.

[A10.5.2]

Name Mangling and cu++filt

debugging

CUDA mangles device symbols using the Itanium C++ ABI plus a _Z…-style scheme for templates. Read them with cu++filt:

$ cuobjdump --dump-elf-symbols ./prog | grep gemm
_Z11gemm_kernelILi128ELi128ELi32EEvPKfS1_Pfiii

$ cu++filt _Z11gemm_kernelILi128ELi128ELi32EEvPKfS1_Pfiii
void gemm_kernel<128, 128, 32>(float const*, float const*, float*, int, int, int)

Use this whenever Nsight Compute shows mangled names. Profile reports become readable.
