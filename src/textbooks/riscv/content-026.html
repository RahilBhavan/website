One bubble preserves the instruction order

The table counts clock intervals. Stage values are visible during each interval and move at its ending edge. “Held” means the instruction stays in its current front-end position.

At the end of cycle 3, the hazard freezes the front end. The load reaches MEM in cycle 4 while EX holds a bubble. In cycle 5, WB forwards the loaded value to ADD in EX.

In cycle 6, the ADD result in MEM forwards into the store's EX operand selection. The store changes memory at the end of cycle 7 and emits its retirement record after WB in cycle 8.

A memory side effect and the later retirement notification occur at different pipeline points. The checker verifies the ordered byte-write stream as well as retirement records.

A taken branch discards two younger stages

beq x1, x1, target
sw  x2, 128(x0)      # wrong path
addi x3, x0, 99      # wrong path
target: addi x4, x0, 42

The branch decides in EX. At that point, younger instructions occupy ID and IF. A taken branch invalidates both. Fetch resumes at the target on the following cycle.

With no other stalls, this design pays two lost issue opportunities for an EX redirect. An untaken branch continues sequential fetching. Other pipelines can resolve branches later and incur a different penalty.

JAL writes a return address and redirects using a PC-relative immediate. JALR adds a signed immediate to a register base and clears target bit zero. This core traps if the resulting taken target is not word aligned.

Forwarded operands must feed branch comparisons and JALR bases. Otherwise a correct arithmetic pipeline can still choose the wrong instruction path.

08 / CONTROL FLOWBUILD NOTES

A trap halts this execution environment

A trap reports an exceptional event. Here, ECALL, EBREAK, unsupported instructions and misaligned accesses or taken targets emit a local trap record and halt fetch.

The faulting instruction performs no register or memory side effect. Younger instructions are discarded. Older instructions continue through the remaining stages. Reset starts execution again.

This default build is a small teaching environment. It has no trap vector, privilege state, cause register, interrupt mechanism or recovery handler. The ZICSR=1 build of the same core adds machine-mode trap entry, cause registers and interrupts. Neither build has a memory access-fault response.

FENCE orders memory operations architecturally. The supported base FENCE acts as a no-op under the stated single-hart, ordered, fixed-latency memory contract. FENCE.I is absent, and CSRs exist only in the ZICSR=1 build.

A Harvard interface uses separate instruction and data ports. This core additionally assumes combinational reads. FPGA block RAM usually has synchronous reads, so connecting typical block RAM directly changes the timing contract.

An instruction implementation is always interpreted within an execution environment. Documenting that environment prevents a small core from appearing more complete than it is.

09 / CUSTOM COMPUTEBUILD NOTES

DOT4 multiplies four signed byte pairs

The custom instruction treats each source register as four independent signed 8-bit lanes. Lane zero is the least significant byte. It multiplies corresponding lanes and sums all four products into a 32-bit result.

DOT4 rd, rs1, rs2
rd = sum(signed8(rs1.byte[i]) * signed8(rs2.byte[i]))
     for i = 0, 1, 2, 3

There is no accumulator input, rounding or saturation. The sum ranges from −65024 to 65536. A signed 16-bit result is too narrow. A signed 18-bit value can represent the full range, and the destination remains 32 bits.

The encoding uses custom-0: opcode 0x0B, funct3=0 and funct7=0. Other function combinations trap. GNU assembly can emit .insn r 0x0b, 0, 0, a0, a1, a2.

This project-specific instruction illustrates a small hardware/software tradeoff. It is not a ratified vector extension or evidence of a lab's accelerator architecture.

The RTL has four useful reading passes

Pass 1: stored state

Find regs, pc and each stage's valid bit. Follow PC, instruction, destination and write-enable through the pipeline registers.

Pass 2: operand selection and execution

Read the first combinational block for forwarding. Read the opcode case for execution. Notice default control values, legality checks, address generation and the signed DOT4 expression.

Pass 3: hazard and memory boundaries

Find uses_rs1, uses_rs2, hazard, redirect and fault. Then follow byte strobes, aligned addresses and load extension.

Pass 4: the rising edge

Read reset first. Then follow WB, MEM/WB and EX/MEM updates. Finally inspect the redirect/fault, hazard and ordinary-advance cases. Older stages advance even when the front end stalls.

11 / VERIFICATIONBUILD NOTES

A reference model predicts architectural results

A sequential model executes one instruction at a time without implementing the pipeline. For each instruction, it calculates the next PC, destination register, result and trap behavior.

The regression runs the same machine words through that model and the RTL. It compares each retired PC, instruction, destination, value and trap flag. It separately compares every ordered byte write.

This catches errors that a final signature can hide. A wrong-path store might briefly corrupt memory and later be overwritten. A final register check alone can miss it.

The model uses Python integers and explicit 32-bit masking. Signed conversion is deliberate. Python's unlimited integer width does not automatically behave like a 32-bit register.

Both model and RTL belong to this project, so they could share a misreading of the ISA. The core also matches Spike on 39 of 39 riscv-arch-test RV32I tests. ACT4 and formal properties are not integrated.
