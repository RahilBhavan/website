// One warp computes a 16x8 output tile of C using mma.sync.
// In practice, you call this inside a loop over the K dimension and
// inside a larger block-level tiling scheme (see Chapter 5).
__device__ inline void mma_m16n8k16_fp16_fp32(
    float       d[4],   // output accumulator
    const uint32_t a[4],  // 4 × b32 from ldmatrix
    const uint32_t b[2],  // 2 × b32 from ldmatrix
    const float   c[4])   // input accumulator
{
    asm volatile(
        "mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 "
        "{%0, %1, %2, %3}, "    // D
        "{%4, %5, %6, %7}, "    // A
        "{%8, %9}, "            // B
        "{%10, %11, %12, %13};\n"
        : "=f"(d[0]), "=f"(d[1]), "=f"(d[2]), "=f"(d[3])
        : "r"(a[0]), "r"(a[1]), "r"(a[2]), "r"(a[3]),
          "r"(b[0]), "r"(b[1]),
          "f"(c[0]), "f"(c[1]), "f"(c[2]), "f"(c[3]));
}

The exact (lane, register slot) → matrix element mapping is normative and lives in the PTX ISA, §"Warp Level Matrix Multiply-Accumulate Instructions."[3] The high-level idea — that the warp distributes a small matrix across 32 lanes — is the part you need to internalize; the exact map is what ldmatrix.sync exists to handle for you.

When to choose each abstraction level

  • WMMA. Prototyping; portability across Volta/Turing/Ampere/Hopper; learning. ~70–80% of peak.
  • mma.sync + ldmatrix. Production-grade hand-written kernels; competitive with cuBLAS. ~85–95% of peak.
  • CUTLASS templates. When you want production-grade and portability and don't want to maintain it yourself. Often within 1–3% of cuBLAS, sometimes ahead on awkward shapes.
  • Hopper wgmma + TMA. H100-only. Async, much larger tiles, dramatically different programming model. Out of scope here but the same architectural ideas.

3.5cp.async and Software Pipelining

Overlap load with compute, by hand

Without async loads, the inner loop of a tiled GEMM looks like: load tile → barrier → compute → barrier → load next tile → barrier → compute → .... Each barrier idles the entire block. The compute and load phases never overlap. The Tensor Cores sit silent while DRAM loads finish.

Ampere added cp.async — an asynchronous memory copy from global memory directly into shared memory, bypassing the register file. The thread issues the copy and continues executing. The copy completes in the background. The thread synchronizes only when it actually needs the data.[4]

With cp.async you can double-buffer: while the Tensor Cores compute on buffer A, fire off the load for buffer B. When the compute is done, swap roles. The compute and the load are now happening at the same time. If the compute time and the load time are similar, you double throughput.

The control-flow primitives

Three PTX instructions form the loop primitives:

  • cp.async.<size>.shared.global [dst], [src], size; — issue a copy. The thread does not block.
  • cp.async.commit_group; — close out the most recent batch of cp.async requests; they form a "group."
  • cp.async.wait_group N; — block until at most N outstanding groups remain. wait_group 0 = wait for everything.
// Convenience CUDA intrinsic (since CUDA 11):
__device__ inline void cp_async_16B(void* smem_dst,
                                    const void* global_src)
{
    // Convert the generic shared-memory pointer to a 32-bit shared address.
    uint32_t smem_int = __cvta_generic_to_shared(smem_dst);
    // 16-byte cp.async — the canonical width for FP16 tile loads.
    asm volatile(
        "cp.async.ca.shared.global [%0], [%1], %2;\n"
        :: "r"(smem_int), "l"(global_src), "n"(16)
    );
}

__device__ inline void cp_async_commit() {
    asm volatile("cp.async.commit_group;\n" ::);
}

__device__ inline void cp_async_wait_all() {
    asm volatile("cp.async.wait_group 0;\n" ::);
}

// Wait until at most N groups remain in flight (lets earlier groups
// finish while later ones keep going — basis for multi-stage pipelines).
template <int N>
__device__ inline void cp_async_wait_group() {
    asm volatile("cp.async.wait_group %0;\n" :: "n"(N));
}
