4.2 Layer 1: resolve it yourself, then pin it

A naive fetcher checks the IP, then hands the hostname to an HTTP library, which resolves it again. If an attacker controls the DNS, the second answer can differ. That gap between the check and the use is what DNS rebinding exploits.

Rebinding works when the check and the connection resolve separately. Pinning makes them use one answer Illustration

4.3 Layer 2: a firewall that doesn't trust layer 1

Layer 1 is Python code, and code has bugs. A library might follow a redirect on its own, or a future edit might bypass resolve_public. So the fetcher container installs docker/egress.nft in its own network namespace before Python starts. The default policy is drop. It allows DNS only to 1.1.1.1 and 8.8.8.8, and TCP 80/443 only to addresses outside the blocked set. The blocked set is 10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16, 127/8, the documentation and benchmark ranges, multicast and reserved. All IPv6 is dropped. Either layer alone would stop the router request in Fig 4.1, so both would have to fail together.

Fig 4.2

Both guards must fail before a request reaches your LAN

4.4 The container and the egress check

  • Non-root, read-only root filesystem, tmpfs /tmp with noexec. Even a parser bug can't drop a persistent file or run a downloaded binary.
  • cap_drop: ALL. NET_ADMIN exists only for the entrypoint to install the firewall, and is dropped before Python starts. A compromised process can't change the firewall.
  • Only ./data is mounted. No $HOME, no Docker socket, so nothing to steal or escalate through.
  • Public resolvers, never the LAN router, so a scam name can't be resolved by your router's view of the network.
  • Egress ASN check. Before fetching, the container asks Cloudflare which IP its DNS query came from (a CHAOS-class TXT lookup of whoami.cloudflare), maps it to an ASN with Team Cymru, and refuses unless the ASN is in allowed_egress_asns (only AS22768, your building's ISP). On campus (AS36375) the fetcher won't start.

4.5 Limits on every response

Connect within 5 s, read within 10 s, and finish the whole body within 20 s. The last limit stops slow-drip tarpits that keep a read timeout alive forever. Bodies are streamed and aborted past 2 MB. The Content-Type must be on an allowlist (HTML, CSS, JS, icon images). At most 3 redirects, http/https only. Binaries are never saved, only their hash and size, and images are never decoded: the favicon is hashed as raw bytes. In passive_visit mode, the favicon and up to 5 same-origin, non-library JS/CSS files are fetched only if the homepage already has ≥ 3 investment terms.

4.6 Pacing: a pacer, not a bucket

SAFETY.md says "token bucket", but fetch.RateLimiter is actually a pacer. Every request, from either worker, waits until next_ok, then pushes next_ok 3 seconds later (60 / 20). A token bucket would let up to its capacity go out at once after a quiet spell. The pacer never bursts. That is stricter than the rule requires, which is fine, but the docs should name it correctly (Appendix A).

At 20 requests a minute the pacer starts one request every 3 s. A bucket could fire five at once Illustration

4.7 Outcomes, and why cloaking is a result, not a failure

Each capture is classified by fingerprint.classify as content, parked, blank, blocked (401/403/406/429/451/503), error or seized. Parked, blank and error pages get retries at +2 h and +24 h. When you review, a page that shows harmless content to SSRD but matches a scam's infrastructure is labeled decoy-cloaked.

Hard rule 3 says a block is recorded, never worked around: no proxies, no rotating IPs, no retry from another network, no headless browser. Evading blocks is also where legal risk rises (chapter 7). One method note: your building's residential IP probably sees less cloaking than a datacenter IP would, because cloakers filter datacenters. So SSRD's decoy share isn't comparable to datacenter-based studies. Say so in the README.

4.8 Evidence you could hand to someone

Raw bytes are stored gzip-compressed as data/captures/<sha256>.gz (mode 0600), so the file name proves the content. Each visit appends one JSON line to data/manifest/YYYY-MM-DD.jsonl: requested and final URL, redirect chain, fetch time, CT time, resolved IP, ASN, request and response headers, certificate SHA-256, body SHA-256, outcome and the tool's git commit. Each day's file gets a SHA-256 in hashes.txt. Past lines are never rewritten. If the VCU ever relies on a lead, this is what shows what you saw, when, and with which version of the code.

Check yourself

A scam domain has two A records: 198.51.100.20 and 192.168.1.1. What does SSRD do?
It refuses the whole name. resolve_public rejects any name with any non-global answer, because mixing public and private answers is a rebinding trick. (Both addresses are blocked by the firewall too: the first is a documentation range.)
Why keep the nftables firewall if resolve_public already refuses private IPs?
Defense in depth. Layer 1 is code that can have bugs or be bypassed by a library or a future edit. Layer 2 is enforced by the kernel and can't be changed by the unprivileged process.
A site returns 403 to SSRD. Should you retry from your phone's hotspot?
No. Record it as blocked or decoy and move on. Retrying from another IP to get past a block breaks hard rule 3 and raises legal risk.
Why is the 20 s total cap needed when there's already a 10 s read timeout?
A read timeout resets every time a byte arrives. A tarpit sending one byte every 9 s would never trip it. The total cap bounds the whole body.

5.1 Why SHA-256 of the page doesn't work

A cryptographic hash is built so that changing one byte changes the whole hash. That makes it perfect for proving a file is unchanged, which is how SSRD names its captures. It is useless for "these two pages are nearly the same", because two copies of a kit differ in the brand, a price ticker and a nonce. SSRD needs two kinds of hash: exact hashes for parts the operator doesn't touch (icons, JS and CSS files, chat-widget snippets), and similarity hashes for parts they edit lightly (the HTML and the copy).
