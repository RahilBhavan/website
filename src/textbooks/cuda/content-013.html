2.4Kernel 3 — Shared-Memory Tiling

The single most important optimization in GPU computing

The naive kernel re-reads each element of A from DRAM N times and each element of B from DRAM M times. If we could read each element from DRAM once and then keep it on-chip, we would multiply our arithmetic intensity by roughly the tile dimension, and we would shift the kernel decisively from memory-bound to compute-bound. That is exactly what shared-memory tiling does.

The algorithm

  1. Each thread block computes one TILE × TILE output tile of C.
  2. The block loops over "phases" of K. In each phase it loads a TILE × TILE tile from A and a TILE × TILE tile from B into shared memory, cooperatively.
  3. Threads synchronize on __syncthreads(). Now the entire tile of A and B is visible to all threads in the block.
  4. Each thread computes a partial sum, reading TILE values out of shared memory.
  5. Threads synchronize again, so no thread overwrites the SMEM tile in the next phase before its peers have finished reading.
  6. After K / TILE phases, each thread writes its accumulator to C.

Why exactly two __syncthreads()

The barriers are not aesthetic. Each one prevents a specific data race:

  • Barrier 1 (after loading). If thread A starts computing using As before thread B has finished writing its piece of As, A reads stale data. Without this barrier you get silent wrong answers, usually with one or two wrong elements per tile.
  • Barrier 2 (after computing). If thread A starts loading the next phase's tile into As before thread B has finished reading the current phase, B reads garbage. The visible failure mode is occasional wrong answers that change depending on warp scheduling.
#define TILE 32

__global__ void gemmTiled(const float* __restrict__ A,
                          const float* __restrict__ B,
                                float* __restrict__ C,
                          int M, int N, int K)
{
    // Shared-memory tiles: one for a row-block of A, one for a col-block of B.
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    // Coordinates of THIS thread's output element in C.
    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;

    // Accumulator lives in a register — fastest memory on the chip.
    float acc = 0.f;

    // Number of phases along the K dimension.
    const int nPhases = (K + TILE - 1) / TILE;

    for (int p = 0; p < nPhases; ++p) {
        // ============== STAGE: COOPERATIVE LOAD ===============
        // Each thread in the block loads ONE element of A and ONE of B
        // into shared memory. Together the block fills both TILE x TILE tiles.

        int aCol = p * TILE + threadIdx.x;
        int bRow = p * TILE + threadIdx.y;

        // Bounds-check the global edges (last phase may be partial).
        As[threadIdx.y][threadIdx.x] =
            (row < M && aCol < K) ? A[row * K + aCol] : 0.f;
        Bs[threadIdx.y][threadIdx.x] =
            (bRow < K && col < N) ? B[bRow * N + col] : 0.f;

        __syncthreads();   // (1) tiles are now fully loaded for everyone

        // ============== STAGE: COMPUTE ===============
        // Each thread does a TILE-element dot product against the tiles.
        // All loads here are from SMEM -> ~20 cycles instead of ~500.
        #pragma unroll
        for (int k = 0; k < TILE; ++k) {
            acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
        }

        __syncthreads();   // (2) safe to overwrite As/Bs in next phase
    }

    if (row < M && col < N) {
        C[row * N + col] = acc;
    }
}

// Launch: one block per output tile.
dim3 block(TILE, TILE);
dim3 grid((N + TILE - 1) / TILE, (M + TILE - 1) / TILE);
gemmTiled<<<grid, block>>>(d_A, d_B, d_C, M, N, K);

Why the index layout is As[threadIdx.y][threadIdx.x] and not the reverse

Shared memory has 32 banks; consecutive 4-byte words go to consecutive banks. When a warp executes As[threadIdx.y][k], all 32 threads in the warp have the same threadIdx.y (recall: warps span the x dimension first) and the same k. They all hit the same address → broadcast, one transaction, no bank conflict.

When the same warp executes Bs[k][threadIdx.x], all 32 threads have the same k and consecutive threadIdx.x values. They hit 32 consecutive 4-byte words → 32 different banks → no conflict, one transaction.

If you index As[threadIdx.x][threadIdx.y], you swap the fast and slow axes and create a 32-way bank conflict in the load. The kernel is suddenly 32× slower for the same source. Bank-conflict-free shared-memory indexing is the most easily-broken correctness-equivalent optimization in CUDA.

How much intensity did we just buy?

Per output tile (TILE² = 1024 output elements), the block reads K/TILE phases × 2·TILE² elements per phase = 2·K·TILE elements from DRAM, and performs 2·K·TILE² FLOPs.

Itiled = 2·K·TILE² / (2·K·TILE · sizeof(float)) = TILE / 4 FLOP/byte

For TILE = 32, that is 8 FLOP/byte — versus ~0.25 FLOP/byte for the naive kernel (1 FMA per 2 loads × 4 bytes each = 0.25 FLOP/byte). A 32× jump in intensity. That is what moves the kernel decisively to the right on the roofline.

To get the rest of the way to peak, we need to push intensity further still — by giving each thread multiple output elements (§2.5), by loading larger words at a time (§2.6), and finally by using the Tensor Cores (§3).

2.5Kernel 4 — 2D Register Tiling (Thread Coarsening)

More work per thread, less SMEM pressure per FLOP

In the tiled kernel, each thread produces one output element. That means the entire SMEM tile of As and Bs is loaded for TILE² threads to produce TILE² outputs — one each. We can buy more arithmetic per SMEM load by giving each thread multiple outputs.

Concretely, let each thread compute a TM × TN sub-tile of C (often called the register tile, because the accumulators live in registers). The block now needs only (TILE_M/TM) × (TILE_N/TN) threads to cover the same output tile. Each thread has TM × TN accumulator registers, loads a strip of As and a strip of Bs into registers, and FMAs them all together.

#define BM 128   // output tile rows handled by one block
#define BN 128   // output tile cols handled by one block
#define BK 16    // K-strip loaded per phase
#define TM 8     // each thread handles 8 output rows
#define TN 8     // each thread handles 8 output cols

// Per block: (BM/TM) x (BN/TN) = 16 x 16 = 256 threads.

__global__ void gemmRegTile(const float* __restrict__ A,
                            const float* __restrict__ B,
                                  float* __restrict__ C,
                            int M, int N, int K)
{
    __shared__ float As[BM][BK];
    __shared__ float Bs[BK][BN];

    // Each thread's top-left output element in this block's tile:
    int threadRow = threadIdx.y;          // 0..(BM/TM - 1)
    int threadCol = threadIdx.x;          // 0..(BN/TN - 1)
    int blockRowOrigin = blockIdx.y * BM;
    int blockColOrigin = blockIdx.x * BN;

    // Per-thread register file for the output sub-tile.
    float regC[TM][TN] = {0.f};

    const int nPhases = (K + BK - 1) / BK;
    for (int p = 0; p < nPhases; ++p) {
        // ============ COOPERATIVE LOAD ============
        // 256 threads cooperatively load BM*BK + BK*BN elements.
        // Each thread loads multiple elements (loop over the slack).
        const int totalA = BM * BK;
        const int totalB = BK * BN;
        const int tid    = threadRow * (BN / TN) + threadCol;
        const int nTh    = (BM / TM) * (BN / TN);

        #pragma unroll
        for (int i = tid; i < totalA; i += nTh) {
            int r = i / BK, c = i % BK;
            int gR = blockRowOrigin + r;
            int gC = p * BK + c;
            As[r][c] = (gR < M && gC < K) ? A[gR * K + gC] : 0.f;
        }
        #pragma unroll
        for (int i = tid; i < totalB; i += nTh) {
            int r = i / BN, c = i % BN;
            int gR = p * BK + r;
            int gC = blockColOrigin + c;
            Bs[r][c] = (gR < K && gC < N) ? B[gR * N + gC] : 0.f;
        }
        __syncthreads();

        // ============ COMPUTE: TM x TN register block ============
        // Outer loop along the K-strip.
        #pragma unroll
        for (int kk = 0; kk < BK; ++kk) {
            // Load a column of As (size TM) and a row of Bs (size TN) into regs.
            float aReg[TM], bReg[TN];
            #pragma unroll
            for (int i = 0; i < TM; ++i)
                aReg[i] = As[threadRow * TM + i][kk];
            #pragma unroll
            for (int j = 0; j < TN; ++j)
                bReg[j] = Bs[kk][threadCol * TN + j];

            // FMA the outer product into the register accumulator block.
            #pragma unroll
            for (int i = 0; i < TM; ++i)
                #pragma unroll
                for (int j = 0; j < TN; ++j)
                    regC[i][j] += aReg[i] * bReg[j];
        }
        __syncthreads();
    }

    // Write the TM x TN block back to C.
    #pragma unroll
    for (int i = 0; i < TM; ++i) {
        int gR = blockRowOrigin + threadRow * TM + i;
        #pragma unroll
        for (int j = 0; j < TN; ++j) {
            int gC = blockColOrigin + threadCol * TN + j;
            if (gR < M && gC < N) C[gR * N + gC] = regC[i][j];
        }
    }
}

What changed and why it pays

Each thread now does TM × TN = 64 FMAs per inner-loop iteration, but reads only TM + TN = 16 values from shared memory (the rest are already in registers). The compute-to-SMEM-load ratio jumps from 1× to 4× — and SMEM throughput stops being the bottleneck. The cost is register pressure: each thread now holds TM·TN = 64 accumulator registers plus the temporaries. At 64 registers per thread you can still hit ~50% occupancy on Ampere, which is plenty.

Boehm's well-known SGEMM walkthrough shows the same kernel family climbing from a few TFLOPS to roughly 70–90% of cuBLAS SGEMM on Ampere consumer parts, with 2D register tiling being the single largest jump in the FP32 path before warp-tiling and double-buffering.[1]

2.6Kernel 5 — Vectorized Memory Access

Four loads in one instruction

The hardware supports loads in widths of 32, 64, and 128 bits. CUDA exposes the wide loads through the built-in vector types float2, float4, int4, etc. A float4 load is a single 128-bit transaction — one instruction, one memory request, one register-file write of four floats.

For coalesced patterns, a 128-bit-wide load by every thread in a warp results in four 128-byte transactions to global memory and fills 4 × 32 = 128 floats with one instruction. The same data using 4 separate float loads would also take four transactions — but you would have spent four times the instruction issue slots. On a kernel that is instruction-throughput-limited, vectorization removes the instruction tax.

// Requires: A is aligned to 16 bytes (cudaMalloc guarantees this).
// Requires: index is a multiple of 4.

// Scalar version — 4 separate 32-bit loads.
float a = A[idx + 0];
float b = A[idx + 1];
float c = A[idx + 2];
float d = A[idx + 3];

// Vector version — one 128-bit load.
float4 v = *reinterpret_cast<const float4*>(&A[idx]);
// v.x v.y v.z v.w are now in registers.

// In the tiled kernel, store with the same pattern:
*reinterpret_cast<float4*>(&C[gIdx]) = make_float4(r0, r1, r2, r3);

The same idea applies to shared memory: a float4 SMEM load is one instruction and accesses 4 banks per thread. As long as the per-thread base is on a 16-byte boundary, you get conflict-free 4-bank-wide access. Vectorized SMEM loads are a standard trick in mature GEMM kernels and are essential when feeding Tensor Cores (chapter 3).

Diagnostic
If you forget to align — e.g. you cast an odd-offset pointer to float4* — the kernel may compile but will hit a misaligned-address fault at run time, reported by cudaGetLastError() as cudaErrorMisalignedAddress.
