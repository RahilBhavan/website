Atomic-note deep dive — §1.4

[[A1.4.1]]

Shared-memory banking — the arithmetic of conflicts

memory

Shared memory is split into 32 banks, each 4 bytes wide. The bank number for address a (in bytes) is (a / 4) % 32. A warp's 32 lanes can issue 32 simultaneous accesses; if every lane targets a different bank or all 32 target the same address (broadcast), the access completes in one cycle. If two or more lanes hit the same bank but different addresses, the hardware serializes them — an N-way conflict costs N cycles. The classic pathology is row-major access of a 32-column FP32 array: every lane lands in bank 0, giving a 32-way conflict and a 32× slowdown.

The classic fix is padding: declare the array as __shared__ float tile[32][33] instead of [32][32]. The extra column shifts every row by one bank, eliminating the conflict at the cost of 32 wasted floats. A more advanced fix is swizzling: XOR the column index with a function of the row so accesses spread evenly across banks without padding. CUTLASS and Hopper TMA descriptors rely on swizzled layouts.

Coalescing as a hardware rule, not an algorithm

memory

The memory subsystem services a warp's 32 loads in sectors: chunks of 32 contiguous bytes aligned to a 32-byte boundary. If all 32 lanes of a warp load 4-byte elements from a 128-byte aligned region, exactly four sectors are fetched — one full transaction per quarter-warp — and "coalescing" has happened. Any other access pattern fetches strictly more sectors than necessary. The hardware does not punish you for non-coalesced access; it just does more work. Coalescing is a property of the address pattern, not the loop nest; the same code path with permuted indices can shift from full coalescing to 32× over-fetch.

L2 cache — the GPU-wide last-level you can hint to

memory

L2 sits between the SMs and HBM. On A100 it is 40 MB; on RTX 3090 it is 6 MB; on H100 it is 50 MB. L2 is the only level shared by every SM, so it is the only place where data brought in by one SM can be cheaply reused by another. Ampere introduced persisting access policy windows: a kernel can mark a buffer as "expected to be reused" via cudaAccessPolicyWindow, and L2 will preferentially keep it resident, evicting transient data first. This is the only programmer-visible knob on the L2 replacement policy; everything else is hardware LRU.

HBM internals — banks, channels, and burst length

memory

HBM2/HBM3 is not a flat pool. The physical memory is organized as stacks, each containing multiple channels, each containing multiple banks. A read transaction is "activate the bank's row buffer, then burst-out 32 bytes (HBM2) or 64 bytes (HBM3)." If two consecutive requests target the same bank with different rows, the bank must precharge and re-activate, costing ≈ 10 ns. Spreading accesses across banks and channels — which the GPU's address scrambler already tries to do — is the difference between 75% and 95% of peak HBM bandwidth in practice. The metric to watch in Nsight Compute is dram__throughput.avg.pct_of_peak_sustained_elapsed.

1.5Occupancy and Latency Hiding

How the GPU survives 500-cycle memory loads

A naive reading of the latency numbers in §1.4 is alarming. A global memory load takes ~500 cycles. Multiply that by the millions of loads per kernel, and nothing should run. In practice, GEMMs hit a sizeable fraction of peak. The reason is latency hiding by warp switching.

When a warp issues an instruction whose result is not yet available (a load, a Tensor Core op, etc.), the warp goes to sleep on a hardware scoreboard. The warp scheduler on that sub-partition immediately looks for another warp that is ready to issue, and runs that one instead. As long as there is always an eligible warp available, the SM never stalls. The 500-cycle load is invisible — it is fully covered by useful work from other warps.

What occupancy is

Occupancy is the ratio of active warps on an SM to the maximum warps the SM can hold:

occupancy = active_warps_per_SM / max_warps_per_SM

On Ampere, the maximum is 48 warps per SM (= 1,536 threads).[2] So an "occupancy of 50%" means the SM is sustaining 24 active warps. An occupancy of "100%" (or "1.0") means 48.

What limits occupancy

Three resources compete for the SM:

  1. Registers per thread. If your kernel needs 64 registers per thread and the SM has 65,536 registers, the SM can hold 65,536/64 = 1,024 threads = 32 warps. That alone caps occupancy at 32/48 ≈ 67%.
  2. Shared memory per block. If your block uses 32 KB of SMEM and the SM allots ~96 KB to SMEM, only 3 blocks fit. If each block has 8 warps, that is 24 active warps — 50%.
  3. Block size limits. Max 1024 threads/block; max 16 blocks/SM on Ampere (32 on Hopper). These ceilings matter most for tiny blocks.

The limiting resource is whichever gives the smallest number. Your job during tuning is to know which one is binding and decide whether to relax it (e.g. spill some registers to gain a warp) or accept it (e.g. trade occupancy for better per-thread ILP).

The "high occupancy is not always optimal" trap

It is tempting to treat 100% occupancy as a goal. It is not. High occupancy is one strategy for hiding latency; the other is instruction-level parallelism within a single warp. A kernel that uses 128 registers per thread and runs at 33% occupancy can outperform a kernel that uses 32 registers at 100% occupancy, if the high-register kernel keeps more outstanding loads per thread and does more independent compute between them. Vasily Volkov's well-known talk Better Performance at Lower Occupancy (GTC 2010) is the canonical reference for this counter-intuitive result; the underlying observation is now reflected in CUDA's best-practice guidance.[7]

Practically: chase occupancy only until your kernel stops being limited by warp stalls. Beyond that, more occupancy buys you nothing.

Practical guidance
On Ampere, anything above about 50% occupancy is usually enough to hide DRAM latency in a well-written GEMM. The remaining performance comes from compute throughput (Tensor Cores), good memory access patterns, and pipelining — not from squeezing out more occupancy.
