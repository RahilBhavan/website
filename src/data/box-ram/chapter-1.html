1.1 Why a fast computer can still become difficult to use

A mixed development desktop has bursty demand. Several projects can each start a compiler, a browser batch or a numerical library. The interesting problem is combined demand: independently reasonable jobs can overlap at an inconvenient moment.

The local November 9 investigation recorded heavy direct reclaim, allocation stalls, swap traffic and a kernel OOM kill. It also found work outside the shared gate and insufficient per-job attribution. Those observations established a problem worth investigating. They did not identify one guilty build or prove a kernel defect. See the dated implementation plan, host findings.

Think of a stall as delayed useful work. A command can consume little CPU because it is waiting, not because it is cheap. A high memory reading can be harmless if the memory is productive and reclaim is inexpensive. A lower memory reading can accompany a bad experience if repeatedly needed state has been displaced. For the box, the relevant question is therefore: what did the user or job have to wait for?

That question motivates the measurements and the policy ordering in this guide. It also explains why a screenshot of a RAM meter is insufficient evidence for a tuning decision.

1.2 PSI provides a resource-contention signal

Linux Pressure Stall Information reports time lost to CPU, memory and I/O contention. some means at least some tasks are stalled; full means all non-idle tasks in the measured scope are stalled together. The rolling averages cover 10, 60 and 300 seconds. The total counter is in microseconds and exposes episodes that rounded averages can obscure. System-level CPU full is undefined and reported as zero. PSI measures resource stalls, not application response time. Kernel PSI documentation.

Engineering inference: combine these signals with an actual latency measurement. If the compositor stalls while memory pressure rises, memory becomes a plausible suspect. If compositor latency remains low despite a short host-wide pressure episode, that episode alone does not establish desktop harm. If display presentation freezes with little memory pressure, investigate a different path.

Two boundaries matter: the scope of the counter and the time interval. A host counter includes work unrelated to the tested command. A job counter narrows the population but does not automatically show a causal connection to the desktop. Comparing counter values from different boot periods is also meaningless without handling reset.

1.3 TMO and Senpai: use feedback and respect delayed costs

The ASPLOS 2022 TMO paper describes Meta's production memory-offloading system. It reports 20–32% total-memory savings across millions of servers. Senpai uses per-workload feedback, including PSI, and considers both anonymous-memory swap-ins and file-cache refaults. The system moved toward stateless reclaim requests instead of leaving workloads restricted by stale limits. Its published control parameters belong to that evaluated server environment. Weiner et al., TMO paper, proceedings DOI.

For BOX, three useful lessons follow. These are adaptations, not claims that the TMO implementation is installed.

First, decide which workload is being managed. Without a boundary, a machine-level observation cannot reliably say which project should receive a different policy. Job scopes and receipts make that question easier to answer.

Second, observe the cost, not just the amount of memory moved. A policy that makes a memory chart smaller can still be counterproductive if it slows the task the user is trying to perform.

Third, allow time for the consequences to appear. A previously idle browser or editor may be resumed after a build ends. An experiment that stops when the build exits can miss the cost paid during that return. This is why the protocol includes a post-build reuse phase.

The box's admission gate does not run Senpai. It does not continuously decide how much each job should offload. It samples pressure before allowing more participating work to start. The intellectual connection is feedback-informed resource management; the implementation and scope differ substantially.

1.4 Hermes: latency-critical work and batch work have different needs

*Memory at Your Service* studies colocated server services and batch jobs. Hermes combines allocator preparation and reservation for designated latency-critical services with proactive batch-file cache reclamation. Its evaluation includes server applications such as Redis and RocksDB. It is more than a generic cache-clearing script. The Middleware 2021 program confirms the publication; the technical source inspected is the authors' arXiv manuscript. Proceedings-text equivalence was not established.

For BOX, the useful interpretation is to distinguish urgent interactive work from work that can wait or restart. That supports preserving burst headroom and avoiding a design in which every build competes without coordination.

It does not establish that a particular desktop should reserve a fixed fraction of RAM. It does not justify replacing the host allocator, pinning broad desktop allocations, or discarding all build caches. Those would be different interventions with their own costs and failure cases.

A concrete transfer example is the control server. Losing the T3 server can make multiple projects harder to inspect or recover. A failed restartable job is also undesirable, but its consequences differ. A preference that preserves the control surface expresses that difference. Whether the current preference succeeds under real failure remains a separate empirical question.

1.5 Why a layered policy is a sensible starting point

The local implementation puts simple, observable controls ahead of a new adaptive reclaim daemon. That choice follows the actual knowledge gap: the early investigation lacked reliable workload attribution. Starting with complex reclaim logic would have increased the number of moving parts before resolving that gap.

The sequence is deliberate:

  1. Coordinate known heavy entry points.
  2. Attribute resource use to actual jobs.
  3. Preserve the baseline kernel mechanisms.
  4. Observe where pressure and latency coincide.
  5. Test one targeted adjustment.

Each step produces information needed for the next. This makes the investigation easier to falsify. A future observation might show that the bottleneck is CPU scheduling, a graphics wait, a long-lived job holding a slot or an uncovered container. The architecture should let the evidence select that next step.

1.6 Why the papers cannot choose BOX's numbers

The evaluation workloads differ from this machine's workload mix. The hardware, background activity and importance of interactive bursts differ too. Paper parameters can help formulate a trial, but they cannot substitute for a local comparison.

Even “memory savings” needs a defined denominator. Saving part of a managed server workload's memory is not the same claim as freeing that percentage of installed desktop RAM. Compression ratios are also data-dependent snapshots. Neither should become a promised speed-up.

The right conclusion is conditional: the research supports measuring contention, separating workloads and evaluating the costs of offloading. The current local evidence supports keeping those controls and collecting better comparisons. The remaining chapters explain what is implemented and how to test its value.
