The pipeline at one altitude

Six Python scripts in data_collection/ turn raw RPC responses into one CSV file. Five R scripts in analysis/ turn that CSV into Tables 2–4 and Figures 1–4 of the paper. Both halves are intentionally re-runnable: every Python script uses SQLite with INSERT OR IGNORE semantics so re-running never duplicates rows, and every R script is deterministic given a fixed random seed.

The pipeline runs end-to-end in roughly 4 hours, dominated by the initial transfer pulls (each token requires a few minutes of Alchemy paging). After that first run, re-running phase A is fast because INSERT OR IGNORE means only new blocks are pulled. Phase B takes maybe 30 minutes total — the CS estimator is the slowest step, because the bootstrap with B=9999 iterations is computationally non-trivial.

The pre-flight checklist

Before any regression runs, five things must be true. The blueprint specifies these as hard preconditions:

  1. All seven token contract addresses verified against issuer documentation, with verification dates logged in notes/data_anomalies.md.
  2. Issuer wallet exclusion lists built and reviewed for each token (no TODO_VERIFY placeholders remain).
  3. Five data-validation checks from Chapter 4 all pass.
  4. Treatment dates in data/treatment_dates.csv cross-referenced with Uniswap/Curve pool creation transactions.
  5. Power analysis (analysis/07_power_analysis.R) confirms the design has at least 40% power for the effect sizes we're targeting.

That last item — the power analysis — deserves emphasis. Before generating any estimates that anyone will see, we run 1,000 synthetic datasets under our maintained DGP assumptions with a postulated effect size, fit the CS estimator to each, and count how often we reject the null of zero effect at $\alpha=0.05$. The result is our pre-registered statistical power. With N=7 and the noise levels we observe in pilot data, expected power for a 30% velocity-increase ATT is around 45%. That's low but not zero. If power were below 30%, we would re-scope (add more tokens, switch to monthly aggregation, etc.) before continuing.

The main specification, formally

Three specifications appear in the paper as "main".

Spec 1: TWFE baseline (comparison)

$$\text{IHS}(V_{i,t}) = \alpha_i + \delta_t + \beta \cdot \text{ammListed}_{i,t} + \mathbf{x}_{i,t}'\gamma + \varepsilon_{i,t}$$

Token FEs $\alpha_i$, week FEs $\delta_t$, binary treatment $\text{ammListed}$, controls $\mathbf x = (\log \text{mcap}, \log \text{holders}, \text{age}, \text{FFR}, \log \text{defiTVL})$. SEs clustered at the token level with wild bootstrap. Reported as Table 2 column 1 — for comparison only. Accompanied by the Bacon decomposition showing the forbidden 2×2 comparisons (already-treated units used as controls) and the share of total Bacon weight they absorb.

Spec 2: Callaway-Sant'Anna (main causal spec)

$$\widehat{\text{ATT}}(g, t) \text{ via } \text{did::att\_gt(yname = "ihs\_velocity\_w", \ldots)} $$

With control_group = "nevertreated", est_method = "reg", time-varying controls in xformla. Aggregated with aggte(type = "simple") for Table 3 and aggte(type = "dynamic") for Figure 2. Wild bootstrap inference with B=9999. This is the headline.

Spec 3: Continuous treatment intensity

$$\text{IHS}(V_{i,t}) = \alpha_i + \delta_t + \beta \cdot \log(\text{ammTVL}_{i,t} + 1) + \mathbf{x}_{i,t}'\gamma + \varepsilon_{i,t}$$

Replaces the binary treatment with continuous AMM TVL (log-transformed). Interpretation: a doubling of AMM TVL is associated with $\beta \cdot \log 2$ additional IHS velocity. This specification tests the mechanism: if AMM listing matters because depth matters, the continuous version should be more significant than the binary version. Reported as Table 4.

Decision points where the project gets a choice

Throughout the pipeline, there are about a dozen judgment calls where the analyst has to pick one option over another. Each one is documented in the blueprint and revisited as a robustness check in Chapter 14. The most consequential:

  • Treatment threshold: $10k / $50k / $100k of AMM TVL? Main spec uses $10k; robustness shows $50k and $100k.
  • Control group: never-treated or not-yet-treated? Main uses never-treated; robustness uses not-yet-treated.
  • Estimation method: regression adjustment, IPW, or doubly robust? Main uses regression; robustness compares.
  • Velocity measure: dollar volume or transfer count divided by mcap? Main uses dollar volume; robustness uses count.
  • Winsorization threshold: 99th or 95th percentile? Main uses 99th; robustness uses 95th and unwinsorized.
  • BENJI scope: Polygon only or include Stellar? Main uses Polygon only; robustness drops BENJI entirely.
  • Aggregation: weekly or monthly? Main uses weekly; robustness uses monthly.
  • Inference: wild bootstrap with Webb weights or Rademacher? Main uses Webb; both reported in appendix.

If the headline finding survives all eight robustness perturbations qualitatively (same sign, statistical significance, roughly the same magnitude), the paper has a strong story. If it does not survive some specific perturbation, that becomes a finding in its own right — we report it honestly and discuss the implications.

The paper-writing handoff

Once all five robustness specs have been run and the placebo test has produced its distribution plot, the analyst hands off to paper-writing. The blueprint's Part 5 provides the section-by-section writing guide. The order is:

  1. Sections 3–4 first (data + institutional background — mechanical, you've already written most of this in your notes).
  2. Section 5 (identification strategy — based on Chapters 7–12 of this textbook).
  3. Section 6 (results — describe the tables and figures you've already produced).
  4. Section 7 (robustness — brief).
  5. Section 2 (literature review — needs citation management).
  6. Section 1 (introduction — last, once you know the full story).
  7. Section 8–9 (discussion + conclusion).
  8. Abstract — last of all, once the full draft exists.

Writing introductions first is one of the most common mistakes empirical authors make. The introduction's contribution paragraph requires knowing exactly what your headline finding is and what surprises came out of the robustness section. Writing it first forces you to commit to claims you may have to walk back. Write it last.

Two practical reminders

  1. Set a random seed at the top of every script that uses randomness. set.seed(42) at the top of 06_placebo.R and 07_power_analysis.R in R; the equivalent random.seed(42); numpy.random.seed(42) at the top of any Python script that uses synthetic data. The placebo and power-analysis figures must be bit-for-bit reproducible by a reviewer.
  2. Commit panel_weekly.csv to the repo. Phase A scripts re-pull on-chain data, which may differ slightly across runs (new transfers arrive, NAV prices update). To make the regression results perfectly reproducible from any time in the future, commit the assembled panel CSV as the canonical input. Re-running phase B against this CSV should always produce identical outputs.

Chapter 14 · Part IV — Execution

Robustness and placebo tests

The ladder of robustness specifications every reviewer expects, and the placebo test that converts "the result is statistically significant" into "the result is meaningfully different from what we'd see under no effect".

The robustness ladder

Modern empirical economics has converged on a fairly standard set of robustness checks for any DiD paper. We run eleven of them across four categories and select the six most informative for Table 5; the remaining five live in the appendix.

Category A: Sensitivity to the dependent variable

  • R1 — Transfer count instead of dollar volume. Define velocity as $(\text{transfer count}) / (\text{mcap})$ instead of $(\text{dollar volume}) / (\text{mcap})$. Tests whether the result is driven by a few large trades or by the broader frequency of activity.
  • R2 — Unwinsorized velocity. Use raw IHS velocity without 99th-percentile winsorization. Tests sensitivity to outliers.
  • R3 — Two-part hurdle model. Decompose effect into Probit on "any trade" + OLS on "log volume | trade". Reports extensive and intensive margins separately.

Category B: Sensitivity to the treatment definition

  • R4 — Alt threshold ($50k TVL). Tighter definition of "AMM listed".
  • R5 — Continuous treatment. Replace binary with $\log(\text{AMM TVL})$ (already in main table as Table 4).

Category C: Sensitivity to the sample

  • R6 — Drop BENJI. Removes the multi-chain confound. Tests whether the result depends on this token.
  • R7 — Drop first 30 days post-launch. Removes the "newly-launched token" weeks where velocity is volatile for non-treatment reasons.
  • R8 — Monthly panel. Re-aggregate to monthly, run CS again. Tests whether the weekly granularity is creating spurious noise.

Category D: Sensitivity to the estimator

  • R9 — Not-yet-treated control group. Switch from never-treated to not-yet-treated. Tests whether the four never-treated tokens differ from the treated tokens in concerning ways.
  • R10 — Sun-Abraham comparison. Already in Table 4.
  • R11 — HonestDiD bounds. Reports the CI under assumed PT violations at relative-magnitude bound $\bar M \in \{0.5, 1, 2\}$.

The exact column count in Table 5 depends on which of these we want to highlight — typically 6 columns, with the rest moved to an appendix.

What "passing" robustness looks like

The result we want to see in Table 5 is: across all robustness columns, the point estimate stays within ±25% of the main spec's value, the sign is always the same, and the standard errors are similar. That pattern says "the headline finding is not a fluke of one specific choice the analyst made."

What does not count as passing: one column where the estimate is much smaller or where the sign flips. If R7 (drop first 30 days post-launch) cuts the effect in half, that suggests the headline is partly driven by post-launch noise rather than AMM listing per se — and the paper has to address that in the text.

The placebo test

Robustness checks ask "is the result stable to choices I made?" The placebo test asks a deeper question: "is the result distinguishable from the kind of pattern that would appear under no effect?"

The procedure:

  1. For each of 500 iterations, randomly re-assign each treated token a fake "first AMM listing date" drawn uniformly from a per-token eligible window — specifically, from week (launch + 8) to week (T_max − 12), so that every fake cohort has at least 8 pre-period weeks and at least 12 post-period weeks of data within the token's actual sample lifetime.
  2. Re-run the CS estimator with these fake treatment dates.
  3. Record the placebo ATT estimate.
  4. Compare the actual ATT to the distribution of 500 placebo ATTs. The placebo p-value is the fraction of placebos with absolute value as large or larger than the actual.

Under the null hypothesis of no treatment effect, the actual ATT should look like a random draw from the placebo distribution. If the actual is in the top 5% (or bottom 5%, in absolute value), we can reject the null at the 5% level — and this rejection is robust to all the assumptions about parametric inference that the bootstrap requires.
