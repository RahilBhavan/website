3.7Hopper — TMA, wgmma, and Thread Block Clusters

What sm_90 added on top of everything in this chapter

Most of this textbook targets Ampere. Hopper (H100, sm_90) keeps every Ampere primitive but adds four big features that change the kernel-engineering shape of GEMM. Even if you do not own an H100, you should know what these are because the next-generation public CUTLASS kernels assume them.

[[A3.7.1]]

TMA — Tensor Memory Accelerator

hopper

The TMA is a hardware unit that copies multi-dimensional tiles from global memory to shared memory described by a tensor descriptor. Instead of one thread issuing one address per cp.async, one elect-one thread issues a single cp.async.bulk.tensor instruction with a tile descriptor and the unit fetches the entire 2D/3D/4D tile, optionally swizzled, into shared memory. The win: zero address-arithmetic instructions on the warps, perfect coalescing for free, asynchronous completion signaled by an mbarrier. Functionally, TMA replaces the entire load-prologue of an Ampere GEMM with a couple of PTX instructions. Required for wgmma performance.

Prereq [[§3.5 cp.async]] [[A2.9.4]]
Used by [[A3.7.2]]
[[A3.7.2]]

wgmma — warp-group MMA, async at the M-N tile level

hopper

Hopper's MMA instruction is wgmma.mma_async: it operates over a warp group (4 warps = 128 threads) and is asynchronous. The warp group issues the instruction, sets a fence, then can keep doing math while the Tensor Cores grind in the background. Combined with TMA-fed shared memory and async barriers, the inner loop of a Hopper GEMM is essentially three independent streams: TMA loads, wgmma execution, and accumulator updates — all overlapping. Output tile sizes are huge by Ampere standards (m64n256k16 is a common micro-tile). Ampere kernels do not port directly; Hopper requires a different scheduling model.

Prereq [[§3.4 mma.sync]] [[A3.7.1]]

Thread block clusters and distributed shared memory

hopper

Hopper added a new layer above blocks: a thread block cluster, up to 8 (or 16) cooperating blocks that share access to each other's shared memory via "Distributed Shared Memory" (DSMEM). A block can directly load from a sibling block's SMEM without going to L2. The use case is split-K GEMMs and FlashAttention-class kernels where the natural tile sizes exceed one SM's SMEM budget: clusters let you spread one tile across multiple SMs while keeping data on-chip. The PTX is ld.shared::cluster, declared via cluster_dim_x/y/z in the launch grid.

FP8 Transformer Engine — per-tensor amax scaling

hopper

Hopper Tensor Cores accept FP8 (E4M3/E5M2) inputs. To use them productively in training, NVIDIA's Transformer Engine library maintains running statistics of each tensor's amax (max absolute value), then rescales tensors per-step so they fit in the narrow FP8 range without overflow. The hardware does the matmul in FP8 but accumulates into FP32; the amax statistics live in extra small tensors that the framework keeps. The end-to-end speedup vs FP16 is roughly 2× at sufficient batch size; the engineering cost is non-trivial.

Nsight Compute:
Seeing Inside Your Kernel

Learning goal. Profile any CUDA kernel with Nsight Compute. Read every metric in the Summary, Memory Workload Analysis, Warp State Statistics, and Source views. Diagnose the dominant bottleneck and know which optimization to apply next — every time.

4.1Nsight Compute Architecture

What it does, and what its measurements are worth

NVIDIA ships two profilers. They sound similar, do different things, and you need both.

  • Nsight Systems (nsys): system-wide timeline. Shows CPU threads, CUDA API calls, kernel launches, memory copies, and CPU ↔ GPU synchronization. Use this to see the shape of your program — gaps between kernels, host-side bottlenecks, launch overhead, multi-stream behavior. Lightweight, almost no slowdown.
  • Nsight Compute (ncu): per-kernel deep dive. Counts hundreds of hardware performance counters during kernel execution and gives you the data needed to diagnose why a kernel is slow. Heavy — it slows your program down enormously while profiling. Use this on the kernels Nsight Systems flagged.

How ncu gets its numbers — and why this matters

The GPU has a fixed number of hardware counter slots — much smaller than the number of metrics you might want. When you ask ncu for a metric set that exceeds the slots in one pass, the tool transparently replays the kernel. Each replay collects a different subset of counters. ncu stitches the results together into a single report. This is called kernel replay, and it has two practical consequences:

  1. Profiling makes the kernel run many times. If your kernel has side effects (e.g. writes to memory the next launch reads), enable kernel replay isolation (the default since recent versions) so each replay sees the same input state.
  2. Profiled timings are not real timings. Counter-collection inflates kernel duration by 2–100×. Use ncu timings only relatively — to compare two kernel versions in the same report. For absolute timing, use CUDA events.

Other replay modes exist (Application Replay, Range Replay) and matter for complex workloads with cross-kernel state.[1]

4.2Running the Profiler

The CLI commands you will use 95% of the time
# 1) Full profile of every kernel launch in the program.
#    Writes report.ncu-rep, which opens in the Nsight Compute UI.
ncu --set full -o report ./my_program

# 2) Default profile (smaller metric set, much faster).
ncu -o report ./my_program

# 3) Profile just a few named metrics — fastest, scriptable.
ncu --metrics sm__throughput.avg.pct_of_peak_sustained_active,\
              dram__throughput.avg.pct_of_peak_sustained_elapsed,\
              l1tex__throughput.avg.pct_of_peak_sustained_active \
    ./my_program

# 4) Skip warmup launches, profile only the steady-state kernel.
#    --launch-skip N    : skip first N kernel launches
#    --launch-count M   : then profile M of them
ncu --launch-skip 5 --launch-count 1 -o report ./my_program

# 5) Filter to a particular kernel by name (regex).
ncu --kernel-name regex:gemmTiled.* --launch-count 1 -o report ./my_program

# 6) Source-level profiling — requires nvcc -lineinfo at compile time.
#    The Source view in the UI then shows per-line PTX and SASS with cycle counts.
nvcc -O3 -arch=sm_86 -lineinfo -o my_program my_program.cu
ncu --set full --import-source on -o report ./my_program

# 7) Multi-process apps (e.g. distributed training): follow children.
ncu --target-processes all -o report ./launch_script.sh

# 8) Compare two builds. ncu does NOT have a --diff flag — comparison
#    is done in the UI by adding a baseline:
#       File -> Open  baseline.ncu-rep
#       File -> Add Baseline  optimized.ncu-rep
#    Or, equivalently, from the CLI summary table:
ncu --import optimized.ncu-rep --baseline baseline.ncu-rep --csv > diff.csv
The baseline workflow is the most underused feature
Always profile both your old and new kernel into separate .ncu-rep files, then add the old one as a baseline when viewing the new one. The UI shows a delta column for every metric. Every optimization in this book should be validated by exactly this workflow: profile, change one thing, re-profile, verify the metric you targeted moved and nothing else regressed.
