2.11Unified Memory and the Allocator Stack

When to cudaMallocManaged, when to stay explicit
[[A2.11.1]]

Unified memory — one pointer, two physical homes

memory

cudaMallocManaged returns a pointer valid on both host and device. The driver page-faults data between host and device on first touch, transparent to the program. Productivity-wise, brilliant; performance-wise, treacherous: every page fault is ~10 µs, and a 4 KB page fault to load a single FP32 row hides nothing. Mitigations: cudaMemPrefetchAsync to push data ahead of time, cudaMemAdvise with cudaMemAdviseSetReadMostly or SetPreferredLocation to bias placement, and oversubscription support on Pascal+ for problems that don't fit. For peak performance use explicit cudaMalloc + cudaMemcpyAsync; for prototyping or for codes whose access patterns the driver can predict, managed memory is fine.

Used by [[A2.11.2]]
[[A2.11.2]]

Stream-ordered allocator (cudaMallocAsync) — the modern default

memory

Since CUDA 11.2, cudaMallocAsync / cudaFreeAsync allocate and free in a stream, using a per-device memory pool. Three wins: (1) freed memory can be reused by a later allocation in the same stream without synchronizing, (2) the pool can be size-trimmed via cudaMemPoolSetAttribute, (3) allocations are dirt cheap after the first one of a size class. Use this as the default; fall back to cudaMalloc only when integrating with code that needs a synchronous allocator.

2.12Error Handling and Sanitizers

The five tools that turn UB into a fix-ticket
[[A2.12.1]]

Sticky errors — why one bad kernel breaks every later call

debugging

CUDA errors are sticky: once a kernel triggers a fault (illegal memory access, misaligned address), every subsequent runtime call on the same context returns the same error until you cudaDeviceReset(). That's why the error you actually print is rarely from the line that caused the problem; it is from the next cudaMemcpy that propagates the sticky state. Always wrap launches with cudaGetLastError() immediately afterward, and call cudaDeviceSynchronize() before declaring success in a unit test — kernels return asynchronously, and a fault inside one can land in the next Test's setup.

Used by [[A2.12.2]]
[[A2.12.2]]

compute-sanitizer — five tools, one binary

debugging
  • memcheck Out-of-bounds, misaligned, leaked allocations.
  • racecheck Shared-memory data races, including the subtle "missing __syncthreads" pattern.
  • initcheck Reads of uninitialized memory.
  • synccheck Misuse of __syncthreads across divergent paths.
  • leakcheck Allocations never freed before context teardown.

Run them on every new kernel before benchmarking; the overhead is large (5–50×) but the output is the difference between "ship it" and "two days of git-bisect."

Tensor Cores & PTX:
The Hardware Acceleration Layer

Learning goal. Understand what a Tensor Core actually is at the hardware level. Write a working WMMA kernel. Drop down to raw PTX mma.sync and cp.async to extract the last 10–20% of performance that the high-level API leaves on the table.

3.1What Tensor Cores Are

Specialized silicon for one operation, executed brilliantly

A Tensor Core is a piece of silicon that performs a small matrix multiply-accumulate in a single hardware instruction. Where a CUDA core does one scalar FMA per clock — d = a·b + c, three inputs, one output — a Tensor Core does D = A·B + C with A, B, C, D all small dense matrices. One instruction; several hundred FMAs of useful work.

Each generation roughly doubles per-SM Tensor-Core throughput at the previous generation's precision and adds a new lower-precision mode. The key consequence for you: the throughput ceiling you measure against is set by the Tensor-Core peak of your specific architecture, not the CUDA-core peak.
