The Bank Model

shared memory

Shared memory on every modern NVIDIA arch is organized as 32 banks, each 4 bytes wide, interleaved across addresses. Bank b of word w holds byte address 4*(32*w + b). A warp issuing one shared-memory access produces 32 addresses. The hardware groups them by bank; per-cycle a bank can serve exactly one 32-bit word. Two cases:

  • No conflict — each thread hits a distinct bank, or all 32 threads hit the same word in the same bank (broadcast). One cycle.
  • N-way conflict — 2 ≤ N ≤ 32 threads each hit a different word in the same bank. The hardware serializes into N cycles.

Bank conflicts are a per-warp, per-instruction property — not per kernel. The metric to watch in Nsight Compute is l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_*.

Three solutions to the column-stride conflict: pad the row (wastes one bank per row), XOR-swizzle the index (no waste — used by CUTLASS), or transpose the tile in shared memory.
// Conflict-free row access, 32-way conflict column access
__shared__ float Tile1[32][32];

// One-pad trick — 4 KB wasted but trivial
__shared__ float Tile2[32][33];

// XOR swizzle — no padding, no conflict.
// Compute the storage index from (row, col):
__device__ inline int swizzle(int row, int col) {
    return row * 32 + (col ^ ((row & 0x7) << 2));
}
__shared__ float Tile3[32 * 32];   // accessed via swizzle(r,c)

// Store-side write uses the same swizzle, so reads/writes are symmetric.
Tile3[swizzle(r, c)] = value;
float v = Tile3[swizzle(r, c)];

11.2XOR Swizzles & ldmatrix Layouts

Why CUTLASS never pads anything

[A11.2.1]

Swizzle as a Permutation

layout

A swizzle is a bijection on memory addresses such that for every access pattern your kernel issues, the addresses land in distinct banks. CUTLASS expresses swizzles as three integers: Swizzle<B, M, S> meaning "XOR the top B bits of the column index, shifted by S, into the row-offset whose lowest M bits we mask." The pattern is parameterized so that for a given tile shape and target instruction (ldmatrix.x4.b16, etc.) you can pick the swizzle that makes both loads and stores conflict-free.

The most useful concrete recipes:

  • 16×16 FP16 fragment (Tensor Core m16n8k16) → Swizzle<3,3,3> over a row-major tile.
  • 16×8 FP16 fragment → Swizzle<2,3,3>.
  • 32×32 FP32 tile (no Tensor Core) → Swizzle<2,3,2> or just the XOR-by-row-bits pattern in Listing 11.1-A.
Mental model

"Bank-conflict free" means the 32 addresses produced by one warp instruction map onto 32 distinct (bank, word) pairs. Padding achieves this by inserting empty bytes; swizzling achieves it by mixing the row bits into the column bits. Padding wastes capacity and complicates pointer arithmetic; swizzling is free at runtime and reversible.

11.3L2 Carveout & Persisting Access Policies

Pin hot data into L2 — the secret weapon for small-K GEMMs and embeddings

[A11.3.1]

The L2 Cache Is Programmer-Visible (sm_80+)

cache

Ampere's L2 is 40 MB on A100, 6 MB on RTX 3090. Hopper H100 has 50 MB. The driver lets you reserve a fraction of L2 as a persistent carveout for a designated address range. Reads/writes inside that range are tagged "persistent" and the cache replacement algorithm protects them from being evicted by streaming traffic. Use it when:

  • The same weights are reused across many launches (LLM decoder weights between tokens).
  • A small lookup table is hit by every thread (embedding tables, position encodings).
  • A GEMM has a small K — the operand traffic dominates and reuse is cross-tile.
Used by§5.2 Vulnerable shapes
cudaStream_t stream;
cudaStreamCreate(&stream);

// 1. Reserve up to 30 MB of L2 as the persistent carveout.
size_t persist_bytes = 30 * 1024 * 1024;
cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, persist_bytes);

// 2. Attach a stream attribute that maps a memory range to persistent policy.
cudaStreamAttrValue attr = {};
attr.accessPolicyWindow.base_ptr   = weight_ptr;
attr.accessPolicyWindow.num_bytes  = weight_bytes;
attr.accessPolicyWindow.hitRatio   = 1.0f;
attr.accessPolicyWindow.hitProp    = cudaAccessPropertyPersisting;
attr.accessPolicyWindow.missProp   = cudaAccessPropertyStreaming;
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &attr);

// 3. Launch kernels on this stream — accesses inside [weight_ptr, +weight_bytes)
//    are treated as persistent.
my_decoder_kernel<<<grid, block, 0, stream>>>(weight_ptr, /*…*/);

// 4. Reset when you're done so the next phase doesn't inherit the policy.
attr.accessPolicyWindow.num_bytes  = 0;
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &attr);
cudaCtxResetPersistingL2Cache();  // optional: drop any persistent lines
Pitfall

Set num_bytes > the carveout size, and you don't get a warning — you get false-positive hit rates because the hardware refuses to mark over-capacity lines as persistent. Always check the L2 hit-rate metric afterward; if it didn't move, the carveout was misconfigured.

11.4HBM, GDDR, and the Memory Subsystem

Why "global memory bandwidth" hides three different physical realities

[A11.4.1]

HBM2e/HBM3 vs GDDR6X — Same Goal, Different Trade-offs

DRAM

HBM (High Bandwidth Memory) stacks 4–8 DRAM die on a silicon interposer right next to the GPU die. The interface is 1024 bits wide per stack, with 4–6 stacks per GPU. A100 has 5 HBM2e stacks at 2.4 Gbit/s, giving 1.6 TB/s. H100 has 5 HBM3 stacks at 5.2 Gbit/s = 3.35 TB/s. The cost: HBM doubles GPU die cost and limits you to data-center thermal envelopes.

GDDR6X sits on a PCB and talks to the GPU over a 256–384-bit bus. RTX 4090 has 384-bit GDDR6X at 21 Gbit/s = 1.0 TB/s. Cheaper, easier to manufacture, but lower bandwidth and higher latency.

Implication for kernel design: HBM rewards large contiguous transfers (cp.async, TMA). GDDR rewards L2 hit rate because the L2-to-HBM ratio is lower. Same kernel often wants different tile sizes on consumer cards vs data center cards.

11.5Pinned, Pageable, Unified, Stream-Ordered

The four allocators and when each one wins

[A11.5.1]

Pageable vs Pinned vs Mapped

host memory

Pageable — default malloc. The CUDA driver must first copy your data into a hidden pinned staging buffer before DMA. Effective H2D bandwidth: ~6 GB/s on PCIe Gen4.

Pinned (cudaMallocHost or cudaHostAlloc) — page-locked, eligible for direct DMA. Effective bandwidth: PCIe peak (~26 GB/s Gen4 x16, ~52 GB/s Gen5). Down-side: pinned pages cannot be swapped, so allocating GBs of pinned memory starves the OS.

Mapped pinned (cudaHostAllocMapped) — pinned plus accessible by the GPU through a unified address. Useful for tiny, latency-critical writes (e.g., a kernel signaling completion to the host). For large transfers, an explicit memcpy is still faster because the driver can stream batches.
