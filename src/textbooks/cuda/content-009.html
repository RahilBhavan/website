Registers

Every thread has private access to the register file. On Ampere, the per-thread register limit is 255 32-bit registers; the per-SM register file is 65,536 32-bit registers. Register allocation is done by the compiler at compile time — you do not allocate registers; you write code, and nvcc decides.

If your kernel uses too many registers per thread, two things happen, both bad. First, occupancy drops, because fewer threads' worth of registers fit in the SM (covered in §1.5). Second, the compiler can spill excess values to local memory, which despite its name is a per-thread region of global memory. A register spill is catastrophic — what should be a single-cycle read is now a 400+ cycle global memory load. You can see spills in the compiler output by passing -Xptxas -v to nvcc.

Shared memory

Shared memory is your primary optimization lever. It is software-managed cache — you decide what goes in and when. On Ampere, 128 KB per SM is shared between the L1 cache and shared memory; you can request a particular split. A single thread block can request up to about 99 KB of shared memory on sm_86 (and up to roughly 163 KB on sm_80, the A100) via the cudaFuncSetAttribute opt-in.

Shared memory has approximately the same latency as L1 and an aggregate bandwidth measured in TB/s per SM. That is roughly 100× the latency advantage over global memory and roughly 20× the bandwidth advantage. The reason tiling works is that every element of a tile is loaded from global memory once into shared memory and then re-read from shared memory many times.

Bank conflicts

Shared memory is organized into 32 banks, each handling 4 bytes per cycle. If 32 threads in a warp access 32 different banks in one cycle (one address per bank), they all complete in parallel — peak throughput. If two or more threads access different addresses on the same bank, the hardware serializes them — a bank conflict, and your shared-memory throughput drops in proportion to the conflict count.

The classic example is loading a tile of float with stride 32. If you index smem[threadIdx.x * 32], every thread hits the same bank — a 32-way bank conflict, and your kernel runs 32× slower on that load. The classic fix is padding: declare __shared__ float smem[32][33] (one extra column) so that consecutive rows fall on different banks.

Global memory coalescing

When a warp issues a load from global memory, the memory subsystem services it in sector transactions — 32-byte sectors on Ampere, grouped into 128-byte cache lines.[6] If all 32 threads of the warp request addresses within a single 128-byte aligned region, the request becomes one 128-byte transaction. If each thread reaches into a different 128-byte region, the warp issues 32 transactions — 32× the bus traffic for the same FLOPs.

This is coalescing, and it is the single most-checked thing in a CUDA code review. The rule, almost universal: thread i in a warp should access address base + i. Indexing patterns that follow base + i get coalesced; patterns like base + i * stride for any stride greater than 1 do not.

// Assume float A[N]. tid = threadIdx.x in [0, 32).
// 'base' is the warp-wide starting offset.

// =================== COALESCED (1 transaction) ===================
// Consecutive threads -> consecutive 4-byte slots
// -> one 128-byte aligned segment fully covered.
float x = A[base + tid];

// ================== UNCOALESCED (up to 32 trx) ==================
// Each thread reads with stride 32 floats = 128 bytes.
// Every thread lands in a DIFFERENT 128-byte segment.
float y = A[base + tid * 32];

// ============ NEAR-COALESCED, OFFSET BUT CONTIGUOUS ============
// Misaligned by 4 bytes -> 2 transactions instead of 1.
// Penalty depends on how much spills across the 128-byte boundary.
float z = A[base + tid + 1];

L2 cache

L2 sits between every SM and the DRAM controllers. It is the only cache that is shared across all SMs. On the RTX 3090 it is 6 MB; on the A100, 40 MB; on the H100, 50 MB. If two thread blocks running on different SMs happen to load the same data, the second one hits L2 instead of DRAM.

L2 hit rate is one of the most diagnostic metrics in Nsight Compute. A high L2 hit rate means your workload's working set fits — you are getting effective reuse across SMs. A low L2 hit rate means each block is pulling new data from DRAM, and the only knob you have is to reuse data within an SM via shared memory.

Global memory (HBM / GDDR)

This is the chip's off-chip memory — HBM2e on data-center parts, GDDR6X on consumer cards. The RTX 3090 has 24 GB GDDR6X on a 384-bit bus at 19.5 Gbps, yielding 936 GB/s of peak bandwidth.[2] The A100 80GB has roughly 2 TB/s of HBM2e bandwidth; the H100 SXM, around 3.35 TB/s of HBM3.

The latency, however, is brutal: 400–800 clock cycles. The GPU hides this latency by switching warps — while one warp waits on its load, another runs. This works only if there are enough warps; that is the next section.

As[threadIdx.y][threadIdx.x] = A[ globalRowA * K + globalColA ];

// 2. Barrier. NEEDED — otherwise some threads read As/Bs before

__syncthreads();

// 3. Compute. Each thread reads many As/Bs elements (reuse!) and
//    accumulates a partial dot product in a register.
float acc = 0.f;
for (int k = 0; k < 32; k++) {

}

// 4. Barrier. NEEDED — so no thread starts overwriting As/Bs in

__syncthreads();
The single most important sentence in this chapter
Every GEMM optimization in this book — tiling, register accumulation, vectorized loads, Tensor Cores, cp.async pipelining — is a different way of squeezing more arithmetic out of each global-memory byte you spend. That ratio has a name (arithmetic intensity, §1.6) and a graph (the roofline). Internalize that, and every optimization slots into one of two buckets: move my workload right on the roofline (more reuse) or move it up (better instruction mix).
