2.9Synchronization and Memory Ordering

Barriers, fences, atomics, and the CUDA memory model
[[A2.9.1]]

__syncthreads() — the all-block barrier with a sneaky guarantee

sync

Three things __syncthreads() does in a single instruction: (1) blocks every thread in the block until all have reached the call, (2) acts as an acquire/release fence for shared memory within the block, (3) flushes any pending shared-memory writes so subsequent reads see them. Calling it inside a divergent region is undefined behavior — if any thread in the block fails to reach the same barrier, the block deadlocks. The compiler will sometimes silently place a __syncthreads() inside an if because it inlined a function for you. Look at the SASS (BAR.SYNC) when in doubt.

Warp-level primitives — shuffle, ballot, vote, sync

sync

Within a single warp, threads share data faster than shared memory permits via warp-shuffle intrinsics. Five families to know:

  • __shfl_sync Exchange a register value across lanes by lane id. The basis for fast warp reductions.
  • __shfl_xor_sync Swap with the lane whose id differs by a fixed XOR mask. The natural butterfly pattern for log-step reductions.
  • __ballot_sync Every lane reports a one-bit predicate, returns a 32-bit mask of where the predicate was true. Used to compress sparse data.
  • __any_sync / __all_sync Boolean reductions across the warp.
  • __syncwarp The warp-only barrier; Volta+ needs it whenever a warp publishes through registers/shared memory and another part of the same warp reads.

All of these take a mask argument — a 32-bit value naming which lanes participate. Passing a wrong mask (a stale one from before a branch) is the #1 source of "intermittent NaNs only on Ampere" bugs.

Atomics — the only safe shared-write primitive

sync

atomicAdd, atomicMax, atomicCAS, and friends. Read-modify-write to a single address that is atomic with respect to every other thread in the device. Two costs to know: (1) atomics on the same address serialize — N threads colliding on one address means N sequential ops; (2) atomics on shared memory are ~10× faster than atomics on global memory because they hit the SM-local L1 alias rather than going out to L2. A privatized histogram (one bin-counter per thread block in shared memory, then one global atomic merge at the end) often turns a 100×-slow naive global-atomics histogram into a ~peak-bandwidth kernel.

Async barriers (cuda::barrier / mbarrier.* PTX) — the post-Ampere primitive

sync

Ampere introduced an async-friendly barrier that lives in shared memory. Unlike __syncthreads, it counts arrivals and completions separately, so a thread can "arrive" (declare its work is in flight) and then go do unrelated computation while the hardware drains its async copies; only when the thread later "waits" does it block. This is the synchronization primitive behind cuda::pipeline and the production-quality cp.async pipelines covered in §3.5. Hopper extends this with the TMA's barrier and "elect-one" optimizations.

Cooperative Groups — typed views of synchronization scopes

sync

The Cooperative Groups header (cooperative_groups.h) wraps the hand-rolled mask-and-shuffle pattern in C++ types: cg::thread_block, cg::coalesced_threads, cg::thread_block_tile<32>, cg::grid_group. Each group has a .sync() method, an .any(), an .reduce(...). The big win is grid-wide synchronization: with a cudaLaunchCooperativeKernel launch and cg::this_grid().sync(), you can write a single-kernel multi-pass algorithm without going back to the host. The cost is that all blocks must fit on the GPU simultaneously, which caps the grid size.

The CUDA memory model — relaxed by default, scoped on demand

sync

The CUDA memory model is patterned after C++11's: every memory operation has a memory order (relaxed / acquire / release / acq_rel / seq_cst) and a scope (thread, block, device, system). Most reads and writes are implicitly relaxed; you bring in stricter ordering by using cuda::atomic_ref, __threadfence_block(), __threadfence(), or __threadfence_system(). The scope argument tells the hardware how far the fence has to reach — thread_scope_block uses only the local L1 fence; thread_scope_device drains L2; thread_scope_system reaches host memory. Tighten only when correctness requires it; each step out costs cycles.

2.10Streams, Events, Async, and Graphs

How to keep the GPU busy when one kernel isn't enough
[[A2.10.1]]

CUDA stream — a queue of work the device executes in order

async

A cudaStream_t is a FIFO of operations (kernel launches, memcopies, events) that the device guarantees to execute in submission order. Operations in different streams may overlap or reorder. Stream 0 (the "default stream") has special blocking semantics in most legacy modes — it serializes against every other stream — so use a named stream from cudaStreamCreate when overlapping work. Per-thread default streams (-default-stream per-thread) restore parallelism for multi-threaded host code.

Used by [[A2.10.2]] [[A2.10.4]]

Events — markers you can wait on or time with

async

A cudaEvent_t is a hardware-recorded timestamp in a stream. Three uses: (1) timing — record one before and one after a kernel, then cudaEventElapsedTime gives sub-microsecond runtime; (2) cross-stream dependencies — cudaStreamWaitEvent(stream2, event_from_stream1) makes stream2 wait without involving the host; (3) host polling — cudaEventQuery tells you whether the event has fired. For benchmarking always prefer events over std::chrono: host clocks see launch overhead but not actual device time.

Async copies (cudaMemcpyAsync, pinned host memory)

async

Host-to-device copies happen at PCIe bandwidth, and that bandwidth is only achievable from pinned host memory (cudaMallocHost / cudaHostAlloc). Pageable allocations cost ~2× because the runtime stages them through an internal pinned buffer. cudaMemcpyAsync on a non-default stream lets you overlap copy with computation in another stream — the classic three-stream "stage-execute-drain" pipeline that hides PCIe behind compute.

Prereq [[A2.10.1]]
[[A2.10.4]]

CUDA Graphs — record a DAG once, replay it cheap

async

A CUDA Graph is a captured DAG of kernel launches, memcopies, events, and host callbacks. You build it once (via stream capture — record the work submitted on a stream, or via the explicit cudaGraphAdd* APIs) and then replay it with one cudaGraphLaunch call. The win is amortization: for a pipeline of 50 small kernels, the per-launch overhead drops from ~50 × 5 µs to a single launch of a few microseconds. Graphs are the canonical fix for "my GPU is 80% idle in the timeline view." Use them whenever the same sequence of work runs many times — every training step, every inference call, every iteration of a numerical solver.

Trap

Graph capture turns runtime API calls into recorded nodes; if a kernel inside the capture depends on a value computed by the host, you must either bake it into the graph as a memcpy node or use cudaGraphExecKernelNodeSetParams to update it before each replay. Modifying a captured graph is much more constrained than rebuilding one.
