Atomic Doesn't Mean Ordered

atomics · ordering

atomicAdd on a global address is atomic w.r.t. other atomics on the same address, but offers no ordering relative to other reads/writes. To enforce a "I wrote X, now signal flag" pattern across blocks, you need __threadfence_system() (or PTX fence.sc.gpu) between the write and the flag set. Forgetting this produces a race only visible under high load when the scheduler interleaves blocks aggressively.

17.4Numerical Validation

The harness you keep next to every kernel

// Compute relative and absolute error vs a reference (CPU or higher precision).
double validate(const float* test, const float* ref, int N,
                double rtol = 1e-3, double atol = 1e-5) {
    double max_rel = 0, max_abs = 0;
    int    n_fail  = 0;
    for (int i = 0; i < N; ++i) {
        double a = std::abs((double)test[i] - (double)ref[i]);
        double r = a / (std::abs((double)ref[i]) + 1e-30);
        max_abs = std::max(max_abs, a);
        max_rel = std::max(max_rel, r);
        if (a > atol && r > rtol) ++n_fail;
    }
    printf("max_abs=%e  max_rel=%e  fails=%d/%d\n", max_abs, max_rel, n_fail, N);
    return max_rel;
}
Set tolerances honestly

For an FP16 Tensor-Core GEMM with FP32 accumulator, expect rtol ≈ 1e-3. For FP32 throughout, rtol ≈ 1e-5. For BF16, rtol ≈ 1e-2. If your test passes only at rtol = 1e-1, you have a bug, not a precision limit.

17.5Printf, Asserts, & Trap

The lo-fi diagnostics that still work

[A17.5.1]

Device-Side printf

printf

Device printf writes into a per-context circular buffer and flushes at kernel exit or on cudaDeviceSynchronize. Each call from each thread serializes onto a hardware FIFO — printing from all 32 lanes of a warp will reorder and may drop messages if the buffer overflows. Use the gating pattern:

if (blockIdx.x == 0 && threadIdx.x == 0) {
    printf("acc[0,0] = %f\n", acc);
}

Grow the buffer with cudaDeviceSetLimit(cudaLimitPrintfFifoSize, 16 << 20) if you're losing output.

[A17.5.2]

assert() in Device Code

assert

Standard C assert() works on the device. On failure it prints the failed expression with the block/thread index and traps the launch — the next cudaDeviceSynchronize returns cudaErrorAssert. Cheap insurance for invariants like "K is a multiple of 16" deep inside a kernel.

Performance Methodology:
The Discipline Behind the Win

Learning goal. Beating cuBLAS is not about knowing one trick; it is about applying a disciplined loop of measurement, hypothesis, intervention, and re-measurement. This chapter codifies that loop so you can apply it to any kernel, not just GEMM. You will learn the SOL (speed-of-light) analysis Nsight Compute exposes, how to bound expected performance from first principles, how to set up an autotuner, and how to recognize and avoid the dead-ends every new kernel engineer falls into.

18.1The Optimization Loop

Five steps, in this order, always

[A18.1.1]

Measure → Bound → Hypothesize → Change One Thing → Measure Again

methodology
  1. Measure — collect Nsight Compute counters with --set full. Read SOL %, achieved occupancy, memory throughput.
  2. Bound — compute the theoretical best for this shape (roofline) and the realistic best (SOL minus known taxes).
  3. Hypothesize — name the single bottleneck (memory BW, MMA throughput, occupancy, launch overhead, branch divergence).
  4. Change one thing — adjust tile size or swizzle or pipeline depth. Never two at once.
  5. Re-measure — if the bottleneck moved, repeat; if it didn't, your hypothesis was wrong.

18.2SOL & OAE Analysis

Two numbers Nsight Compute computes for you

[A18.2.1]

Speed-of-Light Percentages

sol

Nsight Compute reports SOL for compute, memory, and L2 throughput. They are percentages of the architectural peak achieved by your kernel over the time it actually ran. Interpretation:

  • SOL Memory > 80% → kernel is memory-bound at near-peak. Move math closer to the data or change algorithm.
  • SOL Compute > 80% → kernel is compute-bound at near-peak. Pick a better instruction (Tensor Core, FMA, sparse).
  • Both < 40% → you are stalled on something else (latency, scheduler, occupancy). Look at warp-state statistics.
[A18.2.2]

OAE — Occupancy-Adjusted Efficiency

oae

A kernel at 25% occupancy can still hit 80% SOL if it issues enough instruction-level parallelism per thread. OAE = SOL / (theoretical occupancy / 100). High OAE despite low occupancy means your kernel is doing ILP well; you don't need more threads. Low OAE despite high occupancy means each thread is stalled and adding more threads is the wrong answer.

18.3Autotuning Frameworks

Let the search find the tile size

[A18.3.1]

Search Spaces You Will Define

autotuning

Almost every GPU kernel has 4–10 knobs that interact non-linearly. Hand-picking the right combination is impractical. Express them as a Cartesian product, prune known-bad combos, evaluate the rest:

  • Threadblock tile (BM, BN, BK) — typically 8–24 valid combos.
  • Warp tile (WM, WN) — 2–6 valid sub-divisions.
  • Pipeline stages — 2, 3, 4.
  • Vectorization (128-bit vs 64-bit loads).
  • Split-K factor (1, 2, 4, 8).

Tools: Triton's @triton.autotune, CUTLASS Profiler, NVIDIA Kernel Generator, OpenAI's kbench. All produce a JSON or YAML pick-list keyed by problem size.

18.4Sensitivity Analysis

Find out which knobs actually matter

[A18.4.1]

Local Perturbations

sensitivity

Pick a best-known config. For each knob, perturb by ±1 step and re-measure. The knobs whose perturbations change runtime by > 5% are your load-bearing knobs; the rest are noise. Future tuning effort should concentrate on the load-bearing ones.

This protects you from over-tuning a flat region of the search space and helps explain to teammates which choices matter.

18.5Recording & Reproducing Wins

Lab notebook discipline

[A18.5.1]

The Per-Experiment Card

documentation

  • Date, git SHA, driver version, GPU model.
  • Exact kernel parameters and tile sizes.
  • Compile flags (nvcc -V, --ptxas-options).
