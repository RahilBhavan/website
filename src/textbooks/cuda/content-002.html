0.2How Numbers Live in Hardware

From IEEE 754 to FP8: every format you will meet

Why this section exists. Every CUDA program is, at its core, a function that loads numbers, does some arithmetic on them, and stores numbers back. The width of those numbers — 32 bits or 16 bits or 8 bits — sets your memory bandwidth, your tensor-core throughput, your numerical accuracy budget, and whether the kernel even fits in registers. You cannot reason about a kernel without first knowing what its operands physically are.
[[A0.2.1]]

Positional binary encoding — the floor of the stack

representation

A binary integer is just a sum of powers of two with coefficients in {0, 1}. The number 1011 means 1·2³ + 0·2² + 1·2¹ + 1·2⁰ = 11. Every other format on this page — signed integers, fixed-point, floating-point — is a deliberate encoding on top of this primitive, trading bits between three things: the range it can express, the resolution within that range, and how cheap the arithmetic circuits are.

Two's-complement signed integers (used by int32_t, int8_t, the GPU's integer ALU) are the simplest such trade: the top bit is the sign, but the value is encoded so that the same addition circuit works for signed and unsigned. That circuit reuse is why GPUs and CPUs both default to two's-complement — not because mathematicians liked it.

IEEE 754 — scientific notation for circuits

representation

IEEE 754 expresses a real number as (−1)s · 1.mantissa · 2exponent − bias. Three fields, all integers: a sign bit, a biased exponent, and a fractional mantissa with an implicit leading 1 (the "hidden bit"). The bias keeps the exponent unsigned in hardware so a single compare-and-subtract aligns two numbers' exponents before adding their mantissas. Every floating-point format you will see is just a re-budgeting of bits across (sign, exponent, mantissa).

FP32 (binary32) — the unit of GPU compute, until it isn't

format

32 bits, 1 sign / 8 exponent / 23 mantissa, ~7 decimal digits of precision, dynamic range ≈ 10±38. On NVIDIA hardware FP32 is the "natural" CUDA core width: every regular ALU operation issued by an SM executes at FP32 rate, and FP64 is a small fraction of that rate on consumer GPUs (1:64 on a 3090, 1:2 on a server-class A100). FP32 is what you use when you don't know what you need; it is also the dominant cost when memory bandwidth dominates, because at four bytes per scalar a 4 KB row vector burns one whole L2 sector per 64 elements.

FP16 (binary16, "half") — the deep-learning starter format

format

16 bits, 1 / 5 / 10. Range ≈ 6.1·10−5 to 6.55·104. Half the bytes of FP32, half the memory traffic, and on Tensor Cores (Volta and later) 8× the FLOP rate when used as an MMA input. Its weakness is the narrow 5-bit exponent: activation tensors with values like 1·10−5 or 7·104 sit at the edge of the range and overflow to inf, which is why training pipelines use loss scaling and accumulate matrix products in FP32.

BF16 — FP32's exponent at FP16's size

format

16 bits, 1 / 8 / 7. Same exponent budget as FP32, so the dynamic range matches (≈ 10±38); only the mantissa is sacrificed. The implication for training: BF16 will not overflow on activations that would have killed FP16, at the cost of ~3 decimal digits of precision. Introduced by Google for TPUs, supported by NVIDIA Tensor Cores from Ampere onward.

TF32 — Tensor Float, a 19-bit input format that looks like FP32

format

TF32 is an internal tensor-core format introduced on Ampere. The register is 32 bits, but only 19 of them are actually consumed by the MMA datapath: 1 sign + 8 exponent (FP32's range) + 10 mantissa (FP16's precision). The extra 13 mantissa bits the application passed in are discarded. The trick is that you can feed it ordinary float registers and get an ~8× speedup over CUDA-core FP32 — at the cost of mantissa precision the network often doesn't notice. NVIDIA enables it by default on Ampere when an FP32 GEMM hits cublasGemmEx; you opt out via CUBLAS_PEDANTIC_MATH or by setting CUBLAS_TF32_TENSOR_OP_MATH off.

Common confusion

"My FP32 GEMM on an A100 only matches a CPU FP64 reference to 3 decimal places — is something wrong?" Almost certainly not: cuBLAS silently dispatched a TF32 tensor-core kernel.

FP8 — two formats, both 8 bits, one trade-off

format

Hopper (sm_90) and later support two FP8 formats whose names you must memorize because they are not interchangeable: E4M3 (1 sign / 4 exponent / 3 mantissa, narrower range, finer steps) and E5M2 (1 / 5 / 2, IEEE-like, wider range, coarser steps). The standard recipe in FP8 training: weights and forward activations in E4M3, gradients in E5M2. Both formats deviate from IEEE 754 in subtle ways (no inf in E4M3; special NaN encodings).

Mixed-precision: input format ≠ accumulator format

numerics

A tensor-core D = A·B + C almost never accumulates in its input format. The MMA reads FP16 (or BF16, INT8, FP8) operands, multiplies them, and accumulates the dot products into wider registers — typically FP32. This is what keeps GEMM stable: K-deep sums of small noisy numbers do not lose precision the way they would in pure FP16. When you see "FP16 GEMM" in cuBLAS or CUTLASS it almost always means "FP16 inputs, FP32 accumulator." When the accumulator is also FP16 (the HMMA.1688.F16 SASS variant), expect numerical disasters at K > 256.

If the input fits in fewer bytes than the output, the kernel is mixed-precision. Output precision dominates correctness; input precision dominates speed and bandwidth.

Rounding modes — the silent five

numerics

Floating-point arithmetic has to round after every operation that produces more mantissa than the format can store. IEEE 754 defines five rounding modes: round-to-nearest-ties-to-even (the default everywhere serious), ties-to-away (used in financial software), toward zero (truncation), toward +∞, toward −∞. CUDA exposes them as intrinsics: __fadd_rn / _rz / _ru / _rd. On Tensor Cores the rounding mode is hardwired per format and per generation; you cannot change it from the kernel. Hopper introduced stochastic rounding for FP8 to address a specific training instability: when a small gradient is added many times to a large weight, deterministic rounding loses every increment to the same direction; stochastic rounding turns the bias into noise.

INT8 / INT4 — integer matmul as quantization target

format

Tensor cores can also consume signed/unsigned integers: INT8 since Turing, INT4 since Turing (sm_75) but deprecated for new code on Hopper. The semantics are different from float MMA: the multiply is integer (so two INT8 operands fit in an INT16 product), and the accumulator is INT32. INT8 GEMM throughput is 2× the FP16 tensor-core rate on most NVIDIA parts. The catch is that to use it you have to quantize: pick per-tensor or per-channel scales s, store x_q = round(x / s) as INT8, then dequantize after the MMA with another multiply by s. That quantization is application-level, not hardware-level.

Kahan summation — why long dot-products go bad without compensation

numerics

Summing K floating-point numbers in a naive loop accumulates an error that grows as O(Kε) in the worst case, where ε is the machine epsilon. For a K=4096 FP16 dot product with ε ≈ 9.8·10−4, the bound is ~4 — much larger than the answer for many inputs. Kahan's compensated-summation trick maintains an auxiliary "lost low-order bits" running variable and folds it back in on each step, reducing the bound to O(ε) independent of K. CUDA programmers rarely run Kahan inside the inner GEMM loop because it costs ~3× the FLOPs; instead, they sidestep the problem by using an FP32 accumulator (see [[A0.2.8]]) and, for ultra-stable reductions, by reshaping the algorithm into a pairwise tree (see Ch 7 — reductions).
