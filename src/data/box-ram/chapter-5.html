5.1 Define success before changing a setting

A future experiment should answer one question: does a specified policy improve the work Rahil actually needs to do, at an acceptable cost to background progress?

Select a primary outcome before looking at results. Examples include the delay when returning to an idle browser, the worst reproducible freeze during an admitted build, or request-to-result time for a particular project. Then specify secondary outcomes and failure conditions.

A proposed decision rule is: accept a change only if it repeatedly improves the chosen latency problem, preserves correct job results and control-service survival, and has an explicitly acceptable queue/execution cost. This guide does not invent a user-approved latency budget or allowable build slowdown. Agree on those costs when a real trade-off appears. Basic correctness and unexpected-kill failures should not be traded away for a nicer average.

If the baseline does not reproduce a problem, an experiment can still characterize capacity, but it should not be described as fixing an observed stall.

5.2 Freeze a representative workload

Choose one actual build with a known successful result, toolchain and source revision. Keep its input data and output verification stable. Use disk-backed task scratch, not RAM-backed /tmp, for substantial dependency trees and build output.

Separate these phases:

  1. Queue admission.
  2. Dependency preparation, if required.
  3. Build execution.
  4. Correctness checks.
  5. Return to previously idle applications.

This separation prevents a dependency download from masquerading as compiler time and prevents a queued command from masquerading as measured load. If network access is part of the real task, report it separately rather than pretending it is controlled.

Record whether the run is warm or cold. Do not indiscriminately purge host caches to manufacture a cold trial. Prefer an isolated input/output directory and document the cache state you can actually control. A warm incremental build and a clean build answer different questions; both may matter.

Record concurrent work and versions. A busy shared host cannot always produce a clean laboratory comparison. That is a reason to expose confounders and repeat matched trials, not to stop other people's jobs without authority.

5.3 Establish baseline and treatment windows

Collect a comparable no-new-build window, then a window overlapping confirmed build execution. Keep the probe, duration and user activity consistent. The current display-off request remains authoritative: keep the screen off unless the user later chooses a visible-interaction trial.

For an actual policy comparison, use at least three alternating matched pairs as an initial local protocol. This is a proposed starting design, not a power calculation or a guarantee of significance. Alternate the order where practical so warmer caches or background drift do not always favor the treatment.

A useful series might be baseline, treatment, treatment, baseline, baseline, treatment. Preserve each raw result. Do not repeatedly rerun only unfavorable observations until the average becomes attractive. If a run is invalidated by a documented external event, retain it and explain exclusion before computing a replacement result.

Continue the observation after the build. Reopen the same previously idle work when permitted. A policy that improves active-build latency but makes the next interaction much worse may simply move the cost outside the original measurement window.

5.4 Capture the minimum useful measurements

Keep the measurement burden proportionate. Start with timestamps, raw compositor replies, probe wake-up lateness, host and job pressure deltas, job peak memory, swap use, exit status and correctness. Add detailed counters only when they distinguish competing causes.

For suspected reclaim problems, useful additions include reclaim events, major faults, working-set refaults, compaction activity and swap-in/out. For a suspected CPU problem, collect per-group scheduling pressure and actual process placement. For graphics symptoms, use a presentation-aware method instead of interpreting socket replies as frames.

For each trial, preserve:

  • Exact workload revision, command identity, tool versions and source/build directory.
  • Queue request, admission, execution start/end and observation interval.
  • Treatment value, prior value, owning scope and rollback condition.
  • Raw latency samples, error count, empirical percentiles and maximum.
  • Resource counters with units, scope and interval.
  • Correctness result, killed units and any unexpected failure.
  • Concurrent-work changes, cache state and other confounders.

Do not save credentials in full command arguments or logs. The existing receipt design intentionally records command identity without keeping unrestricted argv text.

5.5 Evaluate candidates in an informative order

Candidate A: coverage and identity consistency

First establish whether the workloads causing pressure use the real gate and whether project aliases split accounting. If the relevant build bypasses coordination, adjusting the gate's limit may have little effect on it.

This is often a better first engineering question than changing kernel policy. It tests whether the intended control reaches the work. Preserve required checks and the current job-preserving runner procedures while improving entry points.

Candidate B: classify finite jobs versus long-lived services

The November 10 build could not get a slot within two minutes. Investigate whether the running reservations represent genuine finite heavy work and whether surviving descendants legitimately retain their leases.

If a service was mistakenly launched as a finite heavy job, repair the entry-point classification for future launches. Do not weaken lease safety just to clear a queue. The reservation protects against a real resource overlap; removal requires understanding who still owns the work.

Candidate C: one versus two admissions

Two slots are a current user-selected operating setting, not a measured safe capacity for every job mix. A future comparison should report combined job completion, queue wait and responsiveness. One job might preserve headroom but cause excessive waits; two may improve throughput or merely create interference.

Do not infer the answer from the current timeout alone. That observation contains no measurement of how the same jobs would complete under the other setting. A fair comparison needs the same relevant work and must preserve active job ownership while changing only future admission.

Candidate D: a measured per-project soft threshold

Use receipts to understand a project's peak distribution and bursts before proposing a threshold. An empty memory_high map is currently honest: there is no selected production value.

If a candidate is tested, begin with a disposable job scope, retain headroom, verify correctness and observe the reuse phase. A drop in resident memory alone is insufficient. The threshold may simply make the build spend more time reclaiming. Avoid simultaneously changing concurrency, protection and compression so the outcome remains interpretable.

Candidate E: effective interactive protection

If evidence shows the control server or desktop losing useful state during heavy work, inspect the entire ancestry. A large child declaration is not proof of equally large effective protection. Any ancestor adjustment affects other descendants and has a wider blast radius than a disposable job trial.

A proposed change should name who benefits, who can lose reclaimable capacity, and what measurement will show the result. Do not exempt every agent from recovery: that would undermine the purpose of distinguishing control services from restartable work.

Candidate F: bounded proactive reclaim

Only after the preceding evidence exists should a small, contained reclaim trial be considered. The earlier research proposed 64 MiB as an initial local test request, not a validated production target. It is not a recommendation to install a timer that repeatedly reclaims that amount.

A controller would need a clear managed scope, feedback, a rate budget, backoff, delayed-cost observation and rollback. It would also need to show value beyond the kernel baseline and existing admission policy. Calling a fixed reclaim loop “Senpai” would misrepresent both the research and the local implementation.

Candidate G: alternative compression, DAMON or THP

These are later experiments, selected by evidence rather than novelty. A compression comparison should include CPU cost and resume latency. A topology comparison should distinguish zram from zswap with disk backing. A THP trial should follow evidence implicating allocation/compaction behavior.

DAMON_RECLAIM is intended as selective proactive reclamation under light pressure, with controls for age, rate and activation. It complements ordinary reclaim rather than replacing it. Monitoring first can help establish whether its view of cold memory is useful here. The feature's existence does not establish a benefit for this workload. Kernel DAMON reclaim guide.

5.6 Compare realistic alternatives fairly

No cooperative gate: less explicit queueing, but no coordination of participating heavy starts. This is attractive only if measured interference is acceptable and some other mechanism provides a suitable budget. The earlier pressure incident makes removing coordination a poor unsupported first move.

Only hard job caps: clearer containment, but a badly chosen boundary can terminate correct work. Caps need a recovery plan and a measured basis. A per-job limit also does not automatically provide a host aggregate budget.

Only nicer CPU scheduling: potentially useful if CPU contention is the cause, but it does not address every memory or I/O failure. Verify the implicated resource before treating priority as a general cure.

More compressed capacity: can hold more suitable inactive data, but cannot make unlimited active demand fit. The existing logical zram size is not a promise of usable additional RAM.

More physical RAM or another host: plausible if measured working demand repeatedly exceeds a reasonable local budget. This guide supplies no purchasing recommendation or expected hardware gain. Establish demand, responsiveness and queue costs first, then compare the cost of hardware with the cost of waiting or moving work.

The layered policy is the best-supported starting architecture among these choices for the current evidence. Its exact configuration remains an experimentable engineering decision.

5.7 Stop conditions and an honest recommendation

Stop a trial on an unexpected kill, incorrect result, severe sustained stalls or an explicit user interruption. Restore only the owned experimental setting and preserve diagnostic evidence. Do not restart shared control services merely to complete a benchmark.

If a result is smaller than ordinary run-to-run variability, call it inconclusive. If responsiveness improves while total completion worsens, report both and decide whether that trade-off is acceptable. If nothing improves, retaining the baseline is a valid result.

For BOX today, the recommended next step is a properly timed observation around an admitted representative build. The display-off control path currently provides no demonstrated stall to tune. Fair queue participation, trustworthy job boundaries and transparent completion costs are more useful than claiming that the current RAM numbers are already optimal.
