4. Newer / less-common precisions

INT8 and FP8 cuBLAS paths are newer and less comprehensively tuned across shapes than the FP16 path. INT8 INT4 quantization for inference is a particularly active area where custom kernels routinely beat cuBLAS — see e.g. the techniques used by tinygrad, llama.cpp's CUDA backend, and various INT4 inference papers.

Recommended target for this project

A concrete, defensible target

Shape: M = N = K = 4096, FP16 inputs with FP32 accumulate.
Hardware: RTX 3090 (sm_86), GPU clocks locked.
Baseline: cuBLAS via cublasGemmEx.
Win condition: > 100% of cuBLAS, sustained across >500 iterations, verified by Nsight Compute and bit-identical (within fp16 tolerance) output.

This shape is large enough that the workload is firmly compute-bound (intensity ~1365 vs ridge ~152, see §1.6), small enough to fit in 24 GB, exactly square so cuBLAS picks a well-tuned kernel — and yet community results have repeatedly shown that hand-tuned mma.sync + cp.async kernels can edge past it by a few percent on Ampere consumer parts. A defensible, reproducible, satisfying target.

What each step actually changed in Nsight Compute

  • K1 → K2 (Coalescing). Sectors / Request drops from ~16 to 1. DRAM bandwidth utilization roughly doubles.
  • K2 → K3 (SMEM tiling). DRAM bytes per kernel drop by ~32×; L1 hit rate skyrockets; SM throughput begins to be a meaningful share of time.
  • K3 → K4 (Register tiling). SMEM Wavefronts / Request drops; the short_scoreboard stall reason — caused by SMEM dependency wait — shrinks.
  • K4 → K5 (Vectorization). Total instructions issued drops by ~3×. The "Issue Active" SOL metric goes up.
  • K5 → K6 (Tensor Cores). HMMA SASS instructions appear; the TENSOR pipe shows up in Compute Workload Analysis at 30–50%. The FFMA / HFMA2 pipes go quiet.
  • K6 → K7 (mma.sync). The mix of LDS / HMMA shifts: LDS becomes LDSM (ldmatrix); the lanes-per-MMA arithmetic is now optimal.
  • K7 → K8 (cp.async). The barrier (BAR) count per inner loop drops; long_scoreboard stalls fall; "Issue Active" climbs into the high 80s.

5.4Proving the Win: The Benchmark Protocol

If a stranger cannot reproduce your number, it does not exist

The credibility of a "I beat cuBLAS" claim is determined entirely by the protocol you used to measure it. The following is the minimum bar for a reproducible result.

1. Lock the GPU clocks

Without locking, the boost clock varies with temperature and silicon lottery. Two runs five minutes apart can differ by 8%. Lock to a stable value:

# Need: sudo, NVIDIA driver with persistence mode on.
sudo nvidia-smi -pm 1                       # persistence mode

# Query clock ranges:
nvidia-smi -q -d SUPPORTED_CLOCKS | head -40

# Lock SM clock to a value within the supported range.
# 1695 MHz is the RTX 3090 boost-clock spec; 1395 MHz is base.
# Pick a value the silicon can hold under sustained load.
sudo nvidia-smi -lgc 1695                   # lock graphics (SM) clock

# Optional: lock memory clock.
sudo nvidia-smi -lmc 9501                   # GDDR6X mem clock

# After benchmarking, reset:
sudo nvidia-smi -rgc                        # reset graphics clock
sudo nvidia-smi -rmc                        # reset memory clock

State the locked clock in your published report. "RTX 3090, SM clock locked to 1695 MHz, memory clock locked to 9501 MHz" is the level of precision required.

2. Warm up and timing protocol

  • 10 warmup iterations, results discarded.
  • 500 timed iterations, report mean and stddev in milliseconds.
  • Variance < 1% of the mean. If not, raise iteration count or fix a clock instability.
  • Each iteration must be independent: the same input, the same output buffer, no result carried between iterations.

3. FLOP counting

Use the standard convention: a GEMM of (M, N, K) does 2·M·N·K FLOPs — one multiply and one add per inner-loop iteration. Do not count fused biases or activations in the headline FLOP number unless you are honest about it.

TFLOPS = 2 · M · N · K / (mean_ms · 10⁹)

4. Correctness

Compare the kernel's output against a trusted reference (cuBLAS or a CPU implementation) within a precision-appropriate tolerance. FP16 GEMM accumulating to FP32 typically agrees to ~1e-3 relative error on most elements; outliers up to ~1e-2 on long reductions are normal. Use the verify() helper from §2.7. If correctness fails, the benchmark is meaningless.

5. cuBLAS baseline — the apples-to-apples call

#include <cublas_v2.h>

cublasHandle_t handle;
cublasCreate(&handle);

// IMPORTANT: cuBLAS treats matrices as COLUMN-MAJOR. To compute the
// row-major product C = A * B, call as gemm(B^T, A^T) -> C^T,
// or pass transA = T and transB = T appropriately. The shape M,N,K
// stays the same; the leading dims differ.
// IMPORTANT: cublasGemmEx with CUBLAS_COMPUTE_32F expects the alpha/beta
// scalars to be in the COMPUTE precision (FP32), not the input precision.
const float alpha = 1.0f;
const float beta  = 0.0f;

cublasGemmEx(
    handle,
    CUBLAS_OP_N, CUBLAS_OP_N,         // no transpose
    N, M, K,                          // shapes (note swap for row-major view)
    &alpha,
    d_B, CUDA_R_16F, N,               // B and its leading dim
    d_A, CUDA_R_16F, K,               // A and its leading dim
    &beta,
    d_C, CUDA_R_16F, N,               // C and its leading dim
    CUBLAS_COMPUTE_32F,               // FP32 accumulate
    CUBLAS_GEMM_DEFAULT_TENSOR_OP);   // tensor cores allowed

// Time the same way as your custom kernel (Listing 2.7-A).

7. The benchmark harness, end to end

// Pseudocode shape — wire to your existing kernels.
struct KernelEntry {
    const char* name;
    std::function<void(half* dA, half* dB, half* dC, int, int, int)> launch;
};

void run_suite(int M, int N, int K) {
    // Allocate device buffers, fill with random data, allocate result.
    // Allocate a reference buffer and compute cuBLAS once for verification.

    std::vector<KernelEntry> kernels = {
        {"cuBLAS",             [&](auto a, auto b, auto c, int m, int n, int k){ cublasLaunch(a, b, c, m, n, k); }},
        {"gemmNaive",          [&](auto a, auto b, auto c, int m, int n, int k){ gemmNaive<<<...>>>(...); }},
        {"gemmCoalesced",      ... },
        {"gemmTiled",          ... },
        {"gemmReg",            ... },
        {"gemmVec",            ... },
        {"gemmWmma",           ... },
        {"gemmMma",            ... },
        {"gemmMmaCpAsync",     ... },
    };

    long long flops = 2LL * M * N * K;

    printf("Shape: M=%d N=%d K=%d  FP16->FP32\n", M, N, K);
    printf("%-22s | %-16s | %8s | %9s\n", "Kernel", "Time (ms)", "TFLOPS", "% cuBLAS");
    printf("---------------------- | ---------------- | -------- | ---------\n");

    double cublas_tflops = 0.0;
    for (auto& k : kernels) {
        // Verify correctness ONCE (skip naive if you're impatient — it's slow).
        k.launch(d_A, d_B, d_C, M, N, K);
        cudaDeviceSynchronize();
        bool ok = verifyAgainst(d_C, d_ref, M*N, /*rtol=*/1e-2f);
        if (!ok) { printf("%-22s | INCORRECT — skipping\n", k.name); continue; }

        auto r = benchmarkKernel([&]() {
            k.launch(d_A, d_B, d_C, M, N, K);
        }, flops);

        if (strcmp(k.name, "cuBLAS") == 0) cublas_tflops = r.gflops / 1000.0;
        double pct = (r.gflops / 1000.0) / cublas_tflops * 100.0;
        printf("%-22s | %7.3f ± %5.3f | %8.1f | %8.1f %%\n",
               k.name, r.mean_ms, r.stddev_ms, r.gflops / 1000.0, pct);
    }
}
