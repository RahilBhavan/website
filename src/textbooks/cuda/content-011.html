Atomic-note deep dive — §1.5

[[A1.5.1]]

TLP vs ILP — the two flavors of parallelism your kernel exposes

execution

Thread-Level Parallelism (TLP) is what occupancy measures: more resident warps means the scheduler has more pools to pick from when the current warp stalls. Instruction-Level Parallelism (ILP) is what each warp exposes through independent operations the scheduler can keep in flight. A high-occupancy kernel with low ILP needs DRAM to be saturated by lots of small threads; a low-occupancy kernel with high ILP needs each thread to keep dozens of FMAs in flight. Modern GEMM kernels use both: 4–8 warps per SM and 4–8 independent register accumulators per thread, multiplying out to ~32 in-flight FMAs per scheduler.

[[A1.5.2]]

The register-budget trap — why "use more registers" can lose

execution

An SM has a fixed register file (65,536 32-bit registers on Ampere). If each thread uses R registers and a block has B threads, the SM can host at most 65536 / (R·B) blocks. Past a register budget the kernel spills: the compiler stores excess live values to "local memory," which lives in L1 / L2 / DRAM. A spill costs orders of magnitude more than the register access it replaced. Diagnose with --ptxas-options=-v (look for "stack frame: N bytes spill stores") or with NCU's source view (look for STL/LDL instructions). The fix is one of: lower --maxrregcount, set __launch_bounds__, restructure to shorten live ranges, or accept lower occupancy if the ILP wins.

1.6The Roofline Model

A single chart that classifies every kernel

The Roofline Model was introduced by Williams, Waterman, and Patterson at Berkeley in 2008 and has since become the standard one-page summary for kernel performance.[8] It plots achievable performance against a single number — arithmetic intensity — and bounds every kernel above by two ceilings: peak compute and peak memory bandwidth. Whichever ceiling you hit first is your bottleneck.

Arithmetic intensity

I = FLOPs executed / bytes moved from DRAM

Units: FLOP/byte. High intensity means lots of compute per byte of DRAM traffic (good for compute-bound work). Low intensity means lots of DRAM traffic per FLOP (memory-bound). Two kernels with the same FLOP count can have radically different intensity depending on data reuse.

The two ceilings

Performance P in FLOPS for a kernel with intensity I running on a machine with peak compute C and peak DRAM bandwidth B is bounded by:

P ≤ min(C, I · B)

When you plot this with I on a log-scale x-axis and P on a log-scale y-axis, you get a horizontal "ceiling" of height C and a diagonal of slope B that intersects at the ridge point, I* = C / B. Kernels left of the ridge are memory-bound; kernels right of it are compute-bound.

Ridge point for the RTX 3090 (FP16 Tensor Core, dense)

C = 142,000 GFLOPS (NVIDIA-published peak FP16-TC w/ FP32 acc, no sparsity) B = 936 GB/s (GDDR6X, 384-bit, 19.5 Gbps) I* = C / B = 142000 / 936 ≈ 151.7 FLOP/byte

Arithmetic intensity of a 4096³ FP16 GEMM

FLOPs: 2·M·N·K = 2·4096³ ≈ 1.37 × 1011. Bytes (load each input once, write output once, FP16 = 2 bytes): 2·(M·K + K·N + M·N) ≈ 1.01 × 108.

Ialgorithmic = 2·4096³ / [2·(4096·4096 · 3)] = 137,438,953,472 / 100,663,296 ≈ 1365 FLOP/byte
Algorithmic vs realized intensity — read this twice

The 1365 FLOP/byte above is the algorithmic upper bound — it assumes each input and output element is read from DRAM exactly once. It is what a perfectly tiled kernel can reach.

A naive kernel that re-reads A from DRAM for every output column achieves a realized intensity of roughly 1 FLOP/byte — and that is exactly why naive kernels sit far below the roofline. Tiling chases the upper bound by reusing data through shared memory and registers. Always ask which number you mean.

1365 ≫ 152, so a 4096³ FP16 GEMM is massively compute-bound on the RTX 3090 — provided you implement it well enough to realize the available reuse. This is why GEMM should be Tensor-Core throughput limited, not bandwidth limited, and why cuBLAS-class kernels run at > 90% of FP16-TC peak on large square shapes.

Atomic-note deep dive — §1.6

[[A1.6.1]]

Arithmetic intensity, formally

performance

For a kernel that performs F floating-point operations while moving B bytes between DRAM and the chip, the arithmetic intensity is I = F / B, measured in FLOPs/byte. There are two flavors to be careful about: operational intensity uses the bytes actually transferred (depends on cache behavior and the access pattern), while algorithmic intensity uses the minimum bytes the math requires. Roofline plots usually mean the operational one; the algorithmic one is a theoretical upper bound on it.

For a tiled GEMM with tile size T, the operational intensity rises linearly with T because each tile reused for T inner-loop iterations amortizes its load over T FLOPs per byte. That linear knob is why "make tiles bigger" almost always helps — until you exhaust register or shared-memory budget.

[[A1.6.2]]

The ridge point — single number that classifies your kernel

performance

The ridge point is the intensity I* where the bandwidth roof equals the compute roof: I* = Ppeak / β, where Ppeak is peak FLOP/s and β is peak DRAM bandwidth. Kernels with I < I* are memory-bound; with I > I* they are compute-bound. For an A100 in FP16 with 312 TFLOPs and 1555 GB/s, I* ≈ 200 FLOPs/byte. For the same A100 in FP32 (non-tensor-core) with 19.5 TFLOPs, I* ≈ 12 FLOPs/byte. The ridge is much higher when you turn on tensor cores; that fact alone explains why "tensor cores didn't help" almost always means "the kernel was still memory-bound."
