Double-buffered inner loop, sketched

// Two SMEM buffers, ping-pong.
__shared__ half  As[2][BM][BK];
__shared__ half  Bs[2][BK][BN];

int load = 0;     // buffer being loaded
int comp = 1;     // buffer being computed on
bool first = true;

// Prime the pipeline: issue load for the first phase.
issueLoadsInto(As[load], Bs[load], /*phase=*/0);
cp_async_commit();

for (int p = 0; p < nPhases; ++p) {
    if (p + 1 < nPhases) {
        // Issue the NEXT phase's load while we compute on this phase.
        std::swap(load, comp);                     // ping-pong roles
        issueLoadsInto(As[load], Bs[load], p + 1);
        cp_async_commit();
    }

    // Wait until the buffer we want to COMPUTE on is fully loaded.
    cp_async_wait_group<1>();   // keep one in-flight load (the next phase)
    __syncthreads();

    // Tensor-core compute using mma.sync, consuming As[comp]/Bs[comp].
    runMmaLoop(As[comp], Bs[comp], /*accumulator=*/regC);

    // No second barrier needed here as long as the next phase will
    // load into a DIFFERENT buffer (the swapped one).
}

// Drain the pipeline.
cp_async_wait_all();
Figure 3.5 — Interactive
Without vs with cp.async pipelining
In the bottom timeline, the next phase's load is in flight while the current phase's mma runs. If the load is shorter than the MMA, the load is fully hidden. CUTLASS uses 3–5 stage pipelines on Ampere for even tighter overlap; the trade-off is more shared memory per block.
Why this is the last big lever before peak
On Ampere consumer parts, well-tuned mma.sync kernels without async pipelining typically land around 80–85% of FP16-TC peak. Adding 2- or 3-stage cp.async pipelining pushes that into the low-90% range and lets the kernel cross the cuBLAS line on selected shapes.

Format choice as a first-class optimization knob
Goal. Make the precision/throughput trade-off mechanical instead of guess-and-test. Each format is one node in §0.2; this section says exactly when each one is appropriate on a Tensor Core and what happens at the SASS level when you pick.
[[A3.6.1]]

Accumulator policy — the silent half of every MMA

numerics

Every Tensor Core MMA has two precisions you can pick independently: the operand precision (A and B) and the accumulator precision (C). The hardware allows several combinations per generation; the most useful ones on Ampere are FP16 × FP16 → FP32 and BF16 × BF16 → FP32. The FP16 → FP16 variant exists but is dangerous for K > 256: cumulative round-off blows up. Always default to FP32 accumulators unless you have proved otherwise on real data.

TF32 vs FP32 — when "FP32" isn't FP32

numerics

From CUDA 11 on Ampere, cublasSgemm on default math mode actually runs TF32 tensor cores internally — a 10-bit-mantissa input format (see [[A0.2.6]]). You get 8× throughput vs CUDA-core FP32 at the cost of mantissa precision. To force "real" FP32 numerics call cublasSetMathMode(handle, CUBLAS_PEDANTIC_MATH) or set the math mode to CUBLAS_TF32_TENSOR_OP_MATH_DISALLOW. The throughput-vs-accuracy budget for TF32 is the single biggest "why does my reference disagree" gotcha in cuBLAS.

Sparse Tensor Cores — 2:4 structured sparsity

numerics

Ampere introduced a 2:4 structured-sparsity feature on Tensor Cores: in every contiguous group of 4 elements of A, exactly 2 must be zero. Storing this as a 50%-dense matrix with a 2-bit-per-quad selection metadata cuts memory traffic in half and doubles MMA throughput. The catch is the sparsity pattern is structured, not arbitrary; pruning a dense network to 2:4 typically costs a few percent accuracy and requires fine-tuning. The PTX is mma.sp.sync. Used by NVIDIA's structured-sparse Transformer kernels in cuSPARSELt.

Loss scaling — keeping FP16 from underflowing

numerics

FP16's smallest normal positive value is ≈ 6·10−5. Gradients in deep nets routinely land below that and underflow to zero — training silently stalls. The fix is loss scaling: multiply the loss by a large constant (1024–65536), do the backward in FP16, then divide gradients by the same constant before the optimizer step. The intermediate exponents climb back into the FP16 normal range. BF16 has FP32's exponent and does not need loss scaling. PyTorch's autocast and CUDA's NVIDIA::amp automate this; if you write kernels at this level you almost never have to think about it.
