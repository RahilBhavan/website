1.3Threads, Warps, Blocks, and Grids

The execution hierarchy you write code against

CUDA exposes four nested concepts. They map onto hardware in very specific ways. Get the mapping wrong and your kernel will be slow for reasons that are not obvious from the source code.

Thread

A thread is the atomic unit of execution. One thread runs one instance of your kernel function from start to finish. It has its own program counter, its own slice of the register file, and its own values of threadIdx and blockIdx. You will routinely launch tens of millions of threads.

Warp

A warp is a group of 32 threads that the hardware schedules and executes together. This is the most important number in CUDA. Warp size has been 32 on every NVIDIA GPU shipped to date. The 32 threads in a warp share a single instruction stream — when the warp scheduler issues an instruction, all 32 lanes execute it on their own data. NVIDIA calls this SIMT (Single Instruction, Multiple Thread), which is essentially SIMD with a per-lane predicate and a per-lane register file.

You do not control warps directly. You set a block size, and the hardware partitions the block into warps of 32 threads in linear order: threads 0–31 are warp 0, 32–63 are warp 1, and so on (using row-major order over the multi-dimensional threadIdx).

Warp divergence

Because all 32 threads in a warp share a program counter, an if/else that splits the warp is expensive. The hardware serializes the two paths: it runs the if branch with the else threads masked off, then runs the else branch with the if threads masked off. Both branches contribute to runtime; only the active threads contribute to useful work.

The rule that follows: keep all 32 threads of a warp on the same execution path. Branches that depend on threadIdx.x / 32 (i.e. on the warp ID) are free; branches that depend on threadIdx.x % 32 are the worst case.

Thread block

A thread block is a programmer-defined group of up to 1024 threads. The hardware promises three things about a block:

  1. All threads in the block run on the same SM. They never migrate.
  2. They share a single allocation of that SM's shared memory.
  3. They can synchronize with __syncthreads() — every thread in the block must reach the barrier before any thread can proceed past it.

Block size is the lever you use to trade off occupancy, shared-memory tile size, and per-thread register budget. Common values are 128, 256, or 512 threads per block (i.e. 4, 8, or 16 warps). 1024 is the hardware maximum.

Grid

The grid is the collection of all thread blocks launched by one kernel call. The grid can be 1D, 2D, or 3D. The runtime distributes blocks across SMs in an order you do not control. You cannot assume any ordering of block execution and you cannot synchronize between blocks within a kernel launch (with the exception of cooperative-grid kernels and grid-wide barriers introduced later in CUDA, which are out of scope here).

Launch syntax

// Launch 256 blocks of 128 threads each. Total: 32,768 threads.
myKernel<<<256, 128>>>(args...);

// 2D launch for a matmul. One block computes one TILE x TILE
// output tile. Each thread in the block computes one element of that tile.
const int TILE = 32;
dim3 grid((N + TILE - 1) / TILE, (M + TILE - 1) / TILE);
dim3 block(TILE, TILE);                       // 1024 threads = 32 warps
matmulKernel<<<grid, block>>>(A, B, C, M, N, K);

// Inside the kernel:
//   threadIdx.x in [0, TILE)
//   threadIdx.y in [0, TILE)
//   blockIdx.x  in [0, gridDim.x)
//   blockIdx.y  in [0, gridDim.y)
//   blockDim.{x,y} == TILE
//   gridDim.{x,y} == ceil(N/TILE), ceil(M/TILE)
//
// Global thread coordinates for the (i,j) output element:
//   int j = blockIdx.x * blockDim.x + threadIdx.x;   // col
//   int i = blockIdx.y * blockDim.y + threadIdx.y;   // row

Rule of thumb
Pick a block size that is a multiple of 32. Otherwise the last warp of every block has dead lanes from the start, and you waste hardware on every cycle. 128 or 256 is almost always the right default before any tuning.

[[A1.3.1]]

SIMT in practice — one program counter, 32 lanes

execution

Pre-Volta, a warp shared a single program counter across all 32 lanes; a divergent branch serialized the two sides under a hardware mask. Volta (sm_70) introduced independent thread scheduling: each lane has its own PC and call stack, and the scheduler tracks reconvergence explicitly. The programmer-visible consequence is that you can no longer assume warp-lockstep behavior at byte-level granularity — you must call __syncwarp() when one branch of a warp publishes a value the other branch reads. This is the silent cause of "it works on my Pascal but breaks on my Ampere" bugs.

Warp scheduler — picks one ready warp per cycle per partition

execution

Each SM sub-partition (4 per Ampere SM) owns a warp scheduler. Every cycle each scheduler examines its pool of resident warps — typically 16 — and picks one warp that has at least one instruction whose operands are all ready, then issues that one instruction to the appropriate functional unit (FP32 ALU, FP64 ALU, Tensor Core, LSU, SFU). Because the scheduler only "fires" when there is a ready warp, the entire latency-hiding game reduces to: keep at least one warp ready per cycle. That single sentence is the unifying explanation for occupancy, ILP, cp.async, double-buffering, and software pipelining.

A warp scheduler does not wait; it idles. Your job is to make sure it never has to.

Warp divergence — the lane-mask tax

execution

When threads in a warp take different branches of a conditional, the hardware executes both paths sequentially with a predicate mask: lanes not on the active path are predicated off (their results are discarded) but they still consume a cycle. Worst case: 32 lanes take 32 different paths, the warp takes 32× longer. Two redemption modes: (1) data-dependent divergence on data sorted ahead of time so warp boundaries align with branch boundaries; (2) predicated short branches the compiler fuses into a single selp instruction. The nvcc diagnostic --ptxas-options=-v tells you when a branch was predicated vs branched.

Kernel launch cost — the constant you cannot amortize away

execution

A <<<grid, block>>> launch costs ≈ 5–20 µs on the host side and ≈ 1–5 µs on the device side. For a kernel that does 100 µs of real work the overhead is invisible; for one that does 2 µs of real work the overhead dominates. Mitigations, in order of preference: batch small kernels into bigger ones; use CUDA Graphs (one record-and-replay per pipeline) to fold launches into a single submission; keep persistent kernels running across iterations. Ch 2 — streams & graphs covers the API.

1.4The Memory Hierarchy

The most important section in this textbook

If you remember one thing from this chapter, remember this: kernel optimization is memory hierarchy management. Compute on GPUs is comparatively cheap; getting data to the compute units is comparatively expensive. The hierarchy below is the entire physical reason your naive kernel is slow and your optimized kernel is fast.
