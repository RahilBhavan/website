2.1 The shared gate controls admission

The entry point is workload_budget.py. Participating heavy builds, full suites and browser batches acquire reservations before running. The state directory is ~/.local/state/host-workload.

At authoring time, the live override is {"max_running": 2}. The source default remains one. The runbook still contains wording about one job, so neither the default nor that sentence describes the live override. This guide does not change it.

The effective admission checks currently require at least 4096 MiB available memory and accept pressure readings up to these ceilings: memory full avg10 5%, I/O full avg10 10%, CPU some avg10 20%. These are initial local operating choices. The gate's comparisons are admission conditions, not guaranteed running-job performance targets.

A new job can be admitted while conditions look healthy and later consume much more memory. The gate does not retroactively pause it when pressure rises. This is why limiting simultaneous admissions helps but cannot provide a complete resource guarantee.

Why job-count limits still help

A simple count is inexpensive and understandable. It limits a source of overlap even before reliable peak estimates exist. It is coarse: two small jobs and two huge jobs consume very different resources. The long-term improvement would be better evidence and resource-aware admission, not assuming that one integer describes all workloads.

A protected queue also makes waiting explicit. That has value compared with silent contention, but waiting remains a cost. A policy must be evaluated from job request to useful completion, not only from execution start.

Fairness and ownership

Current selection favors the least recently served project, then order within that project. New waiters have a compatibility marker allowing extra-slot admission; old in-memory wrappers may retain the earlier single-slot behavior. Source inspection confirms these rules; it does not establish perfect fairness for every process on the host.

Project identifiers are strings. Different spellings of the same repository can fragment its accounting and service history. Normalizing identities is a useful future correctness improvement. It should be tested without discarding live tickets or changing which job owns a reservation.

The lease is held through a kernel file lock inherited by the command. Killing the wrapper does not by itself prove its actual work ended. A live descendant can keep the reservation. This prevents a second job being admitted on the false assumption that resources were released. It also means a long-lived descendant can cause a long wait and must be investigated rather than blindly removed.

Thread defaults are advisory

The wrapper supplies defaults of four Cargo/CMake workers and two workers for several numerical-library environments. Explicit caller values remain in force. An application can also use its own worker settings. These defaults reduce accidental fan-out; they do not impose a universal four-thread cap on every descendant.

2.2 Scopes provide a boundary for observation

The active policy requests placement: scope, record: true, bind: part-of, with an empty memory_high map. workload_scope.py plans a hostjob-<ticket>.scope for a supported new host launch.

A cgroup organizes processes in a resource hierarchy. Its controllers can account for and constrain the group. Ancestor restrictions still apply; a child cannot override a tighter parent. memory.low is best-effort reclaim protection, memory.min is stronger protection, memory.high applies reclaim/throttling pressure and can be exceeded, and memory.max is a hard boundary that can cause cgroup OOM. Protection is constrained by the hierarchy. Kernel cgroup v2 documentation.

Local design consequence: placing a job in its own scope improves attribution. It also makes the job separately eligible for some recovery decisions instead of mixing all its memory with the agent's scope. It does not make the job immortal or ensure that every killer chooses only that job.

The launch planner preserves the caller's user slice when appropriate. Jobs launched from an agent slice therefore remain within that slice's aggregate ceiling. A scope launched from another context can have different ancestry; verify the resulting path instead of assuming that all hostjob units live under the same aggregate agent budget.

Lifecycle and fallback details

PartOf ties an explicit caller-unit stop to the job. A caller that simply exits is a different event; the surviving job can retain its lease. This preserves the distinction between “the owner requested a stop” and “the wrapper process disappeared.”

If the user bus or required placement tools are unavailable, the planner can use inherited placement. Runner containers commonly take that path. If systemd-run cannot execute at all, the wrapper can safely fall back because the command has not started. A nonzero result after systemd-run starts is ambiguous, so the wrapper does not blindly rerun a possibly executed command. This protects against duplicate side effects.

An invalid policy falls back to inherited placement and no recording. Current run behavior does not print all policy-loader warnings. Missing receipts therefore deserve inspection; do not assume absence means zero memory use.

2.3 Kernel reclaim and MGLRU

MGLRU is enabled as 0x0007, covering its main switch and the documented accessed-bit batching components. It organizes reclaim around page access history. The kernel exposes min_ttl_ms as a working-set protection control; if the protected recent set cannot fit, it can drive earlier OOM rather than continued thrashing. BOX currently has TTL zero. Kernel MGLRU guide.

Local recommendation: retain the current baseline until measurements implicate a reclaim problem. Enabling a nonzero TTL would change the failure policy, not simply turn on a free performance feature. The box already has an oomd policy, so overlapping recovery changes should be tested separately.

The practical implication for investigation is to record reuse. A reclaim policy should be judged when the user returns to displaced work, not only while the background job is making progress.

2.4 Compressed swap and the disk fallback

zram is a RAM-backed block device that stores compressed pages. Its logical size is capacity, not a physical reservation. mem_used_total includes the allocated storage and overhead; compressed payload alone understates its footprint. A separate disk swapfile is not automatically zram writeback: zram writeback requires its own backing configuration. Kernel zram guide.

BOX's zram uses zstd and swap priority 100; the disk swapfile has priority 0. The observed compressed tier is therefore preferred over the lower-priority disk swap area. A priority ordering does not guarantee that every future allocation succeeds or that the disk tier is never used. See the local swapon --show output in the state record.

The engineering trade-off is workload-dependent. Compression uses CPU and memory bandwidth. Its value depends on how well the pages compress and how often they must be used again. Disk fallback can provide capacity while still being too slow for pleasant interaction. The existence of swap is a recovery option, not permission to overcommit without measurement.

swappiness=150 is valid on Linux: the range is 0–200 and expresses relative reclaim cost, not the percentage of RAM to swap. Values above 100 can make sense for RAM-backed swap. page-cluster=0 disables swap readahead; other values trade initial access against fetching nearby pages. Neither setting is a universal desktop optimum. Kernel VM sysctl guide.

zswap is disabled. zswap is a compressed cache in front of a backing swap device, with eviction to that backing device. It is a different topology from zram. Turning it on above zram does not by itself create the desired disk-backed compressed tier. Compare topologies separately if evidence justifies it. Kernel zswap guide.

2.5 Containment, protection and recovery are different

T3's aggregate agent slice currently declares approximately 24.54 GiB MemoryHigh and 26.54 GiB MemoryMax. The T3 server requests 3 GiB MemoryLow and has kernel OOM score adjustment −900. It also carries oomd preference avoid, with its cgroup marker observed during the earlier investigation. These are local observations, not values chosen by the cited papers.

The installed systemd manual distinguishes reclaim protection, thresholds, and victim preferences. oomd and the kernel OOM killer are separate actors. An oomd avoid preference is not immunity; a kernel score adjustment is not an oomd exclusion. Effective protection also depends on ancestors. The systemd resource-control reference and oomd reference describe these controls. Their web pages timed out during authoring; the installed manual was inspected locally, alongside the earlier local verification record.

The separation of session.slice from the monitored app subtree matters. It avoids deliberately placing the whole interactive session inside the same recovery domain as ordinary apps. That does not protect the compositor against a global kernel failure, driver stall or arbitrary resource starvation.

2.6 What is deliberately not running

There is no new Senpai controller, no Hermes allocator replacement, and no newly installed DAMON reclaim policy. Project memory_high entries are empty. The gate does not dynamically resize jobs while they run.

THP allocation is currently always with defrag madvise; these are separate controls. THP can reduce translation overhead, while page preparation and compaction introduce costs that deserve workload-specific measurement. A single word from the allocation setting is insufficient diagnosis. Kernel THP guide.

The restraint is useful: it keeps the baseline interpretable. If a targeted experiment later establishes a better setting, record its context and evidence instead of treating complexity itself as progress.
