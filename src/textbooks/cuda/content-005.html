Why today's architecture looks the way it does

The modern GPU did not arrive in one step. Each generation answered the previous generation's bottleneck and is the reason a particular CUDA feature exists. Knowing which generation introduced what makes nvcc error messages, compute-capability flags, and PTX manuals legible. Compute capability — the version number that gates every feature

toolchain

Every NVIDIA GPU has a "compute capability" like sm_80 (A100), sm_86 (RTX 3090), sm_90 (H100). It is a two-digit version number: the first digit is the architecture family (Volta=7, Ampere=8, Hopper=9), the second distinguishes SKUs within it. Compute capability decides three things: (1) which PTX instructions exist, (2) which shared-memory budget and register file size you get, (3) which Tensor Core MMA shapes you can issue. When you compile with nvcc -arch=sm_86 you're asking the compiler to emit SASS for that target; -arch=compute_86 emits PTX that the driver JITs at load time. We will revisit this in §2.x — toolchain.

Why this book targets Ampere (sm_80/sm_86)

scope

Three reasons. (1) It is the sweet spot of availability: an RTX 3090 is the most common high-end consumer card with full FP16 Tensor Cores; A100 is the most common data-center part. (2) It is the first generation with all the modern primitives: cp.async, async barriers, BF16, TF32, sparse Tensor Cores. Everything you learn here applies to Hopper; Hopper adds new primitives but does not remove these. (3) The documentation is mature: every Ampere quirk has by now been written about, profiled, and decoded in public. Hopper has more headroom for novel work but a thinner public corpus.

Throughout the rest of this book "the GPU" means an Ampere SM unless we say otherwise. Hopper-only material is collected in §3.6 and an Ampere/Hopper cross-reference lives in §6.1.

1.1Why GPUs Exist: The Parallelism Imperative

A divergence of design philosophies

A CPU and a GPU both move bits around, but they were built to solve completely different problems. A CPU is a latency-minimizing machine — its job is to get a single thread through a complicated instruction stream as quickly as possible. Out-of-order execution, deep speculation, large branch predictors, multi-megabyte caches, and tightly clocked single-thread pipelines all serve one goal: drive the wall-clock time of one task as low as possible.

A GPU is a throughput-maximizing machine. It does not care that any single thread is slow. It cares that tens of thousands of threads, taken together, finish their work in less time than a CPU could. The chip is therefore organized to keep as many arithmetic units busy as physically possible. Where a CPU spends roughly four-fifths of its silicon area on caches and control logic, a GPU spends roughly four-fifths of its silicon on arithmetic units. The cache is small, the control logic is shared across many lanes, and the pipeline depth per lane is shallow.

The free lunch is over

The shift to GPUs is not a fashion. It is a forced response to physics. Until roughly the mid-2000s, every new CPU generation gave you a faster single thread for free — clock frequencies climbed, transistors got smaller, voltages dropped, and the same code simply ran faster on next year's silicon. This was Dennard scaling. It broke down around 2005–2007 as leakage current and thermal density made further voltage reduction impractical. Herb Sutter's essay The Free Lunch Is Over (Dr. Dobb's, March 2005) named the moment for the software industry.[1]

Since the free lunch ended, performance growth has come almost entirely from parallelism — more cores, wider vector units, specialized accelerators. GPUs are the most aggressive expression of that trend: instead of a few fast cores, thousands of slow ones; instead of speculation, brute parallel coverage; instead of large per-core caches, a small shared on-chip memory that the programmer manages explicitly.
