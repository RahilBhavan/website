Five Rules for Any Memory-Bound Algorithm

design pattern
  1. Block to fit shared memory — any intermediate larger than SMEM should be regenerated, not stored.
  2. Stream-update dependent statistics — running max, running sum, running mean/variance (Welford). These let you avoid the multi-pass version.
  3. Recompute < store on backward pass. The FA backward recomputes the attention matrix from saved (max, sum) statistics instead of storing it.
  4. Producer/consumer specialization on Hopper — partition warps by role so load and math overlap without scheduler luck.
  5. Pick block sizes so the next block fits in L2 — by the time a Q-block finishes its K-loop, the next K-block is already there.

Apply these to softmax, layer norm, RMSNorm, cross-entropy with logit shifts, RoPE, and any "compute a big intermediate, immediately reduce it" pattern.

Chapter 15

Convolution Kernels:
From im2col to Winograd

Learning goal. Convolution is the second pillar of deep-learning compute. It looks like a different problem from GEMM, but every fast GPU implementation either reduces it to a GEMM or trades multiplies for additions via Winograd transforms. By the end you can implement each strategy, predict when each one wins, and read a cuDNN log to know which algorithm the heuristic picked.

15.1What Convolution Is — One More Time

2-D, batched, multi-channel — the shape that matters

[A15.1.1]

The 7-D Convolution

convolution

An ML 2-D convolution has shape parameters (N, C, H, W, K, R, S, U, V, pad):

  • N — batch.
  • C — input channels.
  • H, W — input spatial.
  • K — output channels.
  • R, S — filter spatial.
  • U, V — stride.
  • P, Q — output spatial = ((H + 2·pad − R)/U) + 1.

FLOPs: 2 · N · K · C · R · S · P · Q. For ResNet-50's 3×3 layer at 28×28 with 256 channels and batch 64, that's ~6 GFLOP — small individually, but a network has hundreds of such ops.

15.2im2col + GEMM

The straightforward, memory-hungry reduction to matrix multiply

[A15.2.1]

The Unfolding Trick

im2col

For each output pixel, list the C·R·S input values that contribute to it as a column of a giant matrix X_unf of shape (C·R·S) × (N·P·Q). Then convolution is just

Y = W_flat · X_unf

where W_flat is the filter reshaped to K × (C·R·S). This turns convolution into one giant GEMM. Caltech's Caffe popularized the technique; every modern stack still keeps it as a fallback. Downside: X_unf uses R·S× more memory than X. For 3×3 that's 9× — manageable. For 7×7 it is 49×.

Used by§15.3 Implicit GEMM

15.3Implicit GEMM

The same GEMM, without ever materializing X_unf

[A15.3.1]

Compute the Indexing on the Fly

implicit gemm

Implicit GEMM is the standard cuDNN algorithm. The kernel acts as if it is doing the GEMM Y = W_flat · X_unf, but each GEMM tile load does the im2col index calculation inline, reading directly from the original X tensor. The result: same arithmetic and bandwidth as a dense GEMM of the same logical size, no R·S memory overhead. Trade-off: more address-generation pressure, which Hopper's TMA largely mitigates.

15.4Winograd Minimal Filtering

Trade multiplies for additions in 3×3 kernels

[A15.4.1]

F(2,3) — 2-output Winograd

winograd

The "minimal filtering" form due to Winograd computes a 2×2 output tile from a 4×4 input tile using only 16 element-wise multiplies after a fixed linear transform — versus 36 for the direct 3×3 conv. The 2.25× reduction in multiplies maps directly to a 2.25× peak speedup on FP32, but in practice you get 1.4–1.7× because:

  • The four transform matrices (A, B, G) add memory traffic.
  • Precision degrades — Winograd has higher rounding error than direct conv, so FP16 with Winograd can break.

F(4,3) (4-output Winograd) is even more aggressive but loses accuracy faster. Most production stacks default to F(2,3) for FP32 and skip Winograd entirely for FP16/BF16, using implicit GEMM there instead.

// F(2,3) algorithm: G·g·Gᵀ ⊙ Bᵀ·d·B → Aᵀ · (·) · A = 2×2 output where g is 3×3 filter, d is 4×4 input tile.

15.5FFT and Direct Convolution

The other two paths, and when each wins

[A15.5.1]

FFT Convolution

fft

For large filter sizes (R, S ≥ 11), FFT-based conv (cuFFT + element-wise multiply + inverse FFT) is asymptotically O((H·W)·log(H·W)) versus direct O(H·W·R·S). Wins decisively for non-strided conv with very large kernels. ML rarely has those, so FFT-conv is uncommon in deep nets but standard in scientific/image processing.

[A15.5.2]

Direct Convolution

direct

Skip the GEMM mapping entirely; have each thread block compute a small output tile by sliding the filter directly. Wins when: tiny channels (C, K < 16, so GEMM tiles waste rows), tiny H/W (mobile), or depthwise convs where each output channel reads only one input channel.

15.6Depthwise & Group Convolution

The shape that breaks every GEMM-based plan

[A15.6.1]

Why Depthwise Doesn't im2col

depthwise

Depthwise conv applies one filter per input channel. The "GEMM" you'd build is K=1 wide — degenerate. cuDNN's depthwise kernels are direct: each thread block owns one channel, slides the filter through the output. MobileNet's bottleneck is depthwise conv precisely because the GEMM trick stops paying. Same story for grouped conv with small group size.

Triton & CUTLASS:
The Two Abstractions Above Raw CUDA

Learning goal. Most production kernels are no longer written in raw CUDA C++. Triton (Python-embedded tile-IR JIT) and CUTLASS (header-only C++ template library with CuTe layouts) cover ~90% of the kernel design space at a fraction of the engineering cost. By the end you can read a Triton kernel, walk a CUTLASS GEMM template, and decide which abstraction to reach for given a new problem.
