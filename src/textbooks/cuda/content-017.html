3.2The WMMA API: An Entry Point

High-level Tensor-Core access, since CUDA 9

The WMMA (Warp Matrix Multiply-Accumulate) API is in <mma.h>, namespace nvcuda::wmma. It works at the warp level — every Tensor-Core operation in WMMA is collective across all 32 threads in a warp.

The model is: declare opaque fragment types for the A, B, and accumulator/result matrices; load global or shared memory into a fragment; call mma_sync; store the result fragment back. The fragment's storage is distributed across the warp's registers, but you do not see how — the library hides the layout.

#include <cuda_runtime.h>
#include <mma.h>
using namespace nvcuda;

// Computes a single 16x16 output tile of D = A * B + C, where:
//   A is 16 x 16 (FP16), row-major
//   B is 16 x 16 (FP16), col-major
//   C, D are 16 x 16 (FP32), row-major
// One WARP executes this — 32 threads cooperating.
__global__ void wmmaTileKernel(const half* A, const half* B, float* D,
                               int M, int N, int K)
{
    // Each block is a single warp (32 threads).
    // Compute origin of this warp's tile in the output.
    int tileM = blockIdx.y * 16;
    int tileN = blockIdx.x * 16;

    // Fragments live in registers (distributed across the warp).
    wmma::fragment<wmma::matrix_a, 16, 16, 16, half, wmma::row_major> aFrag;
    wmma::fragment<wmma::matrix_b, 16, 16, 16, half, wmma::col_major> bFrag;
    wmma::fragment<wmma::accumulator, 16, 16, 16, float>             cFrag;

    wmma::fill_fragment(cFrag, 0.0f);

    // K-loop: accumulate over slabs of 16.
    for (int k = 0; k < K; k += 16) {
        const half* aPtr = A + tileM * K + k;            // row-major
        const half* bPtr = B + k * N + tileN;            // col-major-equiv

        wmma::load_matrix_sync(aFrag, aPtr, K);          // leading dim = K
        wmma::load_matrix_sync(bFrag, bPtr, N);          // leading dim = N
        wmma::mma_sync(cFrag, aFrag, bFrag, cFrag);      // D = A*B + C, in place
    }

    // Store result tile.
    float* dPtr = D + tileM * N + tileN;
    wmma::store_matrix_sync(dPtr, cFrag, N, wmma::mem_row_major);
}

// Launch: one warp (32 threads) per 16x16 output tile.
dim3 block(32);
dim3 grid(N / 16, M / 16);
wmmaTileKernel<<<grid, block>>>(d_A, d_B, d_D, M, N, K);

What WMMA buys you, and where it hurts

  • Portable across Volta → Hopper. The same source compiles to wmma.mma on Volta and to mma.sync on Ampere/Hopper.
  • Zero PTX in your source. Easier to read, easier to onboard.
  • BUT the register layout of fragments is hidden. You cannot pipeline loads optimally because you cannot see which thread holds which element. You cannot fuse other warp-level operations with the fragment efficiently. You cannot use the most efficient ldmatrix.sync load pattern without dropping to PTX anyway.

WMMA typically gets you to ~70–80% of cuBLAS for a well-tuned shape. To close the last 15–25%, you drop one level deeper.

3.3PTX and Inline Assembly

The intermediate representation NVIDIA exposes to you

PTX (Parallel Thread Execution) is NVIDIA's virtual instruction set. nvcc compiles your CUDA C++ to PTX, and the driver's JIT compiler (or ptxas ahead-of-time) lowers PTX to SASS, the actual machine code for a specific compute capability. PTX is to CUDA what LLVM IR is to C++: a portable, stable, readable intermediate that the next stage of the compiler turns into hardware-specific code.

You can ask nvcc for the PTX of a kernel with -ptx or for the final SASS with cuobjdump --dump-sass. The PTX ISA reference, maintained by NVIDIA, is the authoritative document for every instruction.[3]

Inline PTX syntax

CUDA C++ supports inline PTX via the asm keyword, identical in spirit to GCC inline asm:

// Pattern: asm( "ptx-template" : outputs : inputs : clobbers );

// Trivial example: 32-bit integer add.
int a = 5, b = 3, c;
asm volatile("add.s32 %0, %1, %2;"
             : "=r"(c)              // output 0: 32-bit reg
             : "r"(a), "r"(b));     // input 0,1: 32-bit regs
// c == 8

// Constraints (most common):
//   "r"  -> .u32/.s32  (32-bit int register)
//   "l"  -> .u64/.s64  (64-bit int register)
//   "f"  -> .f32       (32-bit float register)
//   "d"  -> .f64       (64-bit float register)
//   "h"  -> .b16       (16-bit, e.g. half storage)
//   prefix "=" means write-only output; "+" means read+write.

// volatile: prevents the compiler from reordering or eliding the asm.

The PTX template uses %0, %1, ... as placeholders for the operands in declaration order (outputs first, then inputs). Everything else is verbatim PTX. The compiler validates the operand types against the constraints — a type mismatch is caught at compile time, not at run time. This is one of the reasons inline PTX in CUDA is safer than inline ASM in GCC.

3.4The mma.sync PTX Instruction

Where the tensor cores actually live

On Ampere, the PTX instruction for an FP16-input / FP32-accumulator Tensor-Core MMA looks like:

mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 {%0,%1,%2,%3}, // D — accumulator out, 4 × f32 per thread {%4,%5,%6,%7}, // A — 4 × b32 per thread (8 fp16 packed) {%8,%9}, // B — 2 × b32 per thread (4 fp16 packed) {%10,%11,%12,%13}; // C — accumulator in, 4 × f32 per thread

Every token in the mnemonic carries meaning:

  • mma — matrix multiply-accumulate.
  • sync — synchronizes the warp; all 32 threads must execute together.
  • aligned — operand addresses are assumed properly aligned.
  • m16n8k16 — the operation tile shape: A is 16 (M) × 16 (K), B is 16 (K) × 8 (N), C and D are 16 (M) × 8 (N).
  • row.col — A is row-major, B is column-major (the "TN" form, the most natural for the hardware).
  • f32.f16.f16.f32 — the precisions of D, A, B, C respectively. So FP16 inputs, FP32 accumulators.

The register-layout requirement

The catch — and the reason this PTX is not for the faint of heart — is that each operand fragment is distributed across the 32 threads of the warp in a hardware-mandated pattern. For m16n8k16 FP16:

  • A (16×16, FP16): each thread owns 8 FP16 elements = 4 × 32-bit registers, in a specific (lane → element) mapping defined in the PTX ISA.
  • B (16×8, FP16): each thread owns 4 FP16 elements = 2 × 32-bit registers.
  • C, D (16×8, FP32): each thread owns 4 FP32 elements = 4 × 32-bit registers.

If you load the wrong element into the wrong lane, the multiply produces garbage. There is no run-time error and no way to discover this except by checking the output.

ldmatrix.sync — the partner instruction

Manually shuffling 32 lanes into the right layout is error-prone and slow. NVIDIA provides ldmatrix.sync, a PTX instruction that loads up to four 8×8 FP16 matrices from shared memory directly into the register pattern expected by mma.sync. It is the canonical loader.

// Load four 8x8 fp16 matrices from shared memory.
// %0..%3 are output: 4 × .b32 registers per thread (each register holds 2 fp16).
// %4 is input: shared-memory address (each lane provides its own address;
// the hardware reads the addresses from 8 of the 32 lanes per matrix).
//
// .x4   = four 8x8 matrices loaded in one call
// .trans = optional, transposes each 8x8 (so A can be loaded as row-major from
//          col-major shared memory, or vice versa).
//
// Usage from CUDA C++:

uint32_t r0, r1, r2, r3;
uint32_t smem_addr = __cvta_generic_to_shared(&smem_ptr[some_index]);
asm volatile(
    "ldmatrix.sync.aligned.m8n8.x4.shared.b16 "
    "{%0, %1, %2, %3}, [%4];\n"
    : "=r"(r0), "=r"(r1), "=r"(r2), "=r"(r3)
    : "r"(smem_addr));
