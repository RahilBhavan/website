A research-backed guide for Rahil. Written November 10, 2026.

The recommendation: keep the layered architecture: coordinate heavy work before it starts, measure each job separately, retain kernel reclaim and compressed swap, preserve the services needed to control the machine, and tune from representative observations. This is a strong fit for a shared development desktop. It is not yet a demonstrated optimum, and several current numbers remain operating choices.

The point is to keep useful work moving while the desktop and agent controls remain usable. Empty RAM is not the goal. Neither is maximum concurrency at any cost.

The argument in one page

The box hosts different kinds of work. A compositor must answer promptly. A build needs sustained resources and a correct result. An agent conversation needs to survive long enough to report, recover and coordinate. A policy that treats every allocation and process as equally urgent misses these differences.

The chosen architecture addresses this through several distinct decisions:

  • Admission: defer some heavy work before it adds demand. The shared gate currently permits two participating heavy jobs, subject to available-memory and pressure checks.
  • Attribution: give newly launched participating host jobs their own systemd scopes. A job's peak and events can then be examined without confusing them with the launching agent's entire lifetime.
  • Reclaim and compression: retain MGLRU and zram so the kernel has ways to handle inactive memory instead of immediately depending on disk or killing work.
  • Containment and recovery: keep aggregate agent ceilings, distinguish the desktop session from the app kill domain, and bias out-of-memory selection away from the T3 server.
  • Evidence: record completed jobs, inspect short stalls as well as averages, and judge success by responsiveness, correctness and total completion time—including time in the queue.

These are complementary controls. A queue cannot reclaim an application's memory after admission. zram cannot prevent an unlimited set of jobs from demanding RAM. A cgroup cannot show whether the user liked the desktop response. Measurements cannot recover lost work. The layers address different failure modes.

What “best” can honestly mean here

There is no single scalar to maximize. More build concurrency can shorten a particular queue while increasing interference. Compression can preserve capacity while consuming CPU. Stronger protection can save one service by leaving less memory available to others. Earlier killing can shorten a freeze while discarding work.

For this machine, a reasonable decision order is:

  1. Preserve correctness, personal data and required validation.
  2. Preserve usable desktop and control services.
  3. Keep background work recoverable and fairly served.
  4. Improve completed useful work per unit of time.
  5. Reduce memory consumption where it improves those outcomes.

That ordering is an engineering recommendation grounded in the user's mixed desktop workload. It is not a theorem from a paper. Calling a specific configuration best would require testing plausible alternatives against those goals under representative conditions.

Current evidence boundary

On November 10, the display-off probe completed 602 real compositor requests without a timeout. The largest sampled reply was 4.063 ms. This is a narrow finding about the control path under the existing SSRD CPU job and browser batch. It does not measure displayed frames, unlocked interaction or a completed build. The attempted controlled build timed out in the shared queue before executing.

No host setting changed during that measurement or while authoring this guide. The guide makes recommendations and explains controls; it does not install them.
