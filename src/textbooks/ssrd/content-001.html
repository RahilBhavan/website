1.3 What already exists, and what is new

Most of SSRD's parts have been done before. Knowing the prior art keeps the claim honest:

  • phishing_catcher scores CT names by keywords. That is SSRD's first filter (chapter 3).
  • dnstwist compares pages with TLSH (--lsh tlsh), SSRD's content signal (chapter 5).
  • Phillips & Wilder 2020 clustered crypto-scam pages from urlscan snapshots with TF-IDF and DBSCAN, after normalizing the HTML. This is the published baseline. Read its method section on Oct 22.
  • Commercial tools (urlscan Pro "Similar Pages", Validin, DomainTools, Silent Push) already pivot on page structure and favicons.

The likely new part is narrow: a respawn metric (time from a dated takedown to the first matching new domain), and an open, auditable precision number for one network that law enforcement cares about. Using the Bank of Russia (CBR) blacklist as a near-daily ground-truth stream may also be new. The research pass found no published use of it, but that is unverified.

1.4 Three facts that shape every later chapter

  1. Cloaking is the default. Investment-scam sites often show a harmless "white page" to visitors who don't look like victims. Infoblox and Confiant counted about 15.5k investment-scam domains doing this through Keitaro. So "decoy" is its own outcome, reported next to precision (chapters 4 and 8).
  2. The takedown hit the backend. Live respawns from Oct 19 to Nov 15 may be rare. The CBR forward check and the seed backtest exist so a precision number can exist even if few new sites appear (chapter 8).
  3. The KCDA seed set is thin. Only 13 seeds, and the pre-seizure pages recovered from the Wayback Machine are generic WordPress + Elementor sites. Asset hashes can't separate them from ordinary Elementor sites. The page copy can, which is why the copy fingerprint exists (chapter 5.6).

How a public log tells you a domain was born

Before a browser trusts a certificate, the certificate has to appear in a public, append-only log. Scam operators need HTTPS for their platform to look real. So nearly every new scam domain announces itself in a certificate transparency (CT) log, usually minutes before the site goes live.

What you'll learn
Merkle-tree logs, checkpoints, tiles, names tiles, precertificates and the tailer's algorithm.
Why it matters
Time to flag starts at the CT timestamp, and ingest bandwidth decides whether the box can keep up.
In the repo
src/ssrd/ct.py: Tailer.poll_log, tile_path, handle_entry.

2.1 Why the logs exist

CT was built so that anyone can spot a certificate a CA should never have issued. Certificate authorities submit each certificate to several logs, and browsers require proof of logging (signed certificate timestamps, SCTs). To put those proofs inside the certificate itself, the CA first logs a precertificate, a copy marked unusable, and only then issues the real one. The precertificate is why the log entry arrives seconds after issuance, and often before the site is serving anything.

SSRD uses the logs for a job they weren't designed for: a near-real-time feed of newly certified names. Anyone can read them, and the CA logs certificates for every domain it issues to, so a scam domain on a CA that logs (all public CAs do) can't avoid appearing.

2.2 Merkle trees, checkpoints and tiles

A log is a Merkle tree. Each entry is a leaf. Each parent node is the hash of its two children, so the single root hash commits to every entry below it. Change one old entry and the root changes, so a log can't quietly rewrite history. The log publishes a signed checkpoint: its name, the tree size and the root hash.

Older logs answered queries through an API (get-entries), which was expensive to run. Static CT logs (Sunlight is the main implementation) publish the tree as plain files instead, cut into tiles of 256 entries. A full tile never changes, so it can be cached forever. Let's Encrypt now runs only these tiled logs, so an old-API reader misses every Let's Encrypt certificate.

2.3 Names tiles: the reason this runs on home Wi-Fi

A normal data tile carries whole certificates. Some static-CT logs also serve a compact names tile: one JSON line per entry, with just the DNS names, the subject common name and a timestamp. This is an extra endpoint, not part of the core spec. On Oct 17 the Let's Encrypt Sycamore and Willow logs and Geomys Tuscolo served it. Google's and IPng's logs did not.

Back-of-envelope: is the bandwidth affordable?

  • Measured: about 76 KB per 256-entry names tile, about 6× smaller than a data tile. That is about 0.3 KB per entry.
  • Measured: about 25 entries a second per Let's Encrypt log.
  • 25 × 0.3 KB ≈ 7.5 KB/s per log ≈ 650 MB/day per log. Two LE logs plus Tuscolo come to a few GB a day at most.
  • The alternative, certstream-server-go reading every log, was estimated at about 14.5 Mbit/s (≈ 4.7 TB/month; likely, not measured). That is why SSRD has its own tailer.

2.4 The tailer, step by step

  1. GET <log>/checkpoint. The second line is the tree size.
  2. First run only: start at the current head, rounded down to a tile boundary. The tailer never backfills further back than where it first started.
  3. While the next tile is full: fetch /tile/names/<path>. The path encodes the tile number in groups of three digits, so tile 1234067 is x001/x234/067.
  4. For each entry, collect its names (SANs plus the common name), reduce each to its registrable domain (chapter 3), skip names already in the seen-set and run the filter.
  5. Save the new position in ct_state after every tile, so a sleeping box resumes where it stopped.
  6. On HTTP 429, back off 30 s and try the next log. Count bytes, entries, names and filter passes for metrics.jsonl.

Two details are easy to miss. Wildcard names (*.example.com) lose the *., so SSRD sees the registrable domain but not the subdomains the site will use. And about 1 in 1,000 registrable names is kept unfiltered as a background sample, picked by crc32(name) % 1000 == 0. These are the negatives that trained the name classifier. Because the choice is a hash and not a random draw, a given name is always in or always out of the sample, whichever log it came from and however often the tailer restarts.

Check yourself

Why does a Merkle root stop a log from rewriting an old entry?
The root hash depends on every leaf. A changed leaf changes its parent, and so on up to the root, so the signed checkpoints people already saw would no longer match.
What would break if the tailer read the partial tile 2 in Fig 2.1 and moved on?
It would save position 11 and never come back for entry 11 when it arrives. Or, if it re-read, it would process 8–10 twice. Reading only full tiles keeps the position simple, and the cost is about 10 s of latency.
A scam site uses a wildcard certificate made months ago. Does SSRD see its new subdomain?
No. No new certificate means no new log entry. This is one of the memo's stated limitations (wildcard certs, and the CT-only view).
Why use a hash for the 1-in-1,000 background sample instead of random()?
It is deterministic. The same name gets the same decision on every log and after every restart, so the sample doesn't drift or double-count.
