CUDA Programming:
From Syntax to Shared Memory

Learning goal. Write, compile, and run a correct CUDA kernel. Understand the programming model deeply enough to walk a GEMM from naive → coalesced → shared-memory tiled → register-tiled → vectorized, and time each version honestly.

2.1The CUDA Programming Model

A small surface area on top of C++

CUDA is a small dialect of C++ — about a dozen keywords and a couple of built-in variables. Everything else is ordinary C++. The keywords you must know cold:

KeywordMeaningExample
__global__Kernel: callable from host, runs on device, returns void.__global__ void k(...){}
__device__Helper function callable only from device code.__device__ float relu(float)
__host__Runs on the CPU (default for ordinary functions). Combinable with __device__ for dual-mode functions.__host__ __device__ int min(...)
__shared__Allocates memory in the SM's shared memory; per-block scope.__shared__ float t[32][32];
__constant__Read-only memory cached in a dedicated constant cache. 64 KB total per kernel.__constant__ float cf[64];
__syncthreads()Block-wide barrier. Every thread in the block must reach it.__syncthreads();
<<<grid, block>>>Kernel launch syntax. Takes 1D, 2D, or 3D grid and block dimensions.k<<<128, 256>>>(x);
threadIdx, blockIdx, blockDim, gridDimBuilt-in uint3-like variables visible inside every kernel.int t = threadIdx.x;
warpSizeBuilt-in constant. Always 32 today; coded as a variable for forward compatibility.if (t < warpSize) ...

Host ↔ device execution model

The host (CPU) launches a kernel asynchronously — control returns to the host as soon as the launch is enqueued; the GPU runs the kernel concurrently with subsequent host code. You synchronize explicitly with cudaDeviceSynchronize() or, more idiomatically, by recording a cudaEvent_t and waiting on it. All cudaMemcpy calls without a stream argument are implicitly synchronous; the asynchronous variant is cudaMemcpyAsync.

Error handling

Every CUDA API call returns cudaError_t. Kernel launches return errors through the next call to cudaGetLastError(). Wrap every CUDA call; otherwise a failed kernel will silently corrupt your output and you will spend hours blaming your algorithm.

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

#define CUDA_CHECK(x) do {                                          \
    cudaError_t _e = (x);                                            \
    if (_e != cudaSuccess) {                                         \
        fprintf(stderr, "CUDA error %s at %s:%d -> %s\n",          \
                cudaGetErrorName(_e), __FILE__, __LINE__,            \
                cudaGetErrorString(_e));                             \
        std::exit(1);                                                \
    }                                                                \
} while (0)

// Device helper — runs on the GPU, callable only from device code.
__device__ float relu(float x) { return x > 0.f ? x : 0.f; }

// Kernel — entry point. Called from host, runs on device.
__global__ void scaleAndReluKernel(float* __restrict__ out,
                                   const float* __restrict__ in,
                                   float scale,
                                   int N)
{
    // Map this thread to one element of the output.
    int idx = blockIdx.x * blockDim.x + threadIdx.x;

    // Always bounds-check: the grid is rounded up, so the last
    // block has more threads than there is work.
    if (idx < N) {
        out[idx] = relu(in[idx] * scale);
    }
}

int main() {
    const int N = 1 << 20;                     // 1,048,576 elements
    const size_t bytes = N * sizeof(float);

    // 1) Allocate host buffers and initialize input.
    float* h_in  = (float*)std::malloc(bytes);
    float* h_out = (float*)std::malloc(bytes);
    for (int i = 0; i < N; ++i) h_in[i] = (float)(i - N/2);

    // 2) Allocate device buffers.
    float *d_in, *d_out;
    CUDA_CHECK(cudaMalloc(&d_in,  bytes));
    CUDA_CHECK(cudaMalloc(&d_out, bytes));

    // 3) Copy input H->D.
    CUDA_CHECK(cudaMemcpy(d_in, h_in, bytes, cudaMemcpyHostToDevice));

    // 4) Launch: block of 256 threads, ceil(N / 256) blocks.
    const int blockSize = 256;
    const int gridSize  = (N + blockSize - 1) / blockSize;
    scaleAndReluKernel<<<gridSize, blockSize>>>(d_out, d_in, 2.5f, N);
    CUDA_CHECK(cudaGetLastError());     // catch launch-config errors
    CUDA_CHECK(cudaDeviceSynchronize()); // catch run-time errors

    // 5) Copy result D->H.
    CUDA_CHECK(cudaMemcpy(h_out, d_out, bytes, cudaMemcpyDeviceToHost));

    // 6) Quick sanity check on a few elements.
    printf("out[0] = %f  out[N-1] = %f\n", h_out[0], h_out[N-1]);

    // 7) Cleanup.
    CUDA_CHECK(cudaFree(d_in));
    CUDA_CHECK(cudaFree(d_out));
    std::free(h_in);
    std::free(h_out);
    return 0;
}

// Compile (Ampere consumer):
//   nvcc -O3 -arch=sm_86 -o scale scale.cu
// Compile (A100):
//   nvcc -O3 -arch=sm_80 -o scale scale.cu
// Compile with line info for source-level profiling (chapter 4):
//   nvcc -O3 -arch=sm_86 -lineinfo -o scale scale.cu

What the compile flags mean

  • -O3: aggressive C++ optimization, same as host-side g++/clang.
  • -arch=sm_86: generate SASS for Ampere GA10x consumer cards. sm_80 for A100, sm_89 for Ada (RTX 40-series), sm_90 for Hopper (H100). Wrong arch == suboptimal codegen at best, compile failure at worst.
  • -lineinfo: emit SASS↔source line correlation. Required for Nsight Compute's Source View. Adds zero performance cost.
  • -Xptxas -v: print per-kernel register, SMEM, and stack-frame usage at compile time — invaluable when chasing occupancy.
  • --use_fast_math: enable approximated transcendentals (sin, cos, log) — only for kernels where you have audited that loss of precision.

2.2Kernel 1 — Naive GEMM

The simplest correct kernel, and why it is slow

The simplest GEMM kernel: launch one thread per output element. Each thread loops over K, accumulating into a register. This is correct, easy to read, and slow.

// Computes C = A * B where A is M x K, B is K x N, C is M x N (row-major, FP32).
__global__ void gemmNaive(const float* __restrict__ A,
                          const float* __restrict__ B,
                                float* __restrict__ C,
                          int M, int N, int K)
{
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= M || col >= N) return;

    float acc = 0.f;
    for (int k = 0; k < K; ++k) {
        acc += A[row * K + k] * B[k * N + col];   // 2 global loads per inner iter
    }
    C[row * N + col] = acc;                       // 1 global store
}

// Launch: 16x16 = 256 threads/block.
const int TX = 16, TY = 16;
dim3 block(TX, TY);
dim3 grid((N + TX - 1) / TX, (M + TY - 1) / TY);
gemmNaive<<<grid, block>>>(d_A, d_B, d_C, M, N, K);

Why it is slow — by the numbers

For M = N = K = 4096, FP32, on the RTX 3090:

  • Total threads: M·N = 16,777,216.
  • Global loads per thread: 2·K = 8,192.
  • Total global loads: 2·M·N·K = 1.37 × 1011, at 4 bytes each, ≈ 549 GB.

At the RTX 3090's peak DRAM bandwidth of 936 GB/s, just moving the loads takes 549 / 936 = 0.587 s. Add in poor coalescing, cache pressure, and the fact you can never reach peak bandwidth in practice, and the naive kernel measures in hundreds of milliseconds on a problem that cuBLAS finishes in ones of milliseconds.

The fundamental waste: every element of A is read N times and every element of B is read M times. The same word of DRAM crosses the memory bus thousands of times. Tiling exists to read each word from DRAM once and reuse it from on-chip memory thereafter.

2.3Kernel 2 — Memory Coalescing

The cheapest 5×–10× you will ever get

Look closely at the naive kernel's inner-loop loads:

// Warp = 32 threads with consecutive threadIdx.x, same threadIdx.y.
// row = blockIdx.y * blockDim.y + threadIdx.y   -> constant across the warp
// col = blockIdx.x * blockDim.x + threadIdx.x   -> consecutive across the warp

// LOAD 1: A[row * K + k]
//   Index does not depend on threadIdx.x -> ALL 32 threads load the SAME address.
//   The hardware broadcasts this single value to the whole warp -> 1 transaction. Good.

// LOAD 2: B[k * N + col]
//   col = ... + threadIdx.x -> consecutive threads hit consecutive columns of B.
//   In a row-major B, that means consecutive 4-byte words -> ONE 128-byte
//   transaction per warp. Good.

So this mapping is already coalesced. The hazard arises when programmers reverse the axes by accident. Swap the row/col definitions:

int row = blockIdx.x * blockDim.x + threadIdx.x;   // consecutive across warp
int col = blockIdx.y * blockDim.y + threadIdx.y;   // constant across warp

float acc = 0.f;
for (int k = 0; k < K; ++k) {
    // LOAD: B[k * N + col]
    // col is constant across the warp -> broadcast load. Fine.
    // LOAD: A[row * K + k]
    // row is consecutive across the warp -> consecutive ROWS of A,
    // strided by K elements per row -> up to 32 separate cache lines.
    // That is a 32x bandwidth waste per inner iteration.
    acc += A[row * K + k] * B[k * N + col];
}

The lesson is not "swap row and col." The lesson is: pick the loop nest and the thread layout so the fast-varying thread axis runs along the fast-varying memory axis. For row-major matrices, that means threadIdx.x indexes columns.

What you can prove by reading PTX

Compile both versions with nvcc -arch=sm_86 -ptx -O3. In the well-formed kernel, the inner-loop loads from B compile to ld.global.f32 instructions whose addresses differ by 4 bytes across consecutive threads — which the hardware turns into a single 128-byte transaction. In the swapped version, the same instruction appears, but the addresses differ by 4·N bytes — and the hardware issues up to 32 separate transactions. The SASS (cuobjdump --dump-sass) shows the same number of LDG instructions for both kernels; the bus traffic and the L1 sector counts differ wildly. This is why looking only at the source code or only at the instruction count lies to you about cost.

Diagnostic
Nsight Compute exposes the coalescing penalty as the ratio between "Sectors / Request" and the ideal of 1.0 in the Memory Workload Analysis. A ratio of 4× means each warp is touching four 32-byte sectors when one would have sufficed.
