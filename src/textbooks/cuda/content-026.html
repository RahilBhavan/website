7.1Warp Reduce — Sub-Microsecond Sums

The fastest 32-lane primitive a GPU can do
[[A7.1.1]]

Butterfly reduction with __shfl_xor_sync

reduction

Reduce 32 values held in lane registers to a single scalar in 5 steps with the XOR-butterfly pattern: each step swaps with the lane k bits away and accumulates. No shared memory, no barriers, ~5 cycles per step. The idiom every CUDA programmer must memorize:

for (int offset = 16; offset > 0; offset /= 2) val += __shfl_xor_sync(0xFFFFFFFF, val, offset);

After the loop, every lane in the warp holds the same total. To turn a warp-reduce into a warp-broadcast, the answer is already broadcast. To get only one lane to write it out, gate with if (laneIdx() == 0).

7.2Block Reduce — Compose Warp Reduces with Shared Memory

[[A7.2.1]]

Two-stage block reduction

reduction

Stage 1: every warp reduces its 32 lanes to one value via [[A7.1.1]]. Stage 2: lane 0 of each warp writes its result to __shared__ float warp_sums[32]; one __syncthreads; then warp 0 reads the 32 partial sums (one per warp), does another warp reduction, and lane 0 of warp 0 owns the block total. Total cost: 2 warp reductions plus one barrier. For a 1024-thread block that is ~10 cycles of math plus the barrier latency — orders of magnitude faster than a shared-memory tree.

Trap

If your block has fewer than 32 warps (block size < 1024), the warp-0 reduction at stage 2 must guard inactive lanes — they hold garbage, not zero. Either zero-initialize warp_sums, or pass an identity value, or gate the second reduce by laneIdx() < numWarps.

7.3Grid Reduce — Three Strategies

[[A7.3.1]]

Atomic vs two-pass vs cooperative-grid

reduction
  • Atomic add Each block does its own reduction, then lane 0 calls atomicAdd to a single device-side accumulator. Simple, fast for ≤ a few hundred blocks; serializes for thousands.
  • Two-pass Kernel 1: each block writes its reduction to out[blockIdx.x]. Kernel 2: a small launch reduces the partial results. Standard portable pattern; one extra launch.
  • Cooperative grid cg::this_grid().sync() after stage 1, then stage 2 inside the same kernel. Eliminates the second launch but requires a cooperative launch and bounds your grid to "fits on the device."

For a 4 GB tensor on an A100, all three reach > 90% of peak bandwidth. Pick atomic for small grids, two-pass for portability, cooperative for tight per-step kernels (e.g., per-iteration norm-of-residual in a numerical solver).

7.4Prefix Sums — Hillis-Steele, Blelloch, Decoupled-Lookback

[[A7.4.1]]

Hillis-Steele — O(n log n) work, O(log n) span, simple

scan

At step k, every thread reads the value at offset 2k behind it and accumulates. After log₂ n steps, every position holds the prefix sum. Work is n log n — suboptimal — but span is log n and the implementation is one warp-shuffle per step. Right answer for small problems (a single block) where the constant matters more than the asymptotic work.

Builds on [[A2.9.2]]
Contrast [[A7.4.2]]
[[A7.4.2]]

Blelloch — O(n) work, two-phase up/down sweep

scan

Phase 1 (up-sweep): build a binary tree of partial sums in place, like a heap. Phase 2 (down-sweep): propagate prefixes back down. Total work is exactly 2n − 2 — work-optimal — and the span is still O(log n). Standard library scans (CUB BlockScan, Thrust inclusive_scan) use Blelloch variants for the within-block stage.

Contrast [[A7.4.1]]
[[A7.4.3]]

Decoupled lookback — single-pass grid-wide scan

scan

A textbook grid-wide scan needs two passes: compute block partials, then offset each block by the prefix of its partials. Decoupled lookback (Merrill & Garland, 2016) fuses both into one pass. Each block, after its local scan, publishes a status flag and waits for the previous block's flag, then aggregates the previous block's prefix. With careful memory-fencing this runs at near-peak HBM bandwidth in a single kernel. CUB's DeviceScan uses it; it is the production-grade primitive.

7.5Histograms — Privatization Beats Atomics

[[A7.5.1]]

Privatized histogram — per-block bins in shared memory

building-block

Naive histogram: every thread does atomicAdd(&hist[bin], 1) in global memory. For a highly skewed distribution every thread targets the same bin → 32-way serialization → 100×-slow kernel. Privatized fix: each block keeps its own histogram in shared memory (atomicAdd on shared is ~10× faster), then once at the end the block reduces its private histogram into the global histogram with one atomic per bin. Memory traffic equals the input size and a small constant. This is the canonical "atomics ≠ slow, atomics on global ≠ atomics on shared" lesson.

7.6Transpose and Sort — Memory Stories

[[A7.6.1]]

Tile-based transpose with padded shared memory

building-block

Naive transpose has half-coalesced loads or half-coalesced stores — whichever dimension you stride. The standard fix: load a 32×32 tile into shared memory with row-major coalescing, __syncthreads, then store it out column-major. Without padding the store is a 32-way bank conflict; pad to [32][33] (see [[A1.4.1]]) and the conflict disappears. This is the canonical bank-conflict teaching example.

Builds on [[A1.4.1]] [[A1.4.2]]
[[A7.6.2]]

Radix sort — scan-based, the fast GPU sort

building-block

Comparison sorts have a hard n log n lower bound; radix sort doesn't, because it pre-commits to a fixed bit-width. Per pass: count keys by their k-bit digit (histogram), compute the per-digit offsets (scan), scatter keys into their new positions (memcpy by index). Each pass is two memory-bound kernels; for 32-bit keys, 4 passes of 8-bit radix = 8 kernels total. CUB DeviceRadixSort is the reference implementation; for a 1 G-element array it hits ~80% of HBM bandwidth on an A100.
